> **프로세스와 스레드의 차이에 대해 설명해주세요.**

이 질문을 이해하기 위해 다음 개념들을 함께 공부했다.

```text
Program
↓
Process
↓
PCB
↓
Process Memory
├─ Code
├─ Data
├─ Heap
└─ Stack

Process
├─ Thread A
├─ Thread B
└─ Thread C
```

그리고 여기서 다시 다음 주제로 확장했다.

```text
Process / Thread
↓
Memory 구조
↓
Code / Data / Heap / Stack
↓

↓
JVM과 OS의 관계
↓
JDK와 JVM의 관계
```

# 1. Program과 Process의 차이

## Program

프로그램은 아직 실행되지 않은 **정적인 코드 파일**이다.

예:

```text
chrome.exe
Main.class
실행 파일
```

디스크 등에 저장되어 있는 상태다.

---

## Process

프로그램을 실행하면 운영체제가 실행에 필요한 자원을 할당한다.

```text
Program
   ↓ 실행
Process
```

프로세스는 단순히 "실행 중인 프로그램"이라고 할 수도 있지만, 조금 더 정확하게는:

> **운영체제로부터 독립적인 가상 주소 공간과 각종 시스템 자원을 할당받아 실행되고 있는 프로그램의 인스턴스**

라고 볼 수 있다.

프로세스가 사용할 수 있는 자원에는 다음과 같은 것들이 있다.

```text
Process
│
├─ Virtual Address Space
│  ├─ Code
│  ├─ Data
│  ├─ Heap
│  └─ Stack
│
├─ CPU 실행 시간
├─ PID
├─ 열린 파일
├─ Socket
├─ 권한 정보
└─ 기타 OS 자원
```

즉 Code, Data, Heap, Stack은 **프로세스가 받는 모든 자원 그 자체가 아니라, 프로세스의 메모리 주소 공간을 구성하는 일부**다.

---

# 2. PCB란 무엇인가?

PCB는 **Process Control Block**의 약자다.

운영체제가 각각의 프로세스를 관리하기 위해 사용하는 자료구조다.

개념적으로 다음과 같은 정보가 포함된다.

```text
PCB
├─ PID
├─ Process State
├─ Program Counter
├─ CPU Register 상태
├─ Scheduling 정보
├─ Memory 관리 정보
├─ 열린 파일 정보
└─ 기타 프로세스 관리 정보
```

PCB는 프로세스 자체의 메모리 공간이라기보다:

> **운영체제가 해당 프로세스를 기억하고 관리하기 위한 기록부**

라고 이해하는 것이 좋다.

예를 들어 CPU가 Process A에서 Process B로 변경될 때:

```text
Process A 실행
↓
A의 실행 상태 저장
↓
PCB A

PCB B에서 실행 상태 복원
↓
Process B 실행
```

이 구조가 나중에 배우게 될 **Context Switching**과 직접 연결된다.

---

# 3. Process와 Thread의 관계

프로세스는 하나 이상의 Thread를 가질 수 있다.

```text
Process
├─ Thread A
├─ Thread B
└─ Thread C
```

## Thread

Thread는:

> **프로세스 내부에서 실제 명령어를 실행하는 실행 흐름**

이다.

프로세스가 실행에 필요한 **자원과 환경의 단위**라면, Thread는 그 안에서 CPU를 이용하여 **실제로 실행되는 흐름의 단위**라고 보면 된다.

핵심:

```text
Process
→ 자원과 주소 공간의 단위

Thread
→ 실제 실행 흐름의 단위
```

---

# 4. 여러 Thread는 무엇을 공유하는가?

같은 Process 내부의 Thread들은 프로세스 자원의 상당 부분을 공유한다.

```text
Process

공유
├─ Code
├─ Data
├─ Heap
└─ 열린 파일 등의 프로세스 자원

Thread마다 독립
├─ Stack
├─ Register
├─ Program Counter
└─ 실행 상태
```

그림으로 보면:

```text
Process
│
├─ Code       ← 공유
├─ Data       ← 공유
├─ Heap       ← 공유
│
├─ Thread A
│  ├─ Stack A
│  ├─ Register
│  └─ PC
│
├─ Thread B
│  ├─ Stack B
│  ├─ Register
│  └─ PC
│
└─ Thread C
   ├─ Stack C
   ├─ Register
   └─ PC
```

---

# 5. 왜 Thread마다 Stack을 따로 가질까?

Thread마다 현재 실행하고 있는 함수가 다를 수 있기 때문이다.

예를 들어:

```text
Thread A
→ foo() 실행 중

Thread B
→ bar() 실행 중
```

각 Thread는 서로 다른:

- 함수 호출 정보
    
- 지역 변수
    
- 반환 주소
    
- 현재 실행 위치
    

를 가지고 있어야 한다.

따라서 Stack은 Thread별로 독립적이다.

---

# 6. 왜 Program Counter와 Register도 Thread마다 따로 가질까?

각 Thread가 실행 중인 위치와 CPU 상태가 서로 다르기 때문이다.

예:

```text
Thread A
→ 100번째 명령어까지 실행

Thread B
→ 500번째 명령어까지 실행
```

Scheduler가 Thread A → B → A 순으로 전환한다면, 다시 A로 돌아왔을 때 어디부터 실행해야 하는지 기억해야 한다.

그래서 Thread마다 다음 정보가 필요하다.

```text
Program Counter
→ 현재 어디까지 실행했는가

Register
→ 현재 CPU 연산 상태는 무엇인가
```

---

# 7. 프로세스끼리는 왜 데이터를 바로 공유하지 못할까?

서로 다른 프로세스는 기본적으로 **독립된 가상 주소 공간**을 가진다.

```text
Process A
Memory A

Process B
Memory B
```

따라서 A가 B의 메모리를 직접 읽거나 수정하지 못한다.

이를 **Process Isolation**이라고 한다.

프로세스끼리 데이터를 주고받기 위해서는 별도의 IPC가 필요하다.

## IPC

**Inter-Process Communication**

대표적인 방법:

- Pipe
    
- Socket
    
- Shared Memory
    
- Message Queue
    

```text
Process A
   │
   │ IPC
   ↓
Process B
```

---

# 8. Thread끼리는 왜 데이터 공유가 쉬울까?

같은 프로세스의 Thread들은 Data와 Heap 등의 영역을 공유하기 때문이다.

```text
Thread A ─┐
          ↓
      Shared Heap
          ↑
Thread B ─┘
```

따라서 공유 객체나 데이터를 쉽게 사용할 수 있다.

하지만 이것이 장점이면서 동시에 위험 요소다.

두 Thread가 동시에 같은 값을 수정하면 **Race Condition**이 발생할 수 있기 때문이다.

```text
Thread
→ 데이터 공유 쉬움
→ Synchronization 필요
```

이 내용은 이후:

```text
Thread
↓
Race Condition
↓
Critical Section
↓
Synchronization
↓
Mutex / Semaphore
↓
Deadlock
```

으로 이어진다.

# 9. Process와 Thread 비교

|구분|Process|Thread|
|---|---|---|
|기본 의미|실행 중인 프로그램의 독립 실행 환경|프로세스 내부의 실행 흐름|
|주소 공간|프로세스마다 독립|같은 프로세스 내에서 공유|
|Code/Data/Heap|프로세스마다 독립|같은 프로세스 Thread끼리 공유|
|Stack|프로세스 내부 Thread별 존재|Thread마다 독립|
|Register/PC|실행 상태에 포함|Thread마다 독립|
|데이터 공유|IPC 필요|비교적 쉬움|
|생성 비용|상대적으로 큼|상대적으로 작음|
|Context Switching|상대적으로 무거움|같은 프로세스 내에서는 상대적으로 가벼움|
|격리성|높음|낮음|
|오류 영향|다른 프로세스와 격리|같은 프로세스 전체에 영향 가능|
|동기화 문제|상대적으로 적음|공유 자원 때문에 중요|

# 10. Process Memory의 기본 구조

전통적인 Native Process를 단순화하면:

```text
Process Virtual Address Space

┌─────────────┐
│ Code        │
├─────────────┤
│ Data        │
├─────────────┤
│ Heap        │
├─────────────┤
│ Stack       │
└─────────────┘
```

각 영역의 역할을 구분해야 한다.

---

# 11. Code 영역

Code 영역에는 CPU가 실행할 **기계어 명령어**가 저장된다.

예:

```c
int global = 10;

int main() {
    global++;
}
```

소스 코드에는 `global`도 있고 `global++`도 적혀 있지만, 실행 시에는 역할이 나뉜다.

```text
Code
→ global 값을 읽어라
→ 1을 더해라
→ 다시 저장해라

Data
→ global의 실제 값 10
```

즉:

> **소스 코드에 적혀 있다는 것과 실행 시 어느 메모리 영역에 존재하는지는 다른 문제다.**

---

# 12. Data 영역

C/C++의 일반적인 설명에서는 전역 변수와 static storage duration을 가진 데이터가 Data/BSS 영역과 연결된다.

예:

```c
int global = 10;
static int count = 20;
```

개념적으로:

```text
.data
→ 초기값이 존재하는 전역/static 데이터

.bss
→ 초기값이 없거나 0으로 초기화되는 전역/static 데이터
```

읽기 전용 상수 데이터는 `.rodata` 등에 위치할 수도 있다.

---

# 13. 전역 변수와 static 변수는 같은 분류가 아니다

초기에는 다음처럼 생각하기 쉽다.

```text
전역 변수
vs
static 변수
```

하지만 기준이 다르다.

## Global

주로 **어디에 선언되어 있는가 / 어떤 범위에서 이름을 사용할 수 있는가**에 대한 관점이다.

예:

```c
int global = 10;

void foo() {
    global++;
}
```

함수 바깥에 선언되어 있다.

---

## Static

문맥마다 의미가 다르지만 C 계열에서는 특히 **저장 수명과 linkage**에 영향을 준다.

예:

```c
void foo() {
    static int count = 0;
}
```

`count`는 `foo()` 안에서만 접근할 수 있지만 함수가 끝나도 값이 유지된다.

```text
Scope
→ foo 안

Lifetime
→ 프로그램 실행 전체
```

즉 **지역 범위를 가지는 static 변수**도 존재한다.

또:

```c
static int count = 10;
```

처럼 함수 밖의 static 변수도 가능하다.

따라서:

```text
Global
→ 선언 위치/범위 관점

Static
→ 저장 수명이나 linkage 관점
```

으로 구분해야 한다.

# 14. Heap 메모리와 Heap 자료구조는 같은 것인가?

아니다.

## Heap 자료구조

알고리즘에서 배우는:

```text
        1
      /   \
     3     5
```

같은 완전 이진 트리 기반 자료구조다.

주로:

- Priority Queue
    
- Heap Sort
    

등에 사용된다.

## Heap 메모리

프로그램 실행 중 **동적으로 메모리를 할당하는 영역**이다.

```text
malloc
new
동적 배열
객체
```

등과 관련된다.

핵심:

```text
Heap 자료구조
≠
Heap 메모리
```

이름만 같다.

---

# 15. Heap에는 무엇이 들어가는가?

Heap에는 특정 종류의 "변수"가 들어간다고 생각하기보다:

> **실행 중 동적으로 생성되고 함수 호출의 생명주기에 직접 묶이지 않는 데이터**

가 저장된다고 이해하는 것이 좋다.

대표적으로:

- `new`로 만든 객체
    
- `malloc()`으로 확보한 메모리
    
- 동적으로 생성된 배열
    
- 동적 버퍼
    

등이 있다.

---

# 16. Stack에는 무엇이 들어가는가?

Stack은 **Thread의 현재 함수 실행 상태**와 밀접하게 연결된다.

함수 호출마다 **Stack Frame**이 생성된다.

```text
Stack

┌───────────────┐
│ bar() Frame   │
├───────────────┤
│ foo() Frame   │
│ x = 10        │
│ return addr   │
└───────────────┘
```

Stack Frame에는 일반적으로:

- 지역 변수
    
- 함수 인자
    
- 반환 주소
    
- 저장해야 하는 Register 값
    
- 함수 호출과 관련된 상태
    

등이 존재할 수 있다.

함수가 끝나면 해당 Stack Frame도 제거된다.

---

# 17. Heap과 Stack의 본질적 차이

## Stack

```text
함수 호출
↓
Stack Frame 생성

함수 종료
↓
Stack Frame 제거
```

주로 **실행 흐름과 생명주기가 연결되어 있다.**

---

## Heap

```text
동적 데이터 생성
↓
Heap에 저장
↓
함수가 끝나더라도
계속 존재할 수 있음
```

C/C++에서는 `free`, `delete` 등을 통해 직접 해제할 수 있고, Java에서는 GC가 더 이상 참조되지 않는 객체를 회수한다.

---

# 18. Heap과 Stack 비교

|구분|Stack|Heap|
|---|---|---|
|목적|함수 호출 및 실행 상태|동적 데이터 저장|
|관리|Stack Frame 기반|Memory Allocator / GC 등|
|생명주기|주로 함수 실행과 연결|함수보다 오래 유지 가능|
|대표 데이터|지역 변수, 반환 주소 등|객체, 동적 배열 등|
|Thread 관계|Thread마다 별도|같은 Process Thread끼리 공유|

핵심:

```text
Stack
→ 이 Thread가 지금 무엇을 실행하고 있는가

Heap
→ Process가 동적으로 생성해서 유지하는 데이터
```

---

# 19. 여러 Thread가 만든 Heap 데이터는 어떻게 되는가?

같은 프로세스의 Thread들은 하나의 Heap을 공유한다.

```text
Process Heap

├─ Thread A가 생성한 객체
├─ Thread B가 생성한 객체
├─ Thread C가 생성한 배열
└─ ...
```

데이터가 의미 없이 뒤섞이는 것은 아니고, 메모리 관리자가 각 할당 영역을 관리한다.

예:

```text
0x1000 ~ 0x1099 → Object A
0x1100 ~ 0x11FF → Object B
0x1200 ~ 0x13FF → Array C
```

따라서:

> **여러 Thread가 동적으로 생성한 객체들은 같은 Process Heap에 존재할 수 있다.**

그리고 두 Thread가 같은 Heap 객체를 동시에 수정하면 Race Condition이 발생할 수 있다.

# 20. 지역 변수와 Heap 객체의 관계

Java에서:

```java
void foo() {
    int age = 20;
    Person p = new Person();
}
```

`age`와 `p`는 둘 다 **지역 변수**다.

하지만 메모리 구조는 다르다.

```text
Thread Stack

foo() Stack Frame
┌──────────────────┐
│ age = 20         │
│                  │
│ p = reference ───┼─────┐
└──────────────────┘     │
                         ↓
                       Heap

                 ┌──────────────┐
                 │ Person 객체  │
                 └──────────────┘
```

핵심:

```text
p
→ 지역 변수
→ Stack Frame에 존재하는 reference

new Person()
→ 실제 객체
→ Heap
```

---

# 21. 함수 안에서 객체를 생성하면 객체도 지역 변수인가?

아니다.

```java
Person p = new Person();
```

여기서:

```text
p
→ 변수
→ 함수 내부에서 선언
→ 지역 변수
```

반면:

```text
new Person()
→ 변수 아님
→ 생성된 객체
→ Heap
```

이다.

즉 **지역 변수 `p`가 Heap에 있는 Person 객체를 참조하는 것**이다.

# 22. 변수 종류와 메모리 위치를 혼동하면 안 된다

중요한 구분:

```text
변수의 종류
→ 프로그램 소스 구조 관점

Memory 영역
→ 프로그램 실행 시 저장 위치 관점
```

Java에서는 주요 변수 분류를 다음처럼 볼 수 있다.

```text
변수
├─ Local Variable
├─ Instance Field
└─ Static/Class Field
```

---

# 23. Instance Variable

예:

```java
class Person {
    int age;
    String name;
}
```

`age`, `name`은 **인스턴스 변수(instance field)**다.

객체마다 따로 존재한다.

```text
Heap

Person A
├─ age
└─ name

Person B
├─ age
└─ name
```

따라서 객체가 Heap에 있으면 인스턴스 필드도 객체의 일부로 Heap에 존재한다고 개념적으로 볼 수 있다.

---

# 24. Static Variable

예:

```java
class Person {
    static int population = 0;
}
```

static의 중요한 의미는:

> **특정 객체에 속하지 않고 해당 클래스에 하나 존재한다.**

```text
Person 객체 A ─┐
Person 객체 B ─┼→ Person.population 하나
Person 객체 C ─┘
```

모든 클래스가 모든 static 필드를 공유한다는 의미는 아니다.

```java
class A {
    static int x = 10;
}

class B {
    static int x = 20;
}
```

```text
A.x
→ 하나의 변수

B.x
→ 별개의 변수
```

즉:

> **같은 클래스의 인스턴스들이 하나의 static 필드를 공유한다.**

라고 이해해야 한다.

---

# 25. Java의 static 변수를 OS Data 영역에 넣는다고 보면 되는가?

그렇게 단순하게 대응하면 안 된다.

우리가 배우는:

```text
Code
Data
Heap
Stack
```

구조는 일반적인 native process의 메모리 구조를 단순화한 모델이다.

Java는 JVM 위에서 실행된다.

```text
Java Application
      ↓
     JVM
      ↓
Operating System
```

따라서 Java의 static field를:

```text
Java static
=
OS .data
```

라고 직접 대응하면 부정확하다.

---

# 26. OS와 JVM의 관계

우리가:

```bash
java Main
```

을 실행하면 OS는 JVM 구현체가 포함된 프로세스를 실행한다.

큰 흐름:

```text
Main.java
↓ javac
Main.class
↓
JVM
↓
Interpreter / JIT
↓
Machine Code
↓
CPU
```

OS 관점에서는 대략:

```text
OS

└─ JVM Process
   ├─ Memory
   ├─ Threads
   ├─ Files
   ├─ Sockets
   └─ 기타 OS Resource
```

를 실행하고 있는 것이다.

OS가 `Person`, `UserService`, `static field` 같은 Java 언어 개념을 직접 관리하는 것은 아니다.

---

# 27. JVM은 어떤 언어로 구현되어 있는가?

JVM은 우선 **명세(Specification)**다.

그 명세를 구현한 JVM 구현체가 존재한다.

대표적인 JVM 구현체:

```text
HotSpot
```

OpenJDK의 HotSpot은 핵심 부분이 주로 C++로 구현되어 있고 일부 C 및 Assembly 등의 저수준 코드도 사용한다.

즉:

```text
JVM Specification
      ↓ 구현
HotSpot
      ↓
실제 실행 가능한 JVM
```

이다.

---

# 28. JVM 메모리도 결국 OS 메모리인가?

그렇다.

JVM이 별도의 물리 메모리를 만드는 것은 아니다.

```text
Physical RAM
    ↑
OS Virtual Memory
    ↑
JVM Process
    ↑
JVM이 관리하는 Runtime Memory
```

JVM은 OS로부터 받은 가상 메모리를 자신만의 방식으로 다시 관리한다.

예:

```text
JVM Process Memory

├─ Java Heap
├─ JVM Thread Stack
├─ Metaspace / 클래스 관련 영역
├─ JIT Code Cache
├─ GC 관련 영역
└─ JVM 자체 native 데이터
```

---

# 29. JVM Heap과 OS Heap은 동일한가?

아니다.

```text
JVM Heap
≠
OS Process Heap
```

JVM은 OS가 제공한 가상 주소 공간 안에서 Java Heap을 포함한 여러 메모리 영역을 직접 구성하고 관리한다.

따라서 다음과 같이 1:1로 대응시키면 안 된다.

```text
OS Heap  = Java Heap      ❌
OS Stack = JVM Stack      ❌
OS Data  = Method Area    ❌
```

정확한 관계는:

```text
OS
↓
JVM Process에게 Virtual Memory 제공
↓
JVM
↓
자체적으로 Runtime Memory 구성

├─ Java Heap
├─ JVM Stack
├─ 클래스 관련 메모리
├─ Code Cache
└─ 기타
```

이다.

---

# 30. Java 관점에서의 메모리 구조

Java에서는 전통적인 Process Memory 구조보다 다음과 같이 생각하는 것이 더 유용하다.

```text
JVM

├─ Java Heap
│  └─ 객체 / 배열
│
├─ JVM Stack
│  └─ Thread별 Stack Frame
│
├─ Method Area 개념
│  └─ 클래스 관련 정보
│
├─ PC Register
│  └─ Thread별 실행 위치
│
└─ Native Method Stack 등
```

---

# 31. Java에는 C식 전역 변수가 없다

C에서는:

```c
int global = 10;
```

처럼 함수나 클래스 바깥의 전역 변수를 만들 수 있다.

Java에서는 클래스 밖에 변수를 선언할 수 없다.

```java
class A {

    static int x; // class/static field

    int y;        // instance field

    void foo() {
        int z;    // local variable
    }
}
```

따라서 Java에서는 일반적으로:

```text
static field
instance field
local variable
```

를 기준으로 이해하면 된다.

---

# 32. JDK와 JVM의 관계

JDK가 JVM 자체인 것은 아니다.

```text
JDK
├─ JVM 구현체
├─ Java 표준 라이브러리
├─ javac
├─ java
├─ jar
├─ javadoc
└─ 기타 개발 도구
```

즉:

```text
JVM
→ Java Bytecode를 실행하는 가상 머신

JDK
→ Java 개발과 실행에 필요한 전체 도구 묶음
```

이다.

대표적인 관계:

```text
JVM Specification
      ↓
HotSpot 구현
      ↓
JDK에 포함
```

# 33. 이 질문에서 최종적으로 이해해야 하는 구조

```text
Program
   ↓ 실행

Process
│
├─ OS가 PCB를 통해 관리
│
├─ 독립적인 Virtual Address Space
│
├─ 프로세스 자원
│
└─ 하나 이상의 Thread
       │
       ├─ Thread A
       ├─ Thread B
       └─ Thread C
```

Thread들은:

```text
공유
├─ Code
├─ Data
├─ Heap
└─ Process Resource

각자 보유
├─ Stack
├─ Register
├─ Program Counter
└─ 실행 상태
```

# 34. 처음 면접 질문으로 돌아가기

> **프로세스와 스레드의 차이에 대해 설명해주세요.**

## 면접 답변

프로세스는 실행 중인 프로그램으로, 운영체제로부터 독립적인 가상 주소 공간과 파일 등의 시스템 자원을 할당받는 실행 환경입니다.

스레드는 프로세스 내부에서 실제 명령어를 실행하는 실행 흐름입니다.

같은 프로세스의 여러 스레드는 Code, Data, Heap과 같은 프로세스 자원을 공유하지만 각각 자신의 Stack, Register, Program Counter를 가집니다.

따라서 스레드는 프로세스에 비해 데이터를 쉽게 공유할 수 있고 생성 및 Context Switching 비용도 일반적으로 더 작습니다.

반면 공유 자원을 여러 스레드가 동시에 접근할 수 있기 때문에 Race Condition과 같은 동기화 문제가 발생할 수 있으며, 하나의 스레드에서 발생한 심각한 오류가 같은 프로세스 전체에 영향을 줄 수도 있습니다.

서로 다른 프로세스는 주소 공간이 격리되어 있어 안정성과 독립성이 높지만, 데이터를 교환하려면 Pipe, Socket, Shared Memory 등의 IPC가 필요합니다.

---

# 35. 핵심 한 줄 정리

```text
Process
→ 독립적인 주소 공간과 자원을 가진 실행 환경

Thread
→ Process 내부에서 실제로 실행되는 흐름
```

그리고:

```text
Process는 자원의 단위
Thread는 실행의 단위
```

라고 기억하면 구조를 잡기 쉽다.

# 36. 헷갈리기 쉬운 포인트

### 1. Process = Code/Data/Heap/Stack 자체는 아니다

이들은 프로세스가 사용하는 **가상 주소 공간의 구성 요소**다.

---

### 2. 모든 지역 변수의 실제 데이터가 Stack에 존재하는 것은 아니다

```java
Person p = new Person();
```

에서:

```text
p
→ 지역 reference 변수

Person 객체
→ Heap
```

이다.

---

### 3. Heap에는 "Heap 변수"라는 별도의 변수 종류가 있는 것이 아니다

Heap에는 `new`, `malloc` 등을 통해 동적으로 확보한 객체와 데이터가 존재한다.

---

### 4. Heap 메모리와 Heap 자료구조는 별개의 개념이다

```text
Heap Memory
≠
Heap Data Structure
```

---

### 5. static은 모든 클래스가 하나를 공유한다는 의미가 아니다

```text
Person.population
→ Person 클래스 기준으로 하나
```

이다.

---

### 6. Java static field = OS Data 영역이라고 직접 대응하면 안 된다

Java는 JVM 런타임 메모리 모델을 통해 데이터를 관리한다.

---

### 7. JVM Heap과 OS Heap도 같은 개념이 아니다

JVM의 메모리 영역은 OS가 JVM 프로세스에 제공한 가상 메모리 위에 JVM이 구성한 런타임 영역이다.

# 37. 복습 질문

## Q1. Program과 Process의 차이는?

Program은 디스크에 존재하는 실행 가능한 코드이고, Process는 해당 Program이 실행되어 운영체제로부터 메모리와 여러 자원을 할당받은 실행 상태다.

---

## Q2. Process와 Thread의 가장 본질적인 차이는?

Process는 독립적인 주소 공간과 자원을 가진 실행 환경이고, Thread는 그 Process 내부에서 실제 명령어를 실행하는 흐름이다.

---

## Q3. 같은 Process의 Thread들은 무엇을 공유하는가?

Code, Data, Heap과 열린 파일 등의 프로세스 자원을 공유한다.

각 Thread는 Stack, Register, Program Counter 등을 별도로 가진다.

---

## Q4. Thread마다 Stack이 따로 필요한 이유는?

각 Thread가 서로 다른 함수를 실행할 수 있고, 함수 호출 정보와 지역 변수, 반환 주소 등 실행 상태가 서로 다르기 때문이다.

---

## Q5. 서로 다른 Process끼리는 왜 IPC가 필요한가?

각 Process는 독립적인 가상 주소 공간을 가지므로 다른 Process의 메모리에 직접 접근할 수 없기 때문이다.

---

## Q6. Thread를 사용하면 왜 Synchronization이 필요한가?

같은 Process의 Thread들이 Heap이나 Data 같은 공유 데이터를 함께 사용할 수 있으므로 동시에 같은 값을 수정하면 Race Condition이 발생할 수 있기 때문이다.

---

## Q7. Heap과 Stack의 가장 큰 차이는?

Stack은 각 Thread의 함수 호출과 실행 상태를 관리하고, Heap은 Process에서 동적으로 생성되어 함수 호출보다 긴 생명주기를 가질 수 있는 객체와 데이터를 관리한다.

---

## Q8. `Person p = new Person();`에서 지역 변수는 무엇인가?

`p`가 지역 변수다.

`new Person()`으로 만들어진 것은 변수가 아니라 Heap에 생성된 객체이고, `p`가 해당 객체를 참조한다.

---

## Q9. Java의 static field는 어떤 의미인가?

특정 객체 하나에 속하는 것이 아니라 해당 클래스에 하나 존재하는 필드다. 같은 클래스의 여러 인스턴스가 하나의 static field를 공유한다.

---

## Q10. OS와 JVM의 관계는?

OS는 JVM을 하나의 프로세스로 실행하고 CPU, 메모리 등의 자원을 제공한다. JVM은 그 위에서 Java Bytecode를 실행하고 Java Heap, JVM Stack 등의 런타임 메모리를 관리한다.

---

## Q11. JVM Heap과 OS Heap은 같은 것인가?

아니다.

JVM Heap은 JVM이 Java 객체를 위해 관리하는 런타임 메모리 영역이고, 이것은 OS가 JVM 프로세스에 제공한 가상 메모리 위에 구현된다.

---

## Q12. JDK와 JVM의 차이는?

JVM은 Java Bytecode를 실행하는 가상 머신이고, JDK는 JVM 구현체를 포함하여 컴파일러, 라이브러리, 개발 도구 등을 제공하는 Java 개발 키트다.

---

> **Context Switching이란 무엇이며, 왜 발생하고 어떤 비용이 드나요?**

왜냐하면 지금까지:

```text
Process
↓
Thread
↓
각자의 Register / Program Counter / Stack
↓
CPU는 한정됨
↓
여러 실행 흐름을 번갈아 실행해야 함
```

까지 이해했기 때문이다.

다음 단계에서는:

```text
Process State
↓
PCB
↓
Ready / Running / Waiting
↓
Scheduler
↓
Context Switching
```

을 연결하면 된다.
