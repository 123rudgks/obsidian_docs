
## 오버라이딩
변수의 scope
처음 변수가 속한 메소드의 내부 -> 해당 클래스의 멤버 변수 -> 조상 클래스의 멤버변수 순서로 확인한다.

super()는 자식 클래스 생성자의 맨 첫 줄에서만 호출이 가능하다.
즉, 생성자의 첫줄에만 this()나 super()가 올 수 있다.


## 제어자
접근제어자
public, protected, default(package), private
그 외 제어자
static, final, abstract ..

접근 제어자는 하나만 사용 가능, but 그 외 제어자는 여러개 조합 가능

final
final class : 더 이상 확장 할 수 없음 : 상속 금지 -> 오버라이드 금지
final method : 더 이상 재 정의 할 수 없음 : 오버라이드 금지
final variable : 더 이상 값을 바꿀 수 없음
	blank final : 값이 할당 되지 않은 final 멤버 변수. 생성자에서 1회 초기화 가능 (생성자에서 초기화 강제하기 위함)
	static final : 단지 final만 있으면 객체마다 각자의 final 변수가 있다. static final로 해야 모든 객체 공통의 변수로 사용 가능


접근 제어자

| 제한자               | 용도  |     |     | 접근 가능 범위 |        |                |     |
| ----------------- | --- | --- | --- | -------- | ------ | -------------- | --- |
|                   | 클래스 | 생성자 | 멤버  | 같은 클래스   | 같은 패키지 | 다른 패키지의 자손 클래스 | 전체  |
| public            | O   | O   | O   | O        | O      | O              | O   |
| protected         |     | O   | O   | O        | O      | O              | X   |
| default(=package) | O   | O   | O   | O        | O      | X              | X   |
| private           |     | O   | O   | O        | X      | X              | X   |
왜 private와 protected는 클래스에선 사용 못하는가?
private : 나만 접근 가능 -> 최상위 클래스가 private면 어느 곳에서도 사용을 할 수가 없어서 의미가 없어진다.
protected : 같은 패키지 + 다른 패키지의 자손 클래스에서 접근 가능해야하는데 최상위 클래스가 protected라면 다른 패키지의 자손 클래스가 생길 수가 없다.

클래스의 method는 부모의 제한자 범위와 같거나 넓은 범위로만 오버라이딩 가능하다. -> 부모가 외부에 한 약속(접근 범위)을 자식이 파기하면 부모 타입으로 자식을 다루는 외부 코드가 예측 불가능한 상황에 빠지기 때문. (자식은 부모가 할 수 있는건 다 할 수 있고 추가 확장 되는 것)
```java
class Parent{
	protected void method(){}
}

public class OverriedRule extends Parent{
	void method(){} // 에러, 부모의 메소드는 protected인데 자식이 default? 불가
	protected method(){}
	public void method(){}
}
```

부모 타입으로 형변환을 할 경우 자식 타입만의 고유한 **멤버들이 메모리에 있지만** 부모 타입에서 허용하는 범위만 접근 가능.

부모 객체를 자식 타입으로 형변환 할 수는 있지만 **명시적 형변환**을 해야하고 이는 무늬만 바꾸는 것임
```java
Person person = new Person();
SpiderMan sman = (SpiderMan) person;
sman.fireWeb(); // 메모리에는 fireWeb이 없음
```
따라서 instanceof 연산자로 실제 객체의 타입을 확인해야한다.
```java
Person person = new Person();
if(person instanceof SpiderMan){
	SpiderMan sman = (SpiderMan) person;
	sman.fireWeb();
}
```


정적 바인딩과 동적 바인딩
**바인딩**이란, 프로그램에서 사용된 이름(변수명, 메서드명)이 실제로 **어떤 메모리 주소(또는 어떤 코드)와 연결되는지를 결정하는 과정**

| |정적 바인딩 (Static Binding)|동적 바인딩 (Dynamic Binding)|
|---|---|---|
|다른 이름|초기 바인딩 (Early Binding)|후기 바인딩 (Late Binding)|
|결정 시점|**컴파일 타임**|**런타임**|
|결정 기준|참조 변수의 **선언된(compile-time) 타입**|참조 변수가 **실제로 가리키는 객체의 타입**|
|적용 대상|필드, `static` 메서드, `private` 메서드, `final` 메서드, 생성자, 오버로딩된 메서드|**오버라이딩된 인스턴스 메서드** (이것 하나뿐)|
|실행 속도|빠름 (미리 정해져 있으므로)|상대적으로 느림 (매번 실제 타입을 확인)|
|다형성과의 관계|다형성이 적용 **안 됨**|다형성(polymorphism)의 핵심 메커니즘|
> 정적 바인딩 대상인 메서드들의 특징은 **오버라이드**를 할 수 없다는 것
> 그럼 오버로딩 된 메소드는 오버라이드 가능한데 왜 정적 바인딩이야? -> 어떤 오버로드(시그니처)를 호출할지는 이미 코드상에서 결정 되어있음
> 반면 오버라이딩된 인스턴스 메서드는 다형성때문에 런타임이 되어야 실제 타입을 알 수 있음




## 추상 클래스
추상 클래스는 미구현된 메서드가 있으므로 객체 생성이 불가 but 상위 클래스 타입으로써 자식 참조 가능
```java
//Vehicle은 추상 클래스
Vehicle v = new DieselSUV(); 
```

자식은 abstract method를 재정의할 책임이 있음. 만약 자식 클래스에서도 abstract 메소드 재정의하지 않았다면 이 자식 클래스 또한 abstract class가 되어야함

추상클래스는 활용 방안
- interface에 있는 메서드 중 구현할 수 있는 메서드를 구현해 개발 편의 지원

## 인터페이스
클래스와 다르게 다중상속 가능
인터페이스를 implements 한 클래스는 모든 abstract 메서드를 override하여 구현하거나 이 또한 abstract 클래스가 되어버려야함

다형성은 조상 클래스 뿐 아니라 조상 인터페이스에도 적용 가능
```java
IronMan iman = new IronMan();
// Heroable은 인터페이스
Heroable hero = iman;
```

인터페이스 활용
- 서로 상속 관계가 없는 클래스들에게 인터페이스를 통한 관계 부여로 다형성 확장
```java
// charge가 두 클래스 모두에게 중복으로 있음
void badCase(){
	Object[] objs = { new HandPhone(), new ElectricShaver()};
	for(Object obj: objs){
		if(obj instanceof HandPhone phone){
			phone.charge();
		}else if (obj instanceof ElectricShaver shaver){
			shaver.charge();
		}
	}
}

// interface Chargable 생성으로 다형성 확장
void goodCase(){
	Chargeable[] objs = { new HandPhone(), new ElectricShaver()};
	for(Chargeable obj: objs){
		obj.charge();
	}
}
```

default method
- 인터페이스에 선언 된 구현부가 있는 일반 메서드
```java
interface DefaultMethodInterface{
	void abstractMethod();
	
	default void defaultMethod(){
		System.out.println("이것은 기본 메서드입니다.");
	}
}
```

왜 필요해?
- 기존 interface 기반으로 동작하는 라이브러리의 interface에 기능 추가해야함
- abstract 메소드로 추가하면 이를 사용하는 모든 클래스의 메소드를 override해야함
- default 메서드로 추가하여 반드시 구현하지 않아도 되도록 함.

private method
- interface에 abstract method만 있었을 땐 괜찮았는데 body를 가지는 메서드가 등장하면서 공통적으로 처리할 모듈이 발생 (default method 또는 static method)
- 이런 모듈에서 공통으로 사용할 수 있도록 private method 추가
```java
interface MyMath{
	static void add(int a, int b){
		int result = a + b;
		print(a,b,result); // print 재사용
	}
	default void multi(int a, int b){
		print(a,b,a*b); // print 재사용
	}
	
	private static void print(int a, int b){
		System.out.println("...");
	}
}
```
> 구현부를 가지지만 default 키워드 사용 안함. 원한다면 static 처리 가능
