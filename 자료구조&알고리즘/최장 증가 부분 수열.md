**LIS(Longest Increasing Subsequence, 최장 증가 부분 수열)** 는 주어진 수열에서 일부 원소를 선택하여 만든 증가 부분 수열 중 가장 긴 길이를 구하는 문제이다.
부분 수열(Subsequence)은 원본 수열에서 일부 원소를 제외할 수 있지만, **원소의 상대적인 순서는 유지해야 한다.**

## 1. Brute Force
가장 단순한 방법은 가능한 모든 부분 수열을 만들어 그중 증가 수열인 것을 찾는 것이다.
각 원소마다
```text
선택한다 / 선택하지 않는다
```

두 가지 경우가 있으므로 원소가 `N`개라면 부분 수열의 개수는
```text
2^N
```
개이다.

모든 부분 수열을 확인하면 정답을 구할 수 있지만, `N`이 커질수록 경우의 수가 기하급수적으로 증가하므로 비효율적이다.

**시간복잡도: O(2^N) 이상**

---

## 2. DP

Brute Force처럼 모든 부분 수열을 직접 만들지 않고, 앞에서 구한 결과를 재사용할 수 있다.

`LIS[i]`를 다음과 같이 정의한다.
> `i`번째 원소를 마지막 원소로 가지는 증가 부분 수열의 최대 길이

현재 원소 `arr[i]`보다 앞에 있으면서 값이 작은 원소 `arr[j]`를 찾는다.
```text
j < i
arr[j] < arr[i]
```

그러면 `j`에서 끝나는 증가 부분 수열 뒤에 `arr[i]`를 붙일 수 있다.

따라서
```text
LIS[i]
= 앞의 원소 중 arr[i]보다 작은 원소들의 LIS 최대값 + 1
```
이 된다.

예를 들어

```text
3, 2, 6, 4, 5, 1
```
의 결과는
```text
값       3  2  6  4  5  1
LIS      1  1  2  2  3  1
```
이고 최댓값인 `3`이 정답이다.

하지만 각 원소마다 자신의 앞에 있는 모든 원소를 다시 확인해야 한다.

**시간복잡도: O(N²)**

---

## 3. [[이진 탐색]]을 활용한 LIS

DP 방식보다 효율적으로 해결하기 위해 별도의 배열을 관리한다.

이 배열의 각 위치에는 다음 정보를 저장한다.
> 길이가 `k`인 증가 부분 수열을 만들 수 있을 때 가능한 마지막 값의 최솟값
같은 길이의 증가 부분 수열이라면 **마지막 값이 작을수록 이후 더 많은 숫자를 연결할 가능성이 높다.**

예를 들어
```text
2, 4, 8
2, 4, 5
```
는 둘 다 길이가 `3`이지만 `5`로 끝나는 경우가 이후 원소를 연결하기에 더 유리하다.

따라서 새로운 숫자를 하나씩 확인하면서 다음과 같이 처리한다.
```text
현재 값이 저장된 모든 값보다 크다
→ 배열의 맨 뒤에 추가
→ LIS 길이 증가

그렇지 않다
→ 현재 값 이상인 첫 번째 위치를 찾음
→ 해당 값을 현재 값으로 교체
→ LIS 길이는 그대로
```

현재 값 이상인 첫 번째 위치는 배열이 정렬되어 있기 때문에 **이진 탐색(Lower Bound)**으로 찾을 수 있다.

각 원소마다 이진 탐색을 한 번 수행하므로
```text
N개의 원소 × O(log N)
```
이 되어,

**시간복잡도: O(N log N)**
이다.

따라서 세 방법을 비교하면
```text
Brute Force       O(2^N)
DP                O(N²)
이진 탐색 활용     O(N log N)
```

으로 이진 탐색을 활용한 방법이 가장 효율적이다.

단, 이 방법에서 관리하는 배열은 **실제 LIS 자체를 저장하는 배열이 아니라 LIS 길이를 계산하기 위한 상태 배열**이다.

---

## Java 구현 (이진 탐색 방식)

```java
import java.io.*;
import java.util.*;

public class Main {

    public static void main(String[] args) throws Exception {

        BufferedReader br =
                new BufferedReader(new InputStreamReader(System.in));

        int N = Integer.parseInt(br.readLine());

        int[] arr = new int[N];

        StringTokenizer st =
                new StringTokenizer(br.readLine());

        for (int i = 0; i < N; i++) {
            arr[i] = Integer.parseInt(st.nextToken());
        }

        int[] tails = new int[N];
        int length = 0;

        for (int x : arr) {

            int left = 0;
            int right = length;

            // x 이상인 값이 처음 등장하는 위치 탐색
            while (left < right) {

                int mid = (left + right) / 2;

                if (tails[mid] < x) {
                    left = mid + 1;
                } else {
                    right = mid;
                }
            }

            tails[left] = x;

            // 기존 모든 값보다 큰 경우
            if (left == length) {
                length++;
            }
        }

        System.out.println(length);
    }
}
```

> [!question]+ 왜 right는 length -1이 아닌 length로 두는 걸까?
> 현재 값 `x`가 `tails`의 모든 값보다 큰 경우, `x`를 `tails`의 `length`인덱스에 에 추가 해야하기 때문
> 비슷한 이유로 right를 `mid - 1`이 아닌 `mid`로 갱신하는 이유도 `mid` 가 `lower_bound`일 수 있기 때문
## 핵심 

LIS 문제는 모든 증가 부분 수열을 직접 만드는 대신,

```text
각 길이의 증가 부분 수열이 가질 수 있는
가장 작은 마지막 값
```
만 관리하면 된다.

이 값을 작게 유지할수록 이후 원소를 연결하기 유리하며, 교체할 위치를 이진 탐색으로 찾음으로써 전체 시간복잡도를 `O(N log N)`까지 줄일 수 있다.
