## Ⅰ. 객관식 해설

### 1번 — 정답 ③
형변환과 연산 시점이 핵심이다.
- `l1 = i1 + 1` : **int끼리의 연산**이 먼저 일어나 overflow 발생 → 그 결과(-2147483648)가 long으로 넓혀짐 → -2147483648
- `l2 = (long)(i1 + 1)` : 괄호 안에서 이미 int 연산으로 overflow → 캐스팅해도 늦음 → -2147483648
- `l3 = (long) i1 + 1` : **i1이 먼저 long으로 캐스팅**되고 long + int 연산 → overflow 없음 → **2147483648** ✔
- `i2` : 당연히 overflow → -2147483648

### 2번 — 정답 ②
연산은 왼쪽에서 오른쪽으로 진행된다.
- `i3` : `1000000 * 1000000`에서 이미 int 범위 초과 → overflow된 값에 `/1000000` → **-727**
- `i4` : `1000000 / 1000000` = 1 → `1 * 1000000` = **1000000** (overflow 없음)

같은 수식이라도 연산 순서에 따라 overflow 여부가 달라진다.

### 3번 — 정답 ①
Switch Expressions 문법 :
- 여러 case는 **쉼표**로 나열 : `case 4,6,9,11 ->`
- 화살표(`->`) 뒤에 값 하나면 그대로 반환
- 블록이 필요하면 `yield` 키워드로 값 반환 (return 아님 → ③ 틀림)
- 값을 반환하는 switch expression은 모든 경우를 커버해야 하므로 default 생략 불가 (⑤ 틀림)
```java
int day = switch (month) {
    case 2 -> 29;
    case 4,6,9,11 -> 30;
    default -> {
        yield 31; // 블록을 쓸 경우 yield 필요
    }
};
```

### 4번 — 정답 ③
`{...}` 중괄호 초기화 리터럴은 **선언과 동시**이거나 `new int[]{...}` 형태로만 쓸 수 있다. 이미 선언된 변수에 `scores = {90, 80, 100, 95};`로 재대입하면 컴파일 에러.
①은 컴파일은 되지만 **런타임에 ArrayIndexOutOfBoundsException** — "컴파일 에러"를 묻는 문제이므로 답이 아니다. 이 구분(컴파일 에러 vs 런타임 에러)을 놓치지 말 것.

### 5번 — 정답 ③
`this`는 현재 객체의 주소를 참조한다. static 멤버는 객체가 생성되기 **전**에 이미 Method Area에 로딩되어 있으므로, 참조할 객체가 존재하지 않는 시점에도 호출될 수 있다. 따라서 static 영역에서는 this를 쓸 수 없다.

### 6번 — 정답 ②
클래스 구성 요소의 로딩/초기화 순서 :
- **Static 요소** : static 변수 로딩(기본 초기화) → static 메소드 로딩 → static initializer 실행 → main 실행
- **Instance 요소** : 멤버 변수 로딩(기본 초기화) → Instance Initializer 실행 → **생성자 실행**

생성자가 가장 마지막이라는 점이 포인트.

### 7번 — 정답 ③
- **조상 타입 변수로 자식 객체 참조는 항상 안전**(업캐스팅). 부모가 가진 멤버가 더 적기 때문에 부모 타입으로 다뤄도 없는 멤버를 호출할 일이 없다.
- 반대로 자식 타입으로 부모 객체를 참조하면(다운캐스팅) 객체에 없는 멤버를 사용할 수 있게 되므로 위험하다 → ②, ④ 틀림.

### 8번 — 정답 ③
`<? extends Person>`은 **Person 또는 Person을 상속받은 타입**만 허용한다.
- boxPerson ✔ (Person 자신)
- boxSpiderMan ✔ (Person의 자식)
- boxObject ✘ (Person의 조상)

참고로 `<? super Person>`이었다면 boxPerson과 boxObject가 허용된다. `<?>`는 셋 다 허용.

### 9번 — 정답 ④
`GenericBox<?>`는 어떤 타입이 들어있는지 알 수 없으므로, 컴파일러는 타입 안정성을 지키기 위해 **setter로는 null만** 허용한다. 어떤 타입이든 들어올 수 있으니 멤버 변수를 바꾸는 setter를 아예 막아버리는 것이다. (반대로 꺼내는 것(getter)은 Object로 받으면 항상 안전하다.)

### 10번 — 정답 ⑤
enum 상수는 프로그램 전체에서 딱 하나만 존재하는 **싱글턴 객체**로, 클래스 로딩 시 컴파일러가 내부적으로 생성한다. 개발자가 직접 `new`로 만들 수 없다. ①~④는 모두 enum의 기본 메소드에 대한 올바른 설명이다.

### 11번 — 정답 ②
enum의 `compareTo()`는 **두 상수의 ordinal 차이**를 반환한다.
- SALES(0).compareTo(PART_TIME_JOB(1)) = 0 - 1 = **-1**
- NORMAL(2).compareTo(SALES(0)) = 2 - 0 = **2**

### 12번 — 정답 ②
- `set(1, "X")` : 인덱스 1의 값을 **교체** → `[A, X, C]`
- `add(1, "Y")` : 인덱스 1에 **삽입**, 기존 요소는 뒤로 밀림 → `[A, Y, X, C]`

set(교체)과 add(삽입)의 차이를 구분하자.

### 13번 — 정답 ③
원래 코드는 매번 5000번 위치까지 순회(O(n)) 후 삽입하므로 (n+1) × 1000의 비용이 든다.
```java
ListIterator<Integer> iter = list.listIterator(5000); // 이동은 딱 한 번
for (int i = 0; i < 1000; i++) {
    iter.add(i); // 이미 그 자리에 있으므로 O(1) 삽입
}
```
LinkedList가 진짜 빛나는 순간은 이렇게 **찾아가는 비용이 없어지는 경우**뿐이다.

### 14번 — 정답 ③
`Arrays.asList()`는 **고정 크기** 리스트를 만든다.
- add/remove → UnsupportedOperationException (①, ②, ④ 틀림)
- **set으로 요소 값 수정은 가능** (null 대입도 가능) ✔
- 배열을 원본으로 만들면 리스트 수정이 원본 배열에 반영된다 (⑤ 틀림)

### 15번 — 정답 ③
- `put("andy", "4567")` : 동일 key → 값을 **덮어씀** → 4567
- `putIfAbsent("kate", "9999")` : kate가 없으므로 추가 → 9999
- `putIfAbsent("kate", "0000")` : kate가 이미 있으므로 **무시**

### 16번 — 정답 ⑤
for-each 순회 중 컬렉션의 크기를 변경하면 ConcurrentModificationException이 발생한다. ①~④는 모두 안전한 방법이다. (④의 정순 + `i--`는 제거 후 당겨진 요소를 다시 검사하게 만들어 건너뛰기 문제를 해결한다.)

### 17번 — 정답 ⑤
`p1.number - p2.number` : number는 **String**이므로 뺄셈 연산이 불가능 → 컴파일 에러. 문자열 비교는 `compareTo()`를 써야 한다. int 필드였다면 가능한 관용구다(그마저도 overflow 위험이 있어 `Integer.compare()`가 권장된다).
①~④는 Comparator를 만드는 네 가지 올바른 방법이다 : 구현 클래스, 람다, `Comparator.comparing`, 익명 클래스.

### 18번 — 정답 ②
`flatMap`은 중첩 구조를 **평탄화**한다. 각 내부 List를 스트림으로 바꾼 뒤 하나의 스트림으로 이어붙인다 → `[1, 2, 3, 4]`. `map(List::stream)`이었다면 `Stream<Stream<Integer>>`가 되어 버린다.

### 19번 — 정답 ③
`reduce(identity, accumulator)`는 초기값 10에서 시작해 요소를 누적한다.
10 + 1 + 2 + 3 + 4 = **20**
참고로 초기값 없는 `reduce(Integer::sum)`은 스트림이 비어있을 수 있으므로 `Optional<Integer>`를 반환한다.

### 20번 — 정답 ①
- `allMatch(n -> n % 2 == 0)` : 2, 4, 6 모두 짝수 → **true**
- `anyMatch(n -> n > 5)` : 6이 만족 → **true**
- `noneMatch(n -> n < 0)` : 음수가 하나도 없음 → **true**

### 21번 — 정답 ②
num = 0 → `1/0`에서 ArithmeticException → code 2 건너뛰고 catch의 code 3 → **finally는 예외 발생 여부와 무관하게 언제나 실행** → code 4 → 정상 흐름 복귀 후 code 5.
num = 1이었다면 : code 1 → code 2 → code 4 → code 5.

> finally의 대표 활용 : try와 catch 양쪽에 중복 작성되던 정리 코드(`app.delete()` 같은)를 finally 한 곳으로 모으는 것.

## Ⅱ. 단답형 해설

### 22번 — 정답 : 변수 초기화, 반복 조건, 실행문, 증감식
어떤 형태의 반복문이든 이 4가지 요소로 구성된다.

### 23번 — 정답 : Method Area
Method Area에는 타입 정보, Field/Method 정보, static 변수, 상수 풀이 저장된다. 스레드가 공유하는 영역이다.

### 24번 — 정답 : `<? super T>`
- `<? extends T>` : T 또는 T를 상속받은 타입 (하위)
- `<? super T>` : T 또는 T의 조상 타입 (상위)
- PECS : **P**roducer **E**xtends, **C**onsumer **S**uper

### 25번 — 정답 : `listIterator(int index)`
```java
ListIterator<Integer> iter = list.listIterator(5000);
```
해당 위치까지 한 번만 이동한 후 그 자리에서 add/remove/set을 O(1)로 수행할 수 있다.

### 26번 — 정답 : `entrySet()`, `keySet()`
```java
for (Map.Entry<String, Integer> e : map.entrySet()) {
    System.out.println(e.getKey() + " = " + e.getValue());
}
Set<String> keys = map.keySet();
```
value 전체는 `values()`로 얻는다 (반환 타입은 Collection).

### 27번 — 정답 : `Integer.compare(int a, int b)`
Integer는 기본형 int를 더 잘 쓰기 위해 존재하므로, 두 int를 비교할 때 불필요한 박싱 없이 쓸 수 있는 static compare()가 있다. String은 원래 기본형이 없고 항상 객체이므로 `compareTo()`만 있으면 충분하다.

### 28번 — 정답 : `findFirst()`
```java
Optional<Integer> first = nums.stream().filter(n -> n > 2).findFirst();
```
결과가 없을 수 있으므로 Optional로 반환한다.

### 29번 — 정답 : `peek()`
```java
nums.stream()
    .peek(n -> System.out.println("filter 전: " + n))
    .filter(n -> n > 2)
    .peek(n -> System.out.println("filter 후: " + n))
    .toList();
```
요소를 변형/소비하지 않고 그대로 흘려보내면서 확인만 한다.

### 30번 — 정답 : (1) `getMessage()` (2) `getCause()`
- `getMessage()` : 예외 메시지 문자열만 필요할 때 (사용자 안내 등)
- `getCause()` : 예외를 감싸서 다시 던진 경우(예외 번역) 원인 예외를 추적할 때
- `printStackTrace()` : 호출 스택 전체를 출력 — 개발/디버깅 단계에서 사용

## Ⅲ. 서술형 모범 답안

### 31번
**1. 컴파일러의 강제 여부**
- **checked exception** : `Exception`(및 그 하위 중 RuntimeException 계열 제외)을 기준으로 하며, 컴파일러가 "**처리(try-catch)하거나 선언(throws)하라**"고 강제한다. 하지 않으면 컴파일 에러.
- **unchecked exception** : `RuntimeException` 계열. 컴파일러가 처리를 강제하지 않는다. try-catch 없이도 컴파일되며, 처리하지 않으면 런타임에 전파되다가 프로그램이 종료된다.

**2. throws를 통한 처리 위임**
메소드에서 발생할 수 있는 예외를 직접 처리하지 않고 **호출한 곳으로 전달**하는 방법이다.
```java
void exceptionMethod() throws Exception1, Exception2 {
    // 예외 발생 코드 — 여기서는 try-catch 안 해도 됨
}

void methodCaller() {
    try {
        exceptionMethod(); // 호출한 쪽에서 처리해야 함
    } catch (Exception e) { ... }
    // 또는 methodCaller도 다시 throws로 위임 가능
}
```
checked exception은 이렇게 위임 사슬의 어딘가에서 반드시 처리되어야 한다. unchecked exception은 throws 선언 없이도 자동으로 전파된다.

**3. 재정의 시 제약**
메서드를 재정의할 때 **조상 클래스의 메서드가 던지는 예외보다 더 큰(상위) 예외를 던질 수 없다.** 조상 타입으로 다형적으로 호출하는 코드가 예상한 catch 범위를 벗어나면 안 되기 때문이다.

### 32번
**(A) 배열 — 공변**
`Object[] arr = new Person[3];`은 배열의 공변성 덕분에 **컴파일이 통과**한다. 그러나 `arr[0] = 1;`은 실제 배열이 Person[]이므로 **런타임에 ArrayStoreException**이 발생한다. 배열은 런타임에도 자기 요소 타입 정보를 간직하고 있어 실행 중에야 걸러낸다.

**(B) 제네릭 — 무공변**
`List<Object> list = new ArrayList<Person>();`은 **컴파일 단계에서 바로 에러**가 난다. 원소 타입이 상속 관계(Person → Object)라도, 이를 담는 제네릭 타입(List) 사이에는 어떤 상속 관계도 인정하지 않기 때문이다(무공변).

**타입 안정성 근거**
같은 종류의 잘못된 코드가 배열에서는 런타임 예외로, 제네릭에서는 컴파일 에러로 나타난다. 컴파일 에러는 개발자가 코드를 작성하는 시점에 즉시 발견해 고칠 수 있지만, 런타임 에러는 사용자가 실제로 실행할 때 발견되므로 비용이 훨씬 비싸다. 잘못된 타입 대입을 더 이른 단계(컴파일 타임)에서 차단한다는 점이 제네릭이 배열보다 타입 안정성이 좋다는 근거다.

> 보충 : 제네릭은 컴파일 후 타입 정보가 소거(erasure)되므로 런타임 체크는 불가능하다. 그래서 제네릭의 전략은 "런타임에 걸러내기"가 아니라 "**애초에 컴파일에서 못 들어오게 막기**"이며, 이 때문에 무공변이어야만 안전하다.
