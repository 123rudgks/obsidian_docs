## Ⅰ. 객관식 해설

### 1번 — 정답 ②
`int`의 최댓값(2147483647)에 1을 더하면 **overflow**가 발생하여 최솟값 -2147483648로 돌아간다. 정수 계산 시에는 저장할 값의 크기를 고려해 int/long 등 타입을 선택해야 한다. overflow는 예외가 아니라 **조용히 잘못된 값**을 만든다는 점이 핵심이다.

### 2번 — 정답 ②
문자형은 내부적으로 ASCII/Unicode에 매핑된 숫자다.
- `'0'`은 문자 0이며 ASCII 값은 **48** → `c == 0`은 false, `c == 48`은 true
- `'A'`는 65, `'a'`는 97이므로 `65 + 32 == 97` → true

> 암기 포인트 : `'0'` = 48, `'A'` = 65, `'a'` = 97

### 3번 — 정답 ④
- ① `b1 + b2`는 int끼리의 연산(byte는 연산 시 int로 승격) → int를 byte에 대입 불가 (lossy conversion)
- ② `i1 + lv`는 long 결과 → int에 대입 불가
- ③ `10.0`은 double 리터럴 → float에 대입 불가 (`10.0f`로 써야 함)
- ④ `i1 + 1`은 int 결과이고, int → long은 **넓히는 변환**이므로 자동으로 허용 ✔
- ⑤ `10.0f + 20.0`은 float + double = double 결과 → float에 대입 불가

### 4번 — 정답 ②
`break`가 없으면 일치한 case부터 **아래로 계속 실행(fall-through)**된다. `case 3`에서 시작해 3, 4를 출력하고 `case 5`의 break에서 멈춘다. default까지 가지 않는다.

### 5번 — 정답 ②
`new int[][3]`처럼 **앞쪽 차원을 비우고 뒤쪽 차원만 지정하는 것은 불가능**하다. 반대로 ③처럼 `new int[4][]`는 가능하다(행만 만들고 각 행의 배열은 나중에 생성). ④, ⑤처럼 중괄호 초기화도 모두 유효하다.

### 6번 — 정답 ③
static 변수는 Heap이 아니라 **Method Area**에 저장된다. Method Area에는 타입 정보, Field/Method 정보, static 변수, 상수 풀이 들어간다. 객체는 Heap, 지역 변수와 메서드 실행 공간(프레임)은 Stack이다. Stack은 스레드별 별도 관리, Heap과 Method Area는 스레드가 공유한다.

### 7번 — 정답 ③
- **필드는 참조 변수의 타입**을 따른다 → `animal.type`은 Animal의 "동물"
- **메서드는 실제 객체의 타입**을 따른다(동적 바인딩) → `animal.sound()`는 Dog의 "멍멍!"
- `getType()`도 오버라이딩된 메서드이므로 Dog의 것이 실행되고, 그 안의 `type`은 Dog 자신의 필드 → "개"

필드 숨김(hiding)과 메서드 오버라이딩의 동작 차이를 묻는 단골 문제다.

### 8번 — 정답 ⑤
오버라이딩 조건 5가지 :
1. 메서드 이름이 같아야 한다
2. 매개변수의 개수, 타입, 순서가 같아야 한다
3. 리턴 타입이 같아야 한다
4. 접근 제한자는 부모보다 범위가 **넓거나 같아야** 한다
5. 부모(조상)보다 **더 큰 예외를 던질 수 없다** → ⑤는 반대로 서술했으므로 틀림

### 9번 — 정답 ④
제네릭은 **컴파일 시점에만 타입을 체크하고 런타임에는 타입 정보가 소거**된다(type erasure).
- ① 런타임에 동작하는 `new`는 T를 알 수 없어 불가
- ② 런타임에 타입 인자 정보가 없으므로 `instanceof GenericBox<String>` 불가
- ③ 제네릭 타입의 배열 생성 불가 (배열의 공변성 때문) → `List<GenericBox<T>>` 권장
- ④ 와일드카드 `<?>`는 타입 인자를 묻지 않으므로 **컴파일 가능** ✔
- ⑤ T는 인스턴스를 만들 때 결정되는데 static은 모든 객체가 공유하므로 T 사용 불가

### 10번 — 정답 ⑤
상속 계층 : `Iterable ← Collection ← List, Set`. **Map은 Collection과 별개의 계층**이다 (key-value 쌍 구조라서 단일 요소 컬렉션과 인터페이스가 다름).

### 11번 — 정답 ⑤
요소를 삭제해도 내부 배열의 capacity는 자동으로 줄어들지 않는다. ③의 확장 로직은 실제 소스에서 `oldCapacity >> 1`(기존의 절반)을 더해 약 1.5배로 만든다.

### 12번 — 정답 ②
원소를 제거하면 뒤의 원소들이 한 칸씩 **앞으로 당겨지는데** i는 그대로 1 증가하므로, 제거 직후의 다음 원소를 건너뛴다.
```
[1, 2, 2, 3, 4]
i=0 : 1 (홀수, 통과)
i=1 : 2 (짝수, 제거) → [1, 2, 3, 4]   ← 당겨진 두 번째 2는 검사 안 됨!
i=2 : 3 (홀수, 통과)
i=3 : 4 (짝수, 제거) → [1, 2, 3]
```
해결법 : `remove` 후 `i--` 하거나, **역순으로 순회**하거나, `removeIf()` 사용.

### 13번 — 정답 ④
for-each 순회 중 컬렉션의 크기를 변경하면 **ConcurrentModificationException**이 발생한다. 내부적으로 Iterator가 기대하는 수정 횟수(expectedModCount)와 실제 modCount가 어긋나기 때문이다.
안전한 방법 :
```java
// 방법 1 : Iterator의 remove() 사용 (expectedModCount도 함께 갱신)
Iterator<Integer> it = nums.iterator();
while (it.hasNext()) {
    if (it.next() % 2 == 0) it.remove();
}
// 방법 2 : removeIf()
nums.removeIf(num -> num % 2 == 0);
```

### 14번 — 정답 ②
Set은 내부적으로 `hashCode()`와 `equals()`로 중복을 판단한다. String과 Integer는 둘 다 값 기준으로 재정의되어 있으므로 `"Hello"`와 `new String("Hello")`는 같은 원소, `1`과 `Integer.valueOf(1)`도 같은 원소다. 결과는 `[1, Hello]` → size 2.

### 15번 — 정답 ①
`put()`은 **이전 값을 반환**한다 (처음 넣을 때는 null).
- 첫 put → 이전 값 없음 → `null`
- 두 번째 put → 이전 값 `1234` 반환, 값은 `4567`로 덮어씀
- `putIfAbsent`는 **key가 없을 때만** 추가 → andy가 이미 있으므로 무시
- 최종 `get("andy")` → `4567`

### 16번 — 정답 ③
`List.of()`는 **불변(Unmodifiable) 컬렉션**을 만든다. 추가/삭제/수정 시도 시 `UnsupportedOperationException`이 발생한다(런타임 예외, 컴파일은 통과). 참고로 `List.of()`, `Set.of()`, `Map.of()` 모두 null을 허용하지 않는다.

### 17번 — 정답 ④
`Collections.sort(List<T>)`의 시그니처는
```java
public static <T extends Comparable<? super T>> void sort(List<T> list)
```
T가 Comparable을 구현해야 한다는 **제네릭 한정(bounded type)** 조건이 있으므로, Comparable을 구현하지 않은 SmartPhone은 **컴파일 단계에서** 에러가 난다. 런타임 에러가 아니라는 점에 주의.
해결법 : `implements Comparable<SmartPhone>` + `compareTo` 구현, 또는 `Collections.sort(phones, comparator)` 사용.

### 18번 — 정답 ①
`s1.length() - s2.length()`는 음수면 s1이 앞 → **길이 오름차순** 정렬.
Java(4), Hi(2), World(5) → `[Hi, Java, World]`

### 19번 — 정답 ③
파이프라인 추적 :
- `mapToInt(String::length)` → 8, 6, 7, 4
- `filter(len -> len > 4)` → 8, 6, 7
- `average()` → (8+6+7) / 3 = **7.0**

### 20번 — 정답 ②
- `filter(n -> n > 2)` → 5, 3, 8, 9
- `sorted()` → 3, 5, 8, 9
- `limit(3)` → **[3, 5, 8]**

중간 연산의 **순서**가 결과를 바꾼다. limit이 sorted보다 먼저 왔다면 결과가 달라졌을 것.

### 21번 — 정답 ②
num이 0이면 `1 / 0`에서 ArithmeticException 발생 → code 2는 건너뛰고 catch 블록의 code 3 실행 → try-catch를 빠져나와 code 4 실행. **catch에서 예외를 처리하면 프로그램은 정상 흐름으로 계속된다.**

## Ⅱ. 단답형 해설

### 22번 — 정답 : 65
`'0'` = 48, `'A'` = 65, `'a'` = 97은 암기해 두자. 대소문자 차이는 32.

### 23번 — 정답 : 추상화(Abstraction), 다형성(Polymorphism), 상속(Inheritance), 캡슐화(Encapsulation)
OOP is **A P.I.E** — 캡슐화는 데이터 은닉과 보호를 의미한다.

### 24번 — 정답 : `System.arraycopy()`, `Arrays.copyOf()`
```java
System.arraycopy(src, 0, dest, 0, 5); // 원본, 시작위치, 대상, 시작위치, 복사길이
int[] copy = Arrays.copyOf(src, 5);   // 원본, 복사할 길이
```
`Arrays.copyOf`의 길이가 원본보다 크면 나머지는 0으로 채워진다. 특정 범위만 복사하려면 `Arrays.copyOfRange(원본, start, end)`.

### 25번 — 정답 : `hashCode()`
> If two objects are equal according to the equals(Object) method, then calling the hashCode method on each of the two objects must produce the same integer result.

equals만 재정의하면 HashSet/HashMap 같은 해시 기반 컬렉션에서 논리적으로 같은 객체가 다른 버킷에 들어가 중복 판정이 깨진다.

### 26번 — 정답 : `Object[]`
`Object[] elementData`를 private으로 감추고, add는 제네릭 타입 E만 받도록 하여 타입 안정성을 유지한다. get에서만 `(E)` 캐스팅을 하는데 add로만 값이 들어오므로 논리적으로 항상 안전하다.

### 27번 — 정답 : HashMap
key에 원소를 넣어 중복을 방지하고, value에는 더미 값을 사용한다.

### 28번 — 정답 : Comparable 인터페이스, `compareTo()` 메소드
```java
class SmartPhone implements Comparable<SmartPhone> {
    @Override
    public int compareTo(SmartPhone other) {
        return this.number.compareTo(other.number);
    }
}
```
이미 사용 가능한 기준(String, Integer의 compareTo)이 있다면 직접 만들지 말고 활용하는 것이 좋다.

### 29번 — 정답 : `distinct()`
중간 연산으로, 내부적으로 equals/hashCode 기준으로 중복을 제거한다.

### 30번 — 정답 : ConcurrentModificationException
해결법은 13번 해설 참조 (Iterator.remove() 또는 removeIf()).

## Ⅲ. 서술형 모범 답안

### 31번
**내부 구조 차이**
- ArrayList : 내부적으로 `Object[]` 배열에 연속적으로 저장. 인덱스 계산만으로 임의 위치에 바로 접근 가능(O(1)). 크기 변경 시 새 배열 생성 후 복사가 필요하고, 중간 삽입/삭제 시 뒤 요소들을 밀거나 당겨야 한다.
- LinkedList : 각 노드가 이전/다음 노드의 참조를 가진 연결 구조. 삽입/삭제 자체는 포인터 교체 O(1)이지만, 해당 위치까지 **이동하는 비용이 O(n)**이라 결과적으로 임의 위치 삽입/삭제도 O(n)이다.

**상황별 판단**
1. **맨 앞에 데이터 추가 → LinkedList 승.** LinkedList는 head 포인터만 교체하면 되지만, ArrayList는 기존 요소 전체를 한 칸씩 뒤로 밀어야 한다.
2. **중간 요소 조회 → ArrayList 승.** ArrayList는 인덱스로 즉시 접근하지만 LinkedList는 노드를 하나씩 순회해야 한다.
3. **반복자를 이용한 중간 100개 연속 추가 → LinkedList 승.** `listIterator(위치)`로 딱 한 번만 이동한 후에는 그 자리에서 O(1) 삽입을 반복할 수 있다. ArrayList는 삽입할 때마다 뒤 요소들의 이동(벌크 복사)이 불가피하다.
```java
ListIterator<Integer> iter = list.listIterator(5000); // 이동은 한 번만
for (int i = 0; i < 1000; i++) {
    iter.add(i); // 순회 없이 바로 삽입 O(1)
}
```
> 참고 : 그 외 대부분의 상황(단순 조회, 정적 데이터)에서는 ArrayList가 성능/메모리 측면에서 유리하다. System.arraycopy가 잘 최적화되어 있어 실전에서는 벌크 복사가 포인터 순회보다 빠른 경우가 많다.

### 32번
**HashSet의 중복 판단 과정**
1. 추가하려는 객체의 `hashCode()`를 호출해 해시 값을 얻고, 이를 압축(`hashCode % 배열 크기` 개념)하여 저장할 버킷 위치를 찾는다 — O(1).
2. 해당 버킷에 이미 원소가 있으면(해시 충돌 포함) 그 원소들과 `equals()`로 비교한다.
3. **hashCode가 같고 equals도 true**일 때만 같은 원소로 판단하여 추가하지 않는다.

**중복 처리가 안 되는 이유**
SmartPhone은 Object의 hashCode/equals를 그대로 사용한다. 기본 구현은 hashCode는 객체마다 다른 식별 값을, equals는 **같은 주소인지(동일성)**를 비교하므로, 번호가 같아도 `new`로 만든 두 객체는 서로 다른 원소로 취급된다.

**해결 — 비즈니스 기준(번호)으로 두 메소드 재정의**
```java
class SmartPhone {
    String number;
    public SmartPhone(String number) { this.number = number; }

    @Override
    public int hashCode() {
        return number.hashCode(); // 이미 잘 재정의된 String의 hashCode 활용
    }

    @Override
    public boolean equals(Object obj) {
        if (obj != null && obj instanceof SmartPhone param) {
            return this.number.equals(param.number);
        }
        return false;
    }
}
```
재정의 후에는 `set.size()`가 1이 된다. equals를 재정의하면 hashCode도 반드시 함께 재정의해야 한다는 규약도 언급하면 만점.
