# 보충 모의고사 - 해설

> 문제 : [[보충 모의고사 - 문제]]
> 코드 작성 문제는 아래 답안을 보기 전에 반드시 직접 작성하고 실행해 볼 것. 답안과 다르더라도 동작하면 정답이다.

---

## 1부. List / Set / Map 주요 메소드

### 1. Collection 핵심 메소드 종합 작성 — 모범 답안
```java
import java.util.*;

public class CollectionMethodsDrill {
    public static void main(String[] args) {
        Collection<String> c1 = new ArrayList<>();
        Collection<String> c2 = new ArrayList<>();

        c1.add("A");                              // 요소 하나 추가
        c1.addAll(List.of("B", "C"));             // 여러 요소 한번에 추가
        System.out.println("add/addAll 후: " + c1);           // [A, B, C]

        System.out.println(c1.contains("B"));                  // true
        System.out.println(c1.containsAll(List.of("B", "C"))); // true

        c2.addAll(List.of("A", "B", "C"));
        System.out.println(c1.equals(c2));                     // true (내용 비교)

        System.out.println(c1.isEmpty() + ", " + c1.size());  // false, 3

        Iterator<String> it = c1.iterator();
        while (it.hasNext()) System.out.print(it.next() + " "); // A B C
        System.out.println();

		// new String[0]은 단지 타입 정보 알려주는 용
        String[] arr = c1.toArray(new String[0]);
        System.out.println(Arrays.toString(arr));              // [A, B, C]

        c1.remove("B");
        System.out.println("remove 후: " + c1);                // [A, C]
        c1.removeAll(List.of("C"));
        System.out.println("removeAll 후: " + c1);             // [A]
        c1.clear();
        System.out.println("clear 후: " + c1 + ", " + c1.isEmpty()); // [], true
    }
}
```

### 2. 실행 결과 예측 — Collection
```
false
2, false
true
```
`c.remove(Integer.valueOf(20))`은 **값 20**을 제거한다(→ [10, 30]). 만약 `c`가 List 타입 변수이고 `remove(20)`을 호출했다면 **인덱스 20 제거**로 해석되어 IndexOutOfBoundsException이 났을 것이다. Integer 컬렉션에서 remove의 오버로딩(값 vs 인덱스)은 단골 함정이다.

### 3. List 인덱스 메소드 실행 결과
```
c
1
3
[b, c, b]
[z, b, y, c, b, a]
```
- `indexOf`는 앞에서부터, `lastIndexOf`는 뒤에서부터 첫 일치 인덱스
- `subList(1, 4)`는 **끝 인덱스 미포함** → 인덱스 1, 2, 3
- `set(0, "z")`은 교체 → [z, b, c, b, a], `add(2, "y")`는 삽입(뒤로 밀림)

### 4. listIterator 벌크 삽입 — 모범 답안
```java
LinkedList<Integer> list = new LinkedList<>();
for (int i = 0; i < 10; i++) list.add(i);

// 매번 add(5, x)를 호출하면 매번 5번 위치까지 순회(O(n))가 반복된다.
// listIterator로 한 번만 이동하면 그 자리에서 O(1) 삽입을 반복할 수 있다.
ListIterator<Integer> iter = list.listIterator(5); // 이동은 딱 한 번
iter.add(100);
iter.add(101);
iter.add(102);

System.out.println(list); // [0, 1, 2, 3, 4, 100, 101, 102, 5, 6, 7, 8, 9]
```

### 5. 조건 삭제 두 가지 방법 — 모범 답안
```java
List<Integer> nums = new ArrayList<>();
for (int i = 1; i <= 10; i++) nums.add(i);

// (1) Iterator.remove() — expectedModCount도 함께 갱신되므로 안전
Iterator<Integer> it = nums.iterator();
while (it.hasNext()) {
    if (it.next() % 3 == 0) it.remove();
}

// (2) removeIf — 내부적으로 안전하게 일괄 제거
nums.removeIf(num -> num % 3 == 0);
```
for-each 안에서 `nums.remove()`를 직접 호출하면 컬렉션의 modCount가 바뀌어 Iterator가 기대하는 값과 어긋나므로 **ConcurrentModificationException**이 발생한다.

### 6. HashSet 중복 제거 — 모범 답안
```java
// 1. 기본형 중복 제거
int[] arr = {3, 1, 3, 5, 1};
Set<Integer> set = new HashSet<>();
for (int n : arr) set.add(n);
System.out.println(set); // [1, 3, 5]

// 2. 사용자 객체 — hashCode와 equals를 함께 재정의해야 한다
class Product {
    String sn;
    public Product(String sn) { this.sn = sn; }

    @Override
    public int hashCode() {
        return sn.hashCode(); // 잘 재정의된 String의 hashCode 활용 권장
    }

    @Override
    public boolean equals(Object obj) {
        if (obj != null && obj instanceof Product p) {
            return this.sn.equals(p.sn);
        }
        return false;
    }
}
```
HashSet은 hashCode로 버킷을 찾고(O(1)) → 충돌 시 equals로 진짜 일치 여부를 확인한다. 둘 중 하나만 재정의하면 중복 판정이 깨진다.

### 7. Set에는 update가 없다
Map은 key + value 구조라 "key는 두고 값만 교체"가 자연스럽지만, **Set은 원소 자체가 곧 데이터**이므로 "그 값을 수정한다"는 개념이 성립하지 않는다. 값을 바꾸려면 지우고 새로 넣는다.
```java
set.remove("apple");
set.add("banana");
```

### 8. Map CRUD 종합 — 모범 답안
```java
Map<String, Integer> scores = new HashMap<>();
scores.put("kim", 90);
scores.put("lee", 80);

scores.putAll(Map.of("park", 70, "choi", 60));

System.out.println(scores.containsKey("kim"));    // true
System.out.println(scores.containsValue(90));     // true

System.out.println(scores.get("kim"));            // 90
System.out.println(scores.get("hong"));           // null (없는 키)

System.out.println(scores.size());                // 4
System.out.println(scores.isEmpty());             // false

scores.remove("lee");
System.out.println(scores);                       // lee 빠진 3개
scores.clear();
```

### 9. Map 3가지 순회 — 모범 답안
```java
// (1) keySet : key로 순회하며 get으로 값 조회
for (String key : scores.keySet()) {
    System.out.println(key + " = " + scores.get(key));
}

// (2) values : 값만 필요할 때
for (Integer score : scores.values()) {
    System.out.println(score);
}

// (3) entrySet : key와 value가 모두 필요할 때 가장 효율적
for (Map.Entry<String, Integer> e : scores.entrySet()) {
    System.out.println(e.getKey() + " = " + e.getValue());
}
```
key와 value가 둘 다 필요하면 entrySet이 정석이다. keySet 순회 + get은 매번 해시 조회를 다시 하므로 낭비다.

### 10. put vs putIfAbsent 실행 결과
```
null
1
2
null
{a=2, b=4}
```
- `put`은 **이전 값**을 반환 (처음이면 null), 있으면 덮어씀
- `putIfAbsent`는 key가 이미 있으면 **현재 값을 반환하며 무시**, 없으면 넣고 null 반환

### 11. 불변 컬렉션 판별
| 라인 | 결과 |
|---|---|
| (1) `List.of` + set | (c) UnsupportedOperationException — 불변 |
| (2) `Set.of("a", "a")` | (c) IllegalArgumentException — 중복 불가 |
| (3) `Map.of("k", null)` | (c) NullPointerException — null 불가 |
| (4) `Arrays.asList` + set | (a) 정상 동작 — 요소 수정은 가능 |
| (5) `Arrays.asList` + add | (c) UnsupportedOperationException — 고정 크기 |

`List.of / Set.of / Map.of`는 **불변 + null 금지**, `Arrays.asList`는 **고정 크기지만 수정은 가능**. 이 차이를 정확히 구분하자.

### 12. ArrayList vs LinkedList 선택
| 상황 | 선택 | 이유 |
|---|---|---|
| 인덱스로 자주 조회하는 정적 데이터 | ArrayList | 배열 기반이라 인덱스 접근 O(1) |
| 맨 앞에 데이터를 계속 추가 | LinkedList | head 포인터만 교체, ArrayList는 전체를 뒤로 밀어야 함 |
| 반복자로 순회 중 중간 대량 삽입/삭제 | LinkedList | 이동 후 그 자리에서 O(1) 삽입/삭제 반복 |
| 일반적인 상황 | ArrayList | 성능/메모리 모두 유리, arraycopy 최적화가 좋음 |

## 2부. 객체 정렬 (Comparable / Comparator)

### 13. Comparable 구현 — 모범 답안
```java
class Student implements Comparable<Student> {
    String name;
    int score;
    public Student(String name, int score) {
        this.name = name;
        this.score = score;
    }
    @Override
    public int compareTo(Student other) {
        return Integer.compare(this.score, other.score); // 오름차순
    }
    @Override
    public String toString() {
        return name + "(" + score + ")";
    }
}

List<Student> list = new ArrayList<>(List.of(
        new Student("kim", 90), new Student("lee", 70), new Student("park", 80)));
Collections.sort(list);
System.out.println(list); // [lee(70), park(80), kim(90)]
```
`this.score - other.score`도 동작하지만 overflow 위험이 있으므로 `Integer.compare()` 사용을 습관화하자.

### 14. 기존 compareTo 재활용 — 모범 답안
```java
class SmartPhone implements Comparable<SmartPhone> {
    String number;
    public SmartPhone(String number) { this.number = number; }
    @Override
    public int compareTo(SmartPhone other) {
        return this.number.compareTo(other.number); // String의 compareTo 재활용
    }
    @Override
    public String toString() { return "전화 번호" + number; }
}
```
이미 사용 가능한 기준(String, Integer 등)이 있다면 **직접 만들지 말고 활용**하는 것이 좋다.

### 15. Comparator 구현 클래스 — 모범 답안
```java
class StudentNameComparator implements Comparator<Student> {
    @Override
    public int compare(Student o1, Student o2) {
        return o1.name.compareTo(o2.name);
    }
}

Collections.sort(list, new StudentNameComparator());
```
Comparable은 클래스의 **기본 정렬 기준** 1개, Comparator는 **외부에서 주입하는 별도 기준**을 몇 개든 만들 수 있다.

### 16. 익명 클래스 — 모범 답안
```java
Collections.sort(list, new Comparator<Student>() {
    @Override
    public int compare(Student o1, Student o2) {
        return o1.name.compareTo(o2.name);
    }
});
```

### 17. 람다 / 메서드 참조 / 역순 — 모범 답안
```java
// 1. 점수 내림차순 (인자 순서를 바꾸면 역순)
Collections.sort(list, (s1, s2) -> Integer.compare(s2.score, s1.score));

// 2. Integer 배열 정렬
Integer[] nums = {1, 7, 3, 4, 5};
Arrays.sort(nums, (n1, n2) -> n1.compareTo(n2)); // (a) 람다
Arrays.sort(nums, Integer::compareTo);           // (b) 메서드 참조 — 같은 의미

// 3. 역순 정렬
List<String> names = new ArrayList<>(List.of("Hi", "Java", "World"));
names.sort(Comparator.reverseOrder()); // [World, Java, Hi]
```
람다에서 매개변수와 실행문의 구조가 단순하면 괄호/return을 생략할 수 있고, 기존 메소드를 그대로 넘길 뿐이라면 메서드 참조로 더 줄일 수 있다.

### 18. 다중 조건 정렬 — 모범 답안
```java
list.sort(Comparator.comparingInt((Student s) -> s.score).reversed()
        .thenComparing(s -> s.name));
```
`reversed()`로 1차 기준(점수)을 내림차순으로 뒤집고, `thenComparing`으로 동점일 때의 2차 기준(이름 오름차순)을 잇는다.

## 3부. Stream 주요 메소드

### 19. 기본 파이프라인 — 모범 답안
```java
List.of("superman", "batman", "ironman", "hulk").stream()
        .filter(name -> name.length() >= 5)   // 중간 : 걸러내기
        .map(String::toUpperCase)             // 중간 : 변환
        .forEach(System.out::println);        // 최종 : 소비
// SUPERMAN, BATMAN, IRONMAN
```

### 20. 실행 결과 예측
```
[3, 5, 8]
```
단계별 추적 : distinct → 5, 3, 8, 1, 9, 2 / sorted → 1, 2, 3, 5, 8, 9 / skip(2) → 3, 5, 8, 9 / limit(3) → 3, 5, 8

### 21. peek — 모범 답안
```java
List<Integer> r = List.of(1, 2, 3, 4, 5).stream()
        .peek(n -> System.out.println("filter 전: " + n))
        .filter(n -> n % 2 == 0)
        .peek(n -> System.out.println("filter 후: " + n))
        .map(n -> n * 2)
        .toList();
```
스트림은 **지연 연산(lazy)** 이다. 중간 연산은 파이프라인 설계만 해두고, 최종 연산이 호출되어야 실제로 요소가 흐른다. 최종 연산이 없으면 peek도 실행되지 않는다.

### 22. 숫자 스트림 집계 — 모범 답안
```java
int[] scores = {90, 75, 88, 60, 95};

System.out.println(Arrays.stream(scores).sum());                    // 408
System.out.println(Arrays.stream(scores).average().getAsDouble()); // 81.6
System.out.println(Arrays.stream(scores).max().getAsInt());        // 95
System.out.println(Arrays.stream(scores).min().getAsInt());        // 60
System.out.println(Arrays.stream(scores).count());                 // 5
```
max/min/average는 빈 스트림일 수 있으므로 OptionalInt/OptionalDouble을 반환한다. 스트림은 한 번 소비하면 재사용할 수 없으므로 각 집계마다 새로 만들어야 한다.

### 23. mapToInt vs map
`map(String::length)`은 `Stream<Integer>`를 만든다 — 박싱된 Integer라서 sum/average 같은 숫자 전용 집계 메소드가 없다. `mapToInt`는 기본형 특화 스트림 **IntStream**을 만들어 박싱 비용 없이 sum(), average() 등을 바로 쓸 수 있다.
```java
int total = List.of("a", "bb", "ccc").stream()
        .mapToInt(String::length)
        .sum(); // 6
```

### 24. flatMap — 모범 답안
```java
List<List<Integer>> nested = List.of(List.of(1, 2), List.of(3, 4), List.of(5));

List<Integer> flat = nested.stream()
        .flatMap(List::stream)
        .toList();                 // [1, 2, 3, 4, 5]

int sum = nested.stream()
        .flatMap(List::stream)
        .mapToInt(Integer::intValue)
        .sum();                    // 15
```

### 25. 매칭 연산 실행 결과
```
true
true
true
2
```
kim(3), lee(3), park(4) — 모두 길이 3 이상 / "k"로 시작하는 kim 존재 / 빈 문자열 없음 / 길이 3은 kim, lee 두 개.

### 26. findFirst + Optional — 모범 답안
```java
String result = List.of(7, 3, 12, 8, 20).stream()
        .filter(n -> n > 10)
        .findFirst()                    // Optional<Integer>
        .map(String::valueOf)
        .orElse("없음");
System.out.println(result); // 12
```
findFirst는 결과가 없을 수 있어 Optional을 반환하고, orElse/orElseGet으로 기본값을 처리한다.

### 27. reduce — 모범 답안
```java
// 1. 초기값 있는 reduce → 그냥 int 반환
int product = Stream.of(1, 2, 3, 4).reduce(1, (a, b) -> a * b); // 24
```
2. 초기값 없는 `reduce(Integer::sum)`의 반환 타입은 **`Optional<Integer>`** 다. 스트림이 비어 있으면 반환할 값 자체가 없기 때문이다. 초기값이 있으면 빈 스트림이라도 초기값을 반환하면 되므로 그냥 T를 반환한다.

### 28. collect — 모범 답안
```java
List<String> fruits = List.of("apple", "kiwi", "banana", "kiwi");

// 1. toList
List<String> longNames = fruits.stream()
        .filter(f -> f.length() >= 5)
        .collect(Collectors.toList()); // [apple, banana]

// 2. toSet — 중복 자동 제거
Set<String> unique = fruits.stream()
        .collect(Collectors.toSet());  // [banana, kiwi, apple]

// 3. toMap — 중복 키가 있으면 IllegalStateException!
Map<String, Integer> map = fruits.stream()
        .distinct() // 먼저 중복 제거하거나,
        .collect(Collectors.toMap(f -> f, String::length));
// 또는 병합 함수를 제공 : toMap(f -> f, String::length, (a, b) -> a)
```
toMap은 같은 키가 두 번 나오면 예외가 나므로 distinct 또는 병합 함수(merge function)로 대비해야 한다.

### 29. for문 → 스트림 리팩토링 — 모범 답안
```java
double avg = heros.stream()
        .mapToInt(String::length)
        .filter(len -> len > 3)
        .average()
        .getAsDouble();
System.out.println(avg); // (8+6+7+4)/4 = 6.25
```
합계/카운트 변수를 직접 관리하던 로직이 파이프라인 한 문장으로 정리된다.

### 30. 종합 파이프라인 — 모범 답안
```java
List<String> top3 = students.stream()
        .filter(s -> s.score >= 60)
        .sorted(Comparator.comparingInt((Student s) -> s.score).reversed())
        .limit(3)
        .map(s -> s.name)
        .toList();
```
설계 순서 : 걸러내고(filter) → 정렬하고(sorted + Comparator) → 자르고(limit) → 필요한 형태로 바꿔(map) → 수집(toList). 2부의 Comparator와 3부의 스트림이 결합되는 실전 형태다.

## 4부. 예외 처리

### 31. try-catch-finally 흐름
- **num = 2** : `A → B → D → E` (예외 없음, catch 건너뜀, finally는 실행)
- **num = 0** : `A → C → D → E` (B 건너뜀, catch 처리, finally 실행, 정상 흐름 복귀)

finally는 예외 발생 여부와 상관없이 **언제나** 실행된다.

### 32. 다중 catch 순서
**컴파일 에러가 발생한다.** 첫 번째 catch가 조상 타입(Exception)을 잡으면 그 아래의 자식 예외(ArrayIndexOutOfBoundsException) catch에는 도달할 수 없으므로 컴파일러가 거부한다.
수정 : **자식(구체적인) 예외를 먼저, 조상(포괄적인) 예외를 나중에** 배치한다.
```java
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("ArrayIndexOutOfBoundsException");
} catch (Exception e) {
    System.out.println("Exception");
}
```

### 33. finally 리팩토링 — 모범 답안
```java
InstallApp app = new InstallApp();
try {
    app.copy();
    app.install();
} catch (Exception e) {
    e.printStackTrace();
} finally {
    app.delete(); // 성공하든 실패하든 한 곳에서 정리
}
```

### 34. throws 위임 — 모범 답안
```java
static void readFile() throws Exception {
    throw new Exception("파일 없음");
}

// (1) 호출하는 쪽에서 처리
static void caller1() {
    try {
        readFile();
    } catch (Exception e) {
        System.out.println("처리: " + e.getMessage());
    }
}

// (2) 호출하는 쪽도 다시 위임 — 결국 누군가는 처리해야 한다
static void caller2() throws Exception {
    readFile();
}
```
checked exception은 이렇게 "처리하거나(catch) 선언하거나(throws)" 중 하나를 반드시 해야 컴파일된다. unchecked exception(RuntimeException 계열)이었다면 throws 없이도 자동으로 전파된다.

### 35. 사용자 정의 예외 — 모범 답안
```java
class FruitNotFoundException extends Exception {
    public FruitNotFoundException(String name) {
        super(name + "에 해당하는 과일은 없습니다");
    }
}

public class CustomExceptionTest {
    private static String[] fruits = {"사과", "오렌지", "토마토"};

    public static void main(String[] args) {
        try {
            getFruit("오렌지");   // 성공 (오렌지는 null 처리됨)
            getFruit("오렌지");   // 두 번째 → 예외 발생
        } catch (FruitNotFoundException e) {
            e.printStackTrace(); // "오렌지에 해당하는 과일은 없습니다"
        }
    }

    private static void getFruit(String name) throws FruitNotFoundException {
        for (int i = 0; i < fruits.length; i++) {
            if (fruits[i] != null && fruits[i].equals(name)) {
                fruits[i] = null; // 꺼낸 과일은 소진 처리
                return;
            }
        }
        throw new FruitNotFoundException(name);
    }
}
```
포인트 : Exception을 상속(→ checked)하고, 생성자에서 `super(메시지)`로 메시지를 넘기면 getMessage()로 꺼낼 수 있다. checked이므로 던지는 메소드에 `throws` 선언이 필요하다.

### 36. 상황별 Throwable 메소드
1. **printStackTrace()** — 예외 발생 위치와 호출 스택 전체를 출력하므로 개발/디버깅에 적합
2. **getMessage()** — 메시지 문자열만 얻어 사용자에게 간단히 안내
3. **getCause()** — 예외를 감싸 다시 던진 경우(예외 번역) 원인이 된 원래 예외를 추적

### 37. checked / unchecked 판별
| checked (컴파일러가 처리 강제) | unchecked (RuntimeException 계열) |
|---|---|
| IOException | ArithmeticException |
| ClassNotFoundException | NullPointerException |
| FileNotFoundException | ArrayIndexOutOfBoundsException |
| | InputMismatchException |

기준 : RuntimeException을 상속하면 unchecked, 그 외 Exception 계열은 checked.

### 38. 부적절한 예외 처리 리팩토링
**(A)의 문제** : 예외를 **흐름 제어(반복 종료) 용도**로 사용하고 있다. 예외는 예외적인 상황을 위한 것이며, 예외 생성/스택 추적 비용도 크고 코드의 의도도 불명확해진다.
```java
private static void endByException() {
    int sum = 0;
    for (int i = 0; i < nums.length; i++) { // 정상적인 종료 조건 사용
        sum += nums[i];
    }
}
```

**(B)의 문제** : `scanner.nextInt()` 같은 **상태 종속적 메소드**를 예외에 기대어 사용하고 있다. 상태 확인 메소드(`hasNextInt()`)와 함께 사용해 예외 상황 자체를 만들지 않아야 한다.
```java
private static void useScannerGood() {
    Scanner scanner = new Scanner(System.in);
    int sum = 0;
    while (scanner.hasNextInt()) {  // 상태 확인 후 읽기
        int input = scanner.nextInt();
        if (input == 0) break;
        sum += input;
    }
    scanner.close();
}
```
공통 교훈 : **예외는 "정말 예외적인 상황"에만** 사용한다. 예측 가능한 상황은 조건문과 상태 확인 메소드로 다룬다.
