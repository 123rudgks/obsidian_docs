# 1. 왜 Foundation Model을 개인화해야 하는가?

Foundation Model은 방대한 Data를 통해

- 다양한 Visual Pattern
    
- 일반 Knowledge
    
- 많은 Object
    
- 여러 Domain
    

을 학습한다.

따라서 새로운 Task에서도 좋은 출발점이 된다.

하지만 Pre-training Data가 아무리 많아도 모든 상황을 포함할 수는 없다.

---

# 2. Foundation Model의 한계

강의에서는 대표적으로 다음을 설명한다.

```text
Pre-training Data가 오래됨
→ 최신 정보 부족

특정 Domain Data 부족
→ 해당 분야 최적화 부족

특정 User / Product / Identity
→ 사전학습에 존재하지 않을 수 있음
```

따라서

> **이미 학습된 Knowledge를 유지하면서 필요한 부분만 조금 수정하는 능력**

이 중요하다.

---

# 3. AI를 단순히 사용하는 것에서 한 단계 더

강의에서는 실무적으로 Foundation Model 시대에 필요한 역량을

```text
AI를 사용한다.
```

보다 한 단계 확장해

```text
AI Model을
내 목적에 맞게 조금 수정한다.

여러 Model을
서로 연결한다.
```

정도의 능력으로 설명한다.

그리고 가장 기본적인 기술이 **Fine-tuning**이다.

---

# 4. Fine-tuning

Fine-tuning은

> **이미 학습된 Model을 새로운 Data를 이용해 조금 더 학습하여 Parameter를 수정하는 것**

이다.

```text
Pre-trained Model
      ↓
Small Task-specific Dataset
      ↓
Additional Training
      ↓
Adapted Model
```

이다.

---

# 5. 처음부터 Training과 원리는 같다

Fine-tuning도 결국

```text
Forward
↓
Loss
↓
Backpropagation
↓
Gradient Descent
↓
Parameter Update
```

를 수행한다.

즉 학습 Mechanism이 완전히 새로운 것은 아니다.

차이는 **출발점**이다.

---

# 6. From Scratch Training

```text
Random / Initial Parameters
↓
Large Dataset
↓
Long Training
```

---

# 7. Fine-tuning

```text
이미 좋은 Pre-trained Parameters
↓
Small Dataset
↓
Small Additional Update
```

이다.

따라서 일반적으로

- 적은 Data
    
- 적은 Compute
    
- 짧은 Training
    
- 적은 Code
    

로도 Task Adaptation을 할 수 있다는 것이 강의의 핵심이다.

---

# 8. Fine-tuning을 바로 시작하기 전에 해야 할 것

강의에서는 바로 Fine-tuning부터 하는 것을 권하지 않는다.

먼저

```text
Prompt Engineering
+
In-context Learning
```

을 시도한다.

---

# 9. 왜 Prompting부터 해 보는가?

Prompt를 바꾸면서

```text
현재 Model로
어디까지 가능한가?

어떤 부분에서 실패하는가?

Example을 주면
성능이 올라가는가?
```

를 먼저 확인할 수 있다.

즉 Fine-tuning이 정말 필요한지 판단하는 **Diagnostic 단계**다.

---

# 10. 추천 순서

강의의 흐름은 다음과 같다.

```text
Base Foundation Model
      ↓
Prompt Engineering
      ↓
Few-shot / In-context Learning
      ↓
성능 충분?
 ├─ Yes → 그대로 사용
 └─ No
      ↓
Fine-tuning 고려
```

---

# 11. Few-shot Prompting의 한계

Few-shot에서는 Example을 Prompt 안에 넣는다.

```text
Example 1

Example 2

Example 3

...

Current Query
```

문제는 Example도 모두 **Token**으로 들어간다는 것이다.

---

# 12. Context Window 문제

Example이 너무 많으면

```text
Examples ↑
↓
Input Token ↑
↓
Context Window 사용량 ↑
```

한다.

수백·수천 개 Example을 Prompt에 모두 넣을 수는 없다.

심하면 실제 User Query가 Context에서 상대적으로 중요하지 않게 처리될 수도 있다.

---

# 13. Fine-tuning의 직관 — Example을 Model 안에 녹인다

Few-shot:

```text
매 Request마다
Example을 Prompt로 전달
```

Fine-tuning:

```text
Example을 Training Data로 사용
↓
Model Parameter에 Pattern을 반영
↓
Inference 때 Example을
매번 전달할 필요 감소
```

이다.

---

# 14. Fine-tuning의 Service적 장점

Prompt가 짧아지면

```text
Input Token ↓
Processing Token ↓
API Cost ↓
Latency ↓
```

의 효과도 기대할 수 있다.

즉 Fine-tuning은 단순 Accuracy뿐 아니라 **Inference Efficiency**와도 연결될 수 있다.

---

# 15. Fine-tuning과 Gradient Descent

Fine-tuning도 Gradient Descent를 사용한다.

Gradient는

> **Loss를 Parameter에 대해 미분하여 얻은 변화 방향**

이다.

Model Parameter를 Loss가 낮아지는 방향으로 조금씩 이동시킨다.

---

# 16. 강의의 강아지 비유

강의에서는 강아지가

```text
"앉아"
```

라는 목표 자세를 학습한다고 생각한다.

강아지 관절의 각도:

```text
Model Parameters
```

관절을 움직여야 하는 방향:

```text
Gradient
```

한 번에 얼마나 움직일지:

```text
Learning Rate
```

와 대응시킨다.

---

# 17. Fine-tuning에서 Learning Rate가 특히 중요

이미 Model은 좋은 Parameter 위치에서 시작한다.

따라서 큰 Update로 기존 Knowledge를 크게 망가뜨릴 필요가 없다.

```text
Fine-tuning
→ Conservative Update
```

가 중요하다.

---

# 18. Learning Rate가 너무 작으면

```text
Update가 매우 작음
↓
Training 느림
↓
충분히 Adapt하지 못할 수 있음
```

강의에서는 지나치게 작은 Learning Rate 때문에 원하는 지점까지 이동하지 못하는 직관을 설명한다.

---

# 19. Learning Rate가 너무 크면

```text
Parameter가 크게 Jump
↓
좋은 기존 Parameter 영역 이탈
↓
Loss 증가 / Training 불안정
```

할 수 있다.

따라서 Fine-tuning에서는 적절하고 보수적인 Learning Rate 설정이 중요하다.

---

# 47. Synthetic Data 활용 ① Knowledge Distillation

강의에서 첫 번째 실용적 활용법으로 **Knowledge Distillation**을 소개한다.

다른 이름으로

```text
Teacher–Student Learning
```

이라고 이해할 수 있다.

---

# 48. Teacher Model

이미 성능이 높은 큰 Model을 준비한다.

```text
Large High-performance Model
=
Teacher
```

---

# 49. Student Model

우리가 실제로 배포하고 싶은 더 작은 Model을 준비한다.

```text
Small Model
=
Student
```

---

# 50. Training 구조

같은 Input을 두 Model에 넣는다.

```text
Input
├─→ Teacher → Teacher Prediction
│
└─→ Student → Student Prediction
```

그리고

```text
Student Output
≈
Teacher Output
```

이 되도록 Loss를 준다.

---

# 51. Transfer Learning과 차이

### Transfer Learning / Fine-tuning

```text
Pre-trained Model 자체를
새 Task에 Update
```

### Knowledge Distillation

```text
Teacher Model은
정답을 제공하는 역할

다른 Student Model이
Teacher Behavior를 학습
```

한다.

즉 **Teacher 자체를 Student로 바꾸는 것이 아니다.**

---

# 52. Hard Label만 사용하는 것과 차이

Ground Truth가

```text
Cat = 1
Dog = 0
```

처럼 Hard Label만 있다면 정보가 제한적이다.

Teacher는

```text
Cat 0.72
Dog 0.20
Fox 0.07
...
```

처럼 더 풍부한 Probability Distribution을 제공할 수 있다.

---

# 53. Soft Label

Teacher의 이런 Probability Output을 **Soft Label**이라고 볼 수 있다.

여기에는 단순 정답뿐 아니라

```text
Class 간 Similarity

Confidence

Teacher가 학습한 관계
```

가 포함될 수 있다.

---

# 54. 왜 작은 Student가 더 잘 배울 수 있는가?

Raw Training Data를 작은 Model이 직접 해석하는 것보다

```text
이미 큰 Teacher가
Data를 소화해서 만든 Output
```

을 따라가는 것이 쉬울 수 있다.

즉 Teacher Prediction 안에 숨은 Knowledge까지 Student가 전달받는다.

---

# 55. Distillation도 Synthetic Data 활용이다

Teacher가 만든

```text
Pseudo Label / Soft Label
```

은 원래 Human Ground Truth가 아니다.

Model이 생성한 Label이다.

따라서 강의에서는 이것도 **Synthetic Data의 한 형태**로 본다.

---

# 56. Distillation의 대표 목적

```text
Large Model
↓
Knowledge Distillation
↓
Small Model
```

로 압축하여

- Mobile
    
- Edge
    
- Low-latency Service
    

등에 활용할 수 있다.

---

# 100. 가장 단순한 Tool Augmentation — RAG

강의에서는 대표적인 예로 **Retrieval-Augmented Generation(RAG)** 을 든다.

```text
LLM
+
Search / Retrieval Tool
```

이다.

---

# 101. RAG의 역할

외부 Database를 조회할 수 있으므로

```text
Pre-training 이후 최신 정보
```

를 추가 Training 없이 사용할 수 있다.

---

# 102. Personalization에도 활용 가능

User별 Database를 따로 만들면

```text
User-specific DB
↓
Retrieval
↓
LLM
```

을 통해 Parameter Fine-tuning 없이도 개인화된 Response를 만들 수 있다.

---

# 103. Hallucination 완화

외부 Knowledge를 검색하고 Evidence를 Context에 주면

```text
Internal Memory만으로 Generation
```

하는 것보다 사실 확인을 할 기회가 생긴다.

따라서 정확도 향상이나 Hallucination 감소에도 활용할 수 있다.

---

# 105. Visual Programming

강의에서는 Vision Foundation Model을 Tool처럼 연결하는 **Visual Programming** 사례를 소개한다.

흥미로운 점은 중심 Model이 반드시 VLM일 필요가 없다는 것이다.

```text
Language Model
```

이 Planning을 담당할 수 있다.

---

# 106. LLM이 Image를 직접 보지 않아도 된다

User:

```text
"이 Image의 곰을 북극곰으로 바꾸고
배경을 눈밭으로 바꿔."
```

라고 요청한다고 하자.

LLM 자체는 Image Feature를 직접 처리하지 않을 수 있다.

대신

```text
1. Segmentation Tool 실행

2. Ground 영역 찾기

3. Ground를 Snow로 Edit

4. 다시 Object 탐색

5. Bear를 Polar Bear로 Edit
```

와 같은 Program을 작성한다.

---

# 107. Tool Library

LLM에게 사용할 수 있는

```text
Image Understanding API

Segmentation

Detection

Editing

Logic Functions
```

등을 미리 알려준다.

그리고 Program Example도 Context에 제공한다.

---

# 108. In-context Learning으로 Program 생성

```text
Instruction
+
Available Tools
+
Example Programs
      ↓
LLM
      ↓
High-level Program
```

을 생성한다.

별도의 Visual Agent Fine-tuning 없이도 가능한 구조다.

---

# 109. 생성된 Code를 실제 실행

LLM이 만든 Program을 Python Interpreter 등에서 실행하고

```text
실제 Image
+
Tool APIs
```

를 넣어 최종 Result를 얻는다.

즉 LLM은 **직접 모든 Perception을 하지 않고 Tool을 조합하는 Planner**다.

---

# 122. 마지막 실무 주제 — Model Serving

아무리 좋은 Foundation Model을 가지고 있어도 실제 User가 사용할 수 있어야 한다.

그래서 마지막에는 **Serving**을 다룬다.

---

# 123. Serving

Model Serving은

> **AI Model을 Server에서 실행 가능한 상태로 유지하고 외부 Application의 Request를 받아 Prediction을 반환하는 것**

이다.

```text
Model Server
↓
Model Loaded
↓
Request 대기
```

상태로 유지한다.

---

# 124. 일반적인 Service 구조

```text
Frontend
↓
HTTP / REST / gRPC
↓
Model Server
↓
AI Model
↓
Response
```

이다.

---

# 125. 직접 Server 구축의 어려움

Open Model을 직접 Download하려면

- GPU
    
- Linux Environment
    
- Dependency
    
- Serving Framework
    
- Model Setup
    

등이 필요하다.

초보자나 간단한 Prototype에서는 부담스럽다.
