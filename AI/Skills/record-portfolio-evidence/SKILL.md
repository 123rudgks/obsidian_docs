# 포트폴리오 기여 근거 기록

프로젝트를 진행하면서 사용자의 실제 기여와 그 결과를 보존한다. 나중에 다른 에이전트가 `portfolio.md` 하나로 포트폴리오를 작성할 수 있게 한다. 완성된 자기소개서나 홍보 문구를 쓰지 않는다. 기본 기록 언어는 사용자의 언어다.

## 출력과 시작

- 대상 프로젝트의 지침과 기존 기록을 먼저 확인한다. 기본 위치는 프로젝트 루트의 `portfolio-evidence/`이며, 사용자가 지정한 위치나 기존 위치를 우선한다.
- 최종 자료는 **`portfolio.md` 하나**다. 공통 Situation 아래에 안정적인 ID를 가진 Task를 추가하고 각 Task 안에 여러 Action과 Result를 연결한다. Task마다 파일을 만들지 않는다.
- **`recording-state.md`**는 기록 작업 재개용 최신 상태다. 다음 Task 번호, 확인 범위, 진행 중 Task 연결, 미반영 근거와 중요한 미확인 사항만 관리한다. 이미 확보했지만 반영하지 못한 자료와 아직 모르는 사실을 구분한다. 프로젝트 디버깅 인수인계나 작업 일지로 사용하지 않는다. 사용자 기여·결과·해석에 필요한 한계를 이 파일에만 두지 않는다.
- 처음 만들 때 [본문 템플릿](assets/portfolio-template.md)과 [상태 템플릿](assets/recording-state-template.md)을 사용한다. 템플릿은 필수 입력 양식이 아니다. 관련 없는 항목·빈 절·예시 Task는 삭제하고, 해석에 필요한 공백만 `미확인`·`미측정`으로 표시한다. 같은 한계는 적용 범위가 드러나는 곳에 한 번 쓴다.
- 배경 정보는 접근 가능한 자료에서 먼저 찾는다. 학교·수업·팀·역할·기간 등 핵심 공백만 묶어서 짧게 묻고, 답변 전에도 확인된 사실은 기록한다. 동일한 미응답 질문을 매번 반복하지 않는다.
- 사용 가능한 대화·파일·도구 결과만 근거로 삼는다. 새 세션이 이전 대화를 볼 수 있다고 가정하지 않는다. 이 스킬은 상주 프로세스가 아니므로 읽히지 않는 세션에서 자동 기록을 약속하지 않는다.

## 본문과 미주

- 산출물에서 기록 대상자를 AI 대화상의 “사용자”로 부르지 않는다. 처음에 “본인(역할)”으로 소개하고 이후에는 “본인” 또는 주어 생략을 사용한다. 사용자가 다른 서술 시점을 지정하면 따른다. 미주의 출처 표현도 “본인 회고”·“본인 확인”으로 맞춘다. 서비스 이용자는 참가자·고객 등 실제 역할로 구분하며, 인용문은 임의로 바꾸지 않는다. 이 스킬 내부의 “사용자”는 지시 대상을 가리키는 용어다.
- 본문은 배경·문제·선택 이유·실제 역할·변화·결과를 중심으로 쓴다. “이렇게 기록한다”, “성과로 확대하지 않는다” 같은 작성 방침과 반복적인 방어 문장은 넣지 않는다. “본인이 운영 조건을 정하고 AI가 구현했다”처럼 실제 분담을 직접 쓴다.
- 출처 링크, 기록·보충일, 자료 확인 범위, 상세 측정 조건, 증거의 한계와 사실 정정 이력은 같은 `portfolio.md` 끝의 미주에 모으고 관련 주장에 연결한다. 같은 출처·한계는 적용 범위가 분명하면 미주 하나로 합친다. 단순 편집 이력은 남기지 않는다.
- 미주로 옮겨도 본문이 과장되어서는 안 된다. 실제 수행자, 사건 날짜, 목표와 실측의 구분, `본인 회고`·`미검증`처럼 결론을 바꾸는 최소 표시는 본문에 남긴다. 실제 운영 제약·실패·미해결 문제는 기록상의 단서가 아니라 결과이므로 본문에서 설명한다.
- 질문·답변 파일은 임시 수집 수단이다. 답변에서 기여 해석에 필요한 사실·판단 이유·분담·결과를 본문에 통합하고, 출처 성격과 한계는 미주에 보존한다. “Q3 참조”나 외부 질문 파일 링크로 내용을 대신하지 않는다. 원문 전체를 복사할 필요는 없다.
- 각 프로젝트의 `portfolio.md`는 독립적으로 읽혀야 한다. 다른 프로젝트의 경험이 필요하면 그 맥락을 요약해 포함한다. 저장소 내부 근거 링크도 설명의 대체물이 아니다. 질문 원본이나 다른 저장소를 보관하지 않아도 핵심 판단과 결과가 남아야 한다.

## 기여를 판별하는 기준

기본값은 기록하지 않음이다. 새 정보가 사용자의 의미 있는 판단·직접 수행과 그 영향, 기존 기여의 결과·검증·정정, 또는 이를 이해하는 데 필수적인 배경을 추가할 때만 기록한다. 사용자의 실제 발언과 그것이 바꾼 문제 정의·선택·실행·검증을 연결한다. 아직 결과가 없어도 구체적인 문제 발견이나 근거 있는 결정은 진행 중으로 보존한다. 단순 요청·자료 전달을 기여로 승격하지 않는다.

| 관찰된 사용자 개입 | 기록 방법 |
| --- | --- |
| “로그인 만들어 줘”, “응, 진행해” 같은 단순 요청·승인 | 보통 독립 기여로 만들지 않는다. 흐름 이해에 꼭 필요할 때만 짧게 언급한다. |
| AI 요청에 따른 에러 메시지·로그·스크린샷 전달, 재실행·커널 재시작 | 독립 기여로 만들거나 매회 기록하지 않는다. 역할 설명에 필요한 수행 범위는 기존 Action에 한 번 요약한다. 자료가 기존 결과를 입증하거나 뒤집으면 해당 Result에 반영한다. |
| AI 제안 중 “A로 하자”만 말함 | 필요한 경우 선택 사실을 남기되 `선택 이유 미확인`으로 쓴다. 전문적 판단을 추정하지 않는다. |
| “일정과 예상 규모를 고려하면 A면 충분해” | AI가 대안을 냈다는 출처와 사용자의 제약 기반 선택을 분리한다. |
| “A의 이 부분은 요구사항과 안 맞으니 바꿔” | 사용자가 추가한 조건과 변경 전후 차이를 기록한다. |
| “이 조건에서도 맞아? 확인해” | 구체적인 누락 조건·위험을 발견해 설계나 검증 범위를 바꿨을 때만 기록한다. 단순 확인 요청은 생략한다. 의심이 틀렸더라도 의미 있는 판단이면 실제 결과와 함께 남긴다. |

- 진행 보고, 반복 설명, 설치·다운로드 경과, 매번의 재시도·테스트 통과, 추가 출력 요청, 기록 완료 사실 자체는 남기지 않는다. 새 증거 없이 갱신일만 바꾸거나 상태 파일에 생략한 사건 목록을 쓰지 않는다.
- 디버깅은 사용자 기여나 기존 결과의 해석에 필요할 때만 `증상 → 확인된 원인 → 해결 판단 → 검증 결과`로 요약한다. 미해결이면 해당 Task의 현재 장애와 검증 한계만 짧게 갱신한다. 원시 traceback·메모리 덤프·실행 순서는 복사하지 않고 필요한 근거 경로를 연결한다.

- 제안자, 판단자, 수행자를 구분한다. AI 제안의 채택을 사용자의 독자적 발명으로, AI 구현을 사용자의 직접 구현으로 바꾸지 않는다. 공동으로 발전시킨 제안은 각각 무엇을 보탰는지 쓴다. 독립 기여가 아니어도 역할 설명에 필요한 사용자의 실행·결과 검토·제출 범위는 보존한다. 담당 선언이나 산출물의 존재만으로 실제 수행자를 추정하지 않는다.
- AI가 독립적으로 내린 판단과 작업은 기여 목록에 쌓지 않는다. 프로젝트 구성·흐름 또는 사용자 개입 전후의 인과관계 이해에 필요한 최소 맥락만 남긴다.
- 팀 성과와 개인 기여를 구분한다. 사용자 판단과 결과 사이의 연결이 불명확하면 `관련은 있으나 인과관계 미검증`으로 표시한다.
- 실제 발언을 확인할 수 있을 때만 따옴표로 짧게 인용한다. 요약·사용자 사후 설명·AI 해석을 구분하되, 공통 출처 설명은 미주에 한 번 적고 연결한다. 해석·미확인을 사실처럼 서술하지 않는다. 코드나 커밋만 보고 누가 아이디어를 냈는지 추정하지 않는다.
- 핵심 접근법의 선택이나 방향 전환은 `해결할 문제 → 선택한 방법 → 당시 기대한 효과와 근거`를 연결한다. 대안은 실제 검토한 것만 남긴다. 중요한 선택 이유가 없으면 접근 가능한 자료를 먼저 확인하고, 필요하면 짧게 질문하되 답을 얻기 전에도 미확인으로 보존한다. 사소한 선택마다 이유를 묻지 않는다. 나중의 결과·교훈으로 당시 이유를 대신하거나 사후 설명을 당시 발언처럼 쓰지 않는다. 사용자 회고는 독립 증거 유무를 표시한다.

## STAR와 날짜

각 Task는 전문 지식이 없는 독자도 문제·선택 이유·본인 역할·결과를 이해할 수 있게 쓰고, 기술 용어는 처음 등장할 때 필요한 만큼 설명한다.

- **Situation:** 프로젝트의 시작 배경(수업·대회·업무·개인 등), 목적, 기간, 팀과 본인 역할, 제약, 주요 구성과 흐름을 공통으로 작성한다. 변화한 역할·범위는 적용 시점을 적는다.
- **Task:** 구체적 문제, 발견 계기와 영향, 목표와 성공 기준을 쓴다. 단순 작업명 대신 왜 해결해야 했는지 드러낸다. 성공 기준을 뒤늦게 정했다면 그렇게 표시한다.
- **Action:** 선별된 기여에 `A-01` 같은 Task 내 ID를 부여한다. 사용자 개입과 이유, 바뀐 점, 사용자·AI·팀의 실제 수행 범위와 근거를 간결하게 연결한다. 같은 판단의 후속 진행은 기존 항목에 합친다. 실패·철회한 시도도 판단에 의미가 있으면 보존한다.
- **Result:** 어떤 Action과 연결되는지, 확인된 변화, 검증 방법과 증거, 목표 달성 여부, 한계를 남긴다. 구현 완료와 효과 검증 완료는 다르다. 결과가 없으면 `미검증`이지 성공이나 효과 없음이 아니다.
- 협업이 관련되면 개인 산출물 완료와 팀 전달·검토·최종 채택을 구분해 확인된 활용 상태만 짧게 쓴다. 결합 계획을 실제 활용으로 바꾸지 않는다. 미채택도 확인된 이유와 결과를 보존하며, 최종 활용을 모르면 중요한 미확인 사항으로 남긴다.
- 사건 날짜와 기록 날짜를 구분하고, 판단·실행·검증일이 다르면 필요한 곳에 표시한다. 같은 날짜를 필드마다 반복하지 않는다. 사건 날짜는 아는 정밀도만 사용한다(`YYYY-MM-DD`, 월만 알면 `YYYY-MM`, 모르면 `미확인`).
- 시각이 의미 있으면 시간대까지 남긴다. 기록 날짜는 환경의 현재 날짜로 확인하되 사건 날짜로 대체하지 않는다. 상대 날짜는 발언 기준일이 확인될 때만 환산한다. 사후 보충·정정에는 보충일과 대상 사건을 표시한다.

## 결과와 증거의 품질

문제 해결을 보여주는 정량 근거를 우선한다. 코드 줄 수·커밋 수처럼 활동량만 나타내는 숫자를 성과로 포장하지 않는다. 의미 없는 숫자보다 근거 있는 정성 결과가 낫다.

실제로 제시하는 수치의 해석·재현에 필요한 다음 조건을 남긴다. 적용되지 않는 항목은 생략하고, 결론의 신뢰 범위에 영향을 주는 누락만 표시한다.

- 무엇을 증명하는 지표인지, 단위와 통계량(평균·중앙값·p95 등).
- 변경 전 기준값과 변경 후 값, 목표값과 실측값의 구분.
- 측정 대상과 버전, 환경, 데이터 크기, 부하, 캐시 상태 등 비교에 영향을 주는 조건.
- 측정 방법·명령 또는 도구, 측정일, 반복 횟수·표본 수, 집계 방식.
- 출처(로그·테스트·보고서·사용자 제공 값 등)와 핵심 결과의 본문 요약.
- 비교 조건의 동일성, 혼재된 변경과 인과관계의 한계.

모든 항목이 있어야만 기록 가능한 것은 아니다. 부족하면 신뢰 범위를 제한한다. 측정하지 않은 값은 만들지 않는다. 추정·목표·사용자 보고·직접 관측을 구분한다. 서로 다른 조건의 수치를 개선율로 묶지 않는다. 백분율은 기준값과 식을 명시하고, 기준값 0이면 산출하지 않는다. 비율 차이의 퍼센트포인트와 상대 변화율도 구분한다.

정성 결과는 관찰된 전후 변화, 구체적 사례, 피드백 출처와 날짜, 확인 범위를 남긴다. 한 명의 피드백을 전체 사용자 만족도로 일반화하지 않는다. 학습·교훈도 사용자가 말한 것과 AI의 해석을 구분한다.

근거는 핵심 주장을 뒷받침하는 경로·심볼·커밋·명령·링크 중 필요한 것만 연결하고 핵심 결과를 요약한다. 모든 로그·환경 버전·실행 ID를 열거하지 않는다. 없는 커밋·로그를 만들어내지 않는다. 외부 자료나 저장소를 열지 않아도 핵심 판단과 결과를 이해할 수 있게 쓰되, 원본 증거의 보관은 프로젝트 파일에 맡기고 별도 보관 절차나 목록을 만들지 않는다. 원시 로그를 복사하지 않고 비밀키·개인정보·비공개 고객 데이터는 제거하거나 익명화한다. 비공개 근거는 존재와 접근 제한을 설명한다.

측정 공백을 메우려는 목적으로 구현을 바꾸거나 유료·외부·운영 환경 실험을 임의로 실행하지 않는다. 허용된 작업 범위 안의 가벼운 검증만 수행하고, 나머지는 미확인 사항과 재현 방법으로 남긴다.

## 갱신 절차

1. 새 정보가 기록 기준을 충족하는지 먼저 판단한다. 기록할 변화나 미반영 근거가 없으면 두 파일을 읽고 쓰는 절차와 기록 완료 보고를 생략한다. 명시적인 검토·재구성 요청은 해당 범위를 확인한다.
2. 최초 시작·재개 시 상태와 본문의 Task 목록을 확인하고, 대상 Task와 필요한 근거만 읽는다. 같은 세션에서 이미 읽었고 변경되지 않은 지침·템플릿·본문 전체를 반복해서 읽지 않는다. 상태의 확인 지점은 해당 본문과 대조한다.
3. 의미 있는 판단이 확정되거나 기존 기여의 결과·검증 상태가 달라졌을 때 관련 변경을 묶어 반영한다. 작업 마무리 자체는 기록 사유가 아니다. 문맥 손실 전에 중요한 미완료 판단은 보존하되 디버깅의 매 단계는 남기지 않는다.
4. 같은 문제·성공 기준이면 기존 Action·Result를 갱신한다. 독립적인 기여나 목표일 때만 새 ID를 만든다. 같은 결과는 한 곳에 두고 다른 Task에서 참조한다. Task 목록·본문·관련 한계의 현재 상태를 함께 맞추며, 오래된 설명 뒤에 보충만 붙이지 않는다.
5. 사용자의 직접 수정과 유효한 근거는 보존한다. 단순 진행 상태는 최신 내용으로 교체하고 중복은 합친다. 실질적인 사실 정정은 정정 전후·근거·날짜를 짧게 남기고 현재 결론도 고친다. 실패한 판단의 교훈이나 해결되지 않은 상충 증거는 삭제하지 않는다.
6. 본문 반영을 확인한 뒤 상태 파일을 최신 상태로 교체한다. 마지막 본문 반영 지점과 확인 범위를 구분하고, 부분 실패는 미반영 항목으로 남긴다. 중요한 미확인 사항은 관련 Task와 `미질문/답변 대기/결과 대기` 등 현재 상태를 짧게 남긴다. 자료 반영 완료를 확인할 사실이 없는 상태로 취급하지 않는다. 선택 이유·수행 범위·최종 활용처럼 기여 서술을 바꾸는 공백만 추적하고, 모든 미검증 항목이나 디버깅 출력 요청을 대기 목록으로 만들지 않는다. 해결된 항목은 제거하되 답변 완료 사실은 재질문 방지에 필요할 때만 유지한다.
7. 기여 주체·날짜·수치 조건·출처·검증 한계를 점검한다. 질문 원본과 외부 저장소 없이 `portfolio.md`의 본문과 미주만으로 선택 이유·실제 분담·결과·한계를 이해할 수 있는지 확인한다. 본문에는 기여를, 미주에는 필요한 근거 설명을 남기고 기록 방침·중복 단서를 제거한다. 미주 참조가 정의와 연결되는지 확인한다. 중요한 공백은 해당 미주와 상태의 후속 확인에 반영하며, ‘미실행/완료’, ‘대기 없음/요청 중’ 같은 충돌을 정리한다. 실제로 바뀐 Task와 중요한 미확인 사항만 짧게 알린다.

상태 파일이 없으면 본문에서 재구성한다. 사용자가 파일 하나를 넘겨 달라고 하면 `portfolio.md`를 제공한다. 그 파일을 읽는 후속 에이전트가 사용자 기여 범위와 증거의 한계를 지킬 수 있어야 한다.
