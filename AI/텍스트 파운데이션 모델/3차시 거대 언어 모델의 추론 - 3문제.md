# 0. 강의 전체 개요

앞 차시에서는 LLM을 어떻게 학습하는지를 배웠다.

```text
Pre-training
      ↓
Instruction Tuning
      ↓
Preference Learning
      ↓
RLHF
```

이번 차시의 질문은 그다음이다.

> **학습이 모두 끝난 LLM에 Prompt를 넣었을 때 실제 Response는 어떻게 생성되는가?**

전체 흐름은 다음과 같다.

```text
Prompt
      ↓
Tokenization
      ↓
LLM
      ↓
다음 Token의 Probability Distribution
      ↓
Decoding Algorithm
      ↓
실제 다음 Token 선택
      ↓
선택된 Token을 다시 Input에 추가
      ↓
다시 Probability Distribution
      ↓
다시 Decoding
      ↓
반복
      ↓
EOS 또는 Max Length
      ↓
생성 종료
```

그리고 Decoding 방법은 다음처럼 발전한다.

```text
Greedy Decoding
      ↓
Local Best의 한계
      ↓
Beam Search
      ↓
계산량 증가
      ↓
Sampling
      ↓
다양성은 증가하지만
낮은 확률 Token 문제
      ↓
Temperature
      ↓
Top-k Sampling
      ↓
고정 k의 한계
      ↓
Top-p / Nucleus Sampling
```

추론 단계에서는 Decoding뿐 아니라 Input 자체도 성능에 큰 영향을 준다.

```text
Inference
├─ Decoding
└─ Prompt Engineering
      ├─ Instruction
      ├─ System Prompt
      ├─ Chain-of-Thought
      ├─ Few-shot Examples
      └─ Structured Skill
```

---

# 1. LLM은 문장을 한 번에 생성하지 않는다

사용자가 보기에는 LLM이

```text
I am a student.
```

라는 Sentence 전체를 한 번에 만드는 것처럼 보일 수 있다.

하지만 실제 생성은 그렇지 않다.

```text
I
↓
am
↓
a
↓
student
↓
...
```

처럼 **Token을 하나씩 순차적으로 생성**한다.

강의에서는 이것을 **Autoregressive Generation(자동회귀 생성)** 으로 설명한다.

---

# 2. Autoregressive Generation

Autoregressive의 핵심은

> **방금 생성한 Token이 다음 Token을 생성할 때 다시 Input의 일부가 된다.**

는 것이다.

예:

```text
Prompt
↓
"I" 생성

Prompt + I
↓
"am" 생성

Prompt + I am
↓
"a" 생성

Prompt + I am a
↓
"student" 생성
```

즉 Output이 다음 Step의 Input으로 다시 들어간다.

---

# 3. 수식 구조

현재 Input Token Sequence가

`x₁, x₂, ..., x_L`

이라면 LLM은 다음 Token

`x_(L+1)`

을 위한 정보를 계산한다.

그 Token이 선택되고 나면 다음 Step의 Input은

`x₁, ..., x_L, x_(L+1)`

이 된다.

그리고 다시

`x_(L+2)`

를 생성한다.

이를 계속 반복한다.

---

# 4. LLM이 직접 출력하는 것은 Token이 아니다

매우 중요한 핵심이다.

LLM은 직접

```text
"왔어"
```

라는 Token 하나를 결정하는 것이 아니다.

정확히는

```text
왔어      0.30
왔는데    0.20
왔거든    0.10
먹었어    0.03
...
```

처럼 **Vocabulary 전체에 대한 다음 Token Probability Distribution**을 출력한다.

---

# 5. Model과 Decoding Algorithm 역할을 분리해야 한다

다음 Token 생성은 실제로 두 단계다.

```text
[LLM]

현재 Context
↓
다음 Token Probability Distribution


[Decoding Algorithm]

Probability Distribution
↓
실제 다음 Token 선택
```

즉

> **LLM = 확률분포를 예측**
> 
> **Decoding = 그 분포에서 실제 Token을 결정**

이다.

---

# 6. 따라서 같은 Model도 Output이 달라질 수 있다

Model Parameter가 완전히 같아도

```text
Greedy

Sampling

Top-k

Top-p
```

등 어떤 Decoding Algorithm을 사용하느냐에 따라 생성 결과가 달라질 수 있다.

따라서 실제 LLM Service를 이해하려면

```text
Model
+
Decoding
```

을 함께 이해해야 한다.

---

# 7. 생성은 언제 끝나는가?

Autoregressive Generation은 계속 다음 Token을 만들기 때문에 종료 조건이 필요하다.

강의에서는 크게 두 가지를 설명한다.

```text
1. EOS Token 생성

2. 사전에 정한 Maximum Length 도달
```

---

# 8. EOS Token

**EOS(End of Sentence/Sequence)** 는 Sequence가 끝났음을 나타내는 Special Token이다.

Model이 다음 Token으로 EOS를 높은 확률로 선택했다면

> **“여기서 생성을 끝내는 것이 자연스럽다.”**

고 판단한 것으로 볼 수 있다.

System은 EOS가 생성된 것을 확인하고 Generation을 종료한다.

---

# 9. Special Token

Text를 Tokenization할 때 일반 Word뿐 아니라 특별한 의미의 Token도 사용할 수 있다.

강의의 BERT Tokenizer 예에서는

- `[CLS]`
    
- `[SEP]`
    

등을 Sentence의 시작·구분·끝과 관련된 Special Token의 사례로 보여준다.

LLM Generation에서는 같은 큰 개념에서

```text
BOS
EOS
```

등의 Special Token을 이용해 Generation Boundary를 표현할 수 있다고 이해하면 된다.

---

# 10. Maximum Token Length

Model이 EOS를 계속 만들지 않을 수도 있다.

그렇다고 무한히 생성하게 둘 수는 없다.

따라서

```text
max_new_tokens = 100
```

같은 제한을 미리 설정할 수 있다.

그 한도에 도달하면 강제로 생성을 종료한다.

---

# 11. 생성 종료 조건 정리

```text
Generation
      ↓
EOS?
 ├─ Yes → Stop
 └─ No
      ↓
Max Token Length 도달?
 ├─ Yes → Stop
 └─ No → 계속 생성
```

---

# 12. 실제 Code에서는 이 과정이 감춰져 있다

강의에서는 PyTorch/Hugging Face 계열의 GPT-2 생성 예시를 보여준다.

사용자는 개념적으로

```text
Tokenizer
↓
Model
↓
generate()
↓
Decode
```

정도만 작성하면 된다.

하지만 `generate()` 내부에서는 실제로

```text
Token 생성
→ Input에 다시 추가
→ 다음 Token Prediction
→ Decoding
→ 반복
```

이 모두 수행된다.

---

# 13. Tokenizer의 역할

User가 입력한 Natural Language:

```text
Today I believe we finally ...
```

를 Model이 직접 문자열로 처리하는 것은 아니다.

먼저

```text
Natural Language
      ↓
Tokenizer
      ↓
Token IDs
```

로 변환한다.

Model은 이 Token Sequence를 입력으로 받는다.

---

# 14. 생성된 결과도 처음에는 Token이다

Model Generation 결과 역시 Token ID Sequence다.

따라서 다시 Tokenizer의 Decode 기능을 사용해

```text
Token IDs
      ↓
Natural Language
```

로 바꿔야 사람이 읽을 수 있다.

---

# 15. `generate()`의 Argument가 중요한 이유

겉으로는

```text
model.generate(...)
```

한 줄이지만 실제 `generate()`에는 많은 Argument가 존재한다.

이 Argument 설정에 따라

```text
Greedy

Beam Search

Sampling

Top-k

Top-p
```

등 서로 다른 Decoding 방식이 동작한다.

즉 Generation Quality는 Model만의 문제가 아니다.

---

# 16. Decoding Algorithm ① Greedy Decoding

가장 단순한 방법은

> **현재 Step에서 Probability가 가장 높은 Token을 선택한다.**

는 것이다.

이를 **Greedy Decoding**이라고 한다.

---

# 17. Greedy 예

Model이 다음 Token을

```text
good      0.4
nice      0.5
car       0.1
```

로 예측했다면

Greedy는

```text
nice
```

를 선택한다.

다음 Step에서도 가장 Probability가 높은 Token을 선택한다.

---

# 18. Greedy의 장점

### 간단하다

Implementation이 쉽다.

### 빠르다

매 Step에서 가장 높은 Token 하나만 선택하면 된다.

### Deterministic하다

동일한 Model과 동일한 Input이라면 일반적으로 동일한 Sequence가 나온다.

---

# 19. 하지만 Greedy에는 큰 문제가 있다

현재 Step에서 가장 좋은 선택이

> **전체 Sequence 관점에서도 가장 좋은 선택**

이라는 보장은 없다.

이것이 Greedy의 핵심 한계다.

---

# 20. Local Optimum 문제

두 Step Generation을 생각하자.

첫 Step:

```text
nice = 0.5
dog  = 0.4
```

Greedy는 `nice`를 선택한다.

그 뒤

```text
nice → woman = 0.4
```

라면 Sequence Probability는

`0.5 × 0.4 = 0.20`

이다.

---

# 21. 다른 Path가 전체적으로 더 좋을 수 있다

`dog`를 선택했을 경우

```text
dog → house = 0.9
```

라고 하자.

그러면

`0.4 × 0.9 = 0.36`

이다.

즉

```text
Greedy Path
0.20

Alternative Path
0.36
```

가 된다.

현재 Step에서 Probability가 조금 낮았던 선택이 뒤까지 보면 더 좋은 Sequence가 될 수 있다.

---

# 22. Greedy의 본질적 문제

```text
현재 가장 좋은 것
```

만 보고 결정하기 때문에

```text
미래에 더 좋은 결과로 이어질 Candidate
```

를 너무 일찍 버릴 수 있다.

---

# 23. 해결 — Beam Search

이 문제를 완화하기 위해 하나의 Candidate만 유지하지 않고 여러 Candidate를 유지한다.

이것이 **Beam Search**다.

---

# 24. Beam Size

Beam Search에서는 동시에 유지할 Candidate 수를

```text
Beam Size = K
```

라고 한다.

예:

```text
K = 2
```

라면 매 Step에서 상위 2개의 Sequence Candidate를 유지한다.

---

# 25. Beam Search 과정

```text
Step 1

Top-2 Candidate 유지
A
B
      ↓

Step 2

A에서 가능한 다음 Token
B에서 가능한 다음 Token
모두 계산
      ↓

전체 후보 중
Sequence Score Top-2 유지
      ↓

다음 Step 반복
```

---

# 26. Beam Search의 장점

Greedy가 첫 번째 선택을 잘못해 좋은 Path를 버리는 문제를 완화한다.

```text
Greedy
→ 1개 Path

Beam Search
→ K개 Path
```

를 동시에 탐색한다.

따라서 더 좋은 전체 Sequence를 발견할 가능성이 증가한다.

---

# 27. Beam Search의 단점 — 계산량

Beam Size가 `K`라면 여러 Candidate를 계속 유지해야 한다.

따라서 대략적으로 Candidate 수에 비례해 연산량이 증가한다.

```text
Beam Size ↑
→ Search 범위 ↑
→ Compute ↑
```

---

# 28. 큰 LLM에서는 Beam Search가 부담스럽다

LLM 자체의 한 번 Forward Pass 비용도 크다.

그런데 Beam을 여러 개 유지하면 이 비용이 다시 증가한다.

강의에서는 실제 대형 LLM에서 Beam Size를 크게 설정하기 어렵고, 현대 생성에서는 Beam Search를 적극적으로 사용하지 않는 경우가 많다고 설명한다.

---

# 29. 새로운 방향 — Sampling

Greedy와 Beam Search는 기본적으로 높은 Probability Token을 정해진 방식으로 선택한다.

다른 접근은

> **Probability Distribution에서 Random Sampling하자.**

는 것이다.

---

# 30. Random Sampling

예:

```text
green = 0.5
red   = 0.3
blue  = 0.2
```

라면

```text
green이 50% 확률로 선택

red가 30%

blue가 20%
```

되도록 Sampling한다.

---

# 31. Sampling의 장점 — Diversity

Greedy에서는 동일한 Prompt에 항상 같은 Token을 선택한다.

Sampling에서는 Randomness가 있으므로

```text
같은 Prompt
↓
Response A

같은 Prompt
↓
Response B

같은 Prompt
↓
Response C
```

와 같이 다양한 결과를 만들 수 있다.

---

# 32. Preference Learning과도 연결된다

앞 차시에서 하나의 Prompt에 대해 LLM이

```text
A
B
C
D
```

라는 여러 Response를 만드는 구조를 배웠다.

그것이 가능한 이유 중 하나가 이러한 **확률적 Decoding**이다.

---

# 33. 하지만 순수 Sampling도 문제가 있다

Probability가 매우 낮은 Token도 Probability가 `0`은 아닐 수 있다.

예:

```text
good      40%
nice      30%
bad       10%
???       0.001%
```

순수 Sampling에서는 이론적으로 `???`도 선택될 수 있다.

그 결과 문장 Quality가 갑자기 무너질 수 있다.

---

# 34. Sampling의 핵심 Trade-off

```text
Diversity ↑
```

를 얻고 싶지만

```text
Quality ↓
```

는 막아야 한다.

따라서 이후 Sampling Algorithm들은

> **낮은 Probability의 이상한 Token은 억제하면서 적당한 Randomness는 남기는 방법**

을 찾는다.

---

# 35. Temperature

첫 번째 Control 방법이 **Temperature**다.

Temperature는 Model의 Probability Distribution의 Sharpness를 조절한다.

---

# 36. Temperature = 1

```text
T = 1
```

이면 Model이 원래 계산한 Probability Distribution을 그대로 사용한다.

---

# 37. Temperature < 1

Temperature를 낮추면 Distribution이 더 **Sharp**해진다.

```text
High-probability Token
→ 더 높아짐

Low-probability Token
→ 더 낮아짐
```

즉 보수적인 Generation이 된다.

---

# 38. Temperature → 0

이론적으로 Temperature가 0에 가까워지면

```text
가장 높은 Token
→ 거의 Probability 1

나머지
→ 거의 0
```

이 된다.

따라서 Greedy Decoding에 가까워진다.

---

# 39. Temperature > 1

Temperature를 높이면 Distribution을 더 평평하게 만든다.

```text
높은 Probability Token
↓ 상대적으로 낮아지고

낮은 Probability Token
↑ 상대적으로 높아짐
```

따라서 더 다양한 Token이 선택될 수 있다.

---

# 40. Temperature → 매우 큰 값

Temperature를 계속 키우면 Distribution이 Uniform에 가까워진다.

즉 모든 Token이 비슷한 Probability를 가지게 된다.

그러면 Generation Randomness가 크게 증가한다.

---

# 41. Temperature 활용 직관

### 정답성이 중요한 Task

예:

- Math
    
- Factual QA
    
- Stable Output
    

```text
Temperature 낮게
```

사용하는 것이 자연스럽다.

### 다양성이 중요한 Task

예:

- Novel
    
- Creative Writing
    
- Brainstorming
    

```text
Temperature 높게
```

하여 더 다양한 표현을 탐색할 수 있다.

---

# 42. Temperature의 한계

Temperature는 전체 Probability Distribution의 형태를 조절한다.

하지만

```text
어떤 Token 후보까지 허용할 것인가?
```

를 직접 결정하는 것은 아니다.

또 Task에 따라 적절한 Temperature를 조정해야 하는 Hyperparameter 문제가 남는다.

---

# 43. Top-k Sampling

다음 방법은 **Top-k Sampling**이다.

핵심 아이디어는 단순하다.

> **Probability가 높은 상위 K개의 Token만 남기고 나머지는 제거한다.**

---

# 44. 예: Top-k = 6

Vocabulary 전체에서 Probability가 높은 상위 6개의 Token만 후보로 남긴다.

나머지는

```text
Probability = 0
```

으로 만든다.

그리고 남은 6개 Token 안에서 Sampling한다.

---

# 45. Top-k의 장점

순수 Random Sampling에서 발생하던

```text
극도로 Probability가 낮은
이상한 Token Sampling
```

가능성을 제거할 수 있다.

---

# 46. Top-k는 직관적이다

예:

```text
"상위 10개 Token에서만 고르자."
```

라는 식으로 이해하기 쉽다.

하지만 새로운 문제가 있다.

---

# 47. Top-k의 핵심 문제 — 고정된 K

Probability Distribution의 Shape는 매 Token Generation마다 다르다.

어떤 Step에서는

```text
Token 1 = 0.80
Token 2 = 0.10
Token 3 = 0.05
나머지 ≈ 매우 낮음
```

처럼 매우 Peaky할 수 있다.

이때 `k=10`은 너무 크다.

---

# 48. 반대로 Flat한 Distribution도 있다

다른 Step에서는

```text
Token 1 = 0.10
Token 2 = 0.09
Token 3 = 0.08
...
```

처럼 여러 Token이 비슷한 Probability를 가질 수 있다.

이때 `k=3`으로 고정하면 의미 있는 Candidate까지 버릴 수 있다.

---

# 49. 따라서 적절한 K는 Distribution에 따라 달라져야 한다

```text
Peaky Distribution
→ 작은 K 적절

Flat Distribution
→ 큰 K 필요
```

하지만 Top-k는 `K`가 항상 고정되어 있다.

이것이 단점이다.

---

# 50. 해결 — Top-p Sampling

고정된 Candidate 수를 정하지 말고

> **Probability Mass가 일정 수준 이상 될 때까지 Candidate를 선택하자.**

라는 아이디어가 나온다.

이것이 **Top-p Sampling**, 다른 이름으로 **Nucleus Sampling**이다.

---

# 51. Top-p의 핵심

Token을 Probability가 높은 순서로 정렬한다.

그리고 앞에서부터 Probability를 더한다.

예:

```text
0.40
+
0.25
= 0.65

+
0.15
= 0.80

+
0.12
= 0.92
```

`p=0.9`라고 설정했다면 누적 Probability가 처음으로 0.9 이상이 되는 지점까지 Candidate로 유지한다.

---

# 52. Top-p에서는 Candidate 개수가 자동으로 변한다

Distribution이 Peaky하다면

```text
2~3개 Token만으로
p=0.9 도달
```

할 수 있다.

Distribution이 Flat하다면

```text
10개 이상 필요
```

할 수도 있다.

즉

> **K를 직접 고정하는 대신 Distribution에 맞춰 Candidate 수를 동적으로 결정한다.**

---

# 53. Top-p의 직관적인 Hyperparameter

`p=0.9`라면

> **전체 Probability Mass의 약 90%를 설명하는 Candidate들을 사용한다.**

는 의미다.

강의에서는

```text
0.90
0.95
0.99
```

등이 Top-k의 임의적인 `k=640` 같은 값보다 사람이 해석하기 더 자연스러운 설정이라고 설명한다.

---

# 54. 강의에서 소개한 Top-p 결과

강의에서는 Nucleus Sampling 연구 결과에서 적절한 Probability Mass를 남겼을 때 Human Text와 유사한 Generation Pattern을 보였다고 설명한다.

또 Greedy와 Beam Search는 Human Generation Pattern과 상대적으로 다른 특성을 보였다는 실험도 소개한다.

---

# 55. Decoding Algorithm 전체 비교

|방법|핵심|장점|단점|
|---|---|---|---|
|Greedy|매 Step 최고 Probability|빠름, 단순|전체 최적 Sequence 보장 X|
|Beam Search|상위 K Sequence 유지|더 넓은 Search|Compute 증가|
|Random Sampling|Probability대로 Sampling|다양한 Output|낮은 Quality Token 가능|
|Temperature|Distribution Sharpness 조절|다양성 제어|Parameter 조정 필요|
|Top-k|상위 K Token만 Sampling|Low-probability 제거|고정 K|
|Top-p|누적 Probability p까지 Sampling|분포에 따라 Candidate 수 적응|p 설정 필요|

---

# 56. 강의에서 현대적 대표 방식으로 강조한 것

강의에서는 현재 일반적인 LLM Generation에서 대표적으로 사용하는 Sampling 방식으로 **Top-p Sampling**을 강조한다.

그리고 실제 Service/API에서는

- Temperature
    
- Max Tokens
    
- Top-p
    

등을 Generation Parameter로 설정할 수 있는 사례를 보여준다.

---

# 57. Top-p = 1의 의미

`p = 1`

이면 누적 Probability 100%를 포함해야 한다.

즉 사실상 전체 Vocabulary 후보를 허용하는 Sampling에 가까워진다.

---

# 58. 왜 같은 Prompt에 다른 Response가 나오는가?

Sampling 기반 Decoding에는 Randomness가 존재한다.

따라서

```text
같은 Model
+
같은 Prompt
+
같은 Hyperparameter
```

여도 Sampling 결과에 따라 다른 Token이 선택될 수 있다.

그 Token이 다음 Context를 바꾸고, 이후 모든 Generation Path도 달라진다.

---

# 59. 작은 Randomness가 전체 문장을 바꾼다

```text
Step 1

A 선택
vs
B 선택
```

이라는 작은 차이가 생기면

다음 Step의 Input Context 자체가 달라진다.

따라서

```text
A → C → F → ...
B → D → G → ...
```

처럼 전체 Response가 크게 달라질 수 있다.

---

# 60. 따라서 LLM Output은 본질적으로 확률적일 수 있다

사용자가

> “똑같이 물어봤는데 왜 답이 달라졌지?”

라고 느끼는 이유 중 하나가 이것이다.

Model 자체가 매번 바뀐 것이 아니라

```text
Probability Distribution
↓
Stochastic Decoding
```

과정에서 다른 Sample이 선택될 수 있기 때문이다.

---

# 61. 완전히 같은 결과가 필요하면?

강의에서는 Greedy Decoding과 같이 Deterministic한 선택 방식으로 가까이 갈 수 있다고 설명한다.

Temperature를 매우 낮게 두면 Sampling Distribution이 Greedy에 가까워진다.

---

# 62. Temperature 0과 Greedy를 엄밀히 동일시할 때 주의

강의에서는 일부 실제 Service에서는 User가 `temperature=0`을 입력해도 내부적으로 정확한 수학적 0을 사용하는 것이 아니라 작은 양수처럼 처리할 가능성이 있다고 추정하며, 따라서 미세한 Randomness가 남을 수 있다고 설명한다.

이는 **강의자의 구현 추정 설명**으로 기억하는 것이 적절하다.

---

# 63. 이제 Decoding에서 Prompt로

좋은 Response를 만드는 방법은 Decoding Algorithm을 조절하는 것만이 아니다.

같은 Model에 **어떤 Input을 넣는가**도 매우 중요하다.

이것이 **Prompt Engineering**으로 이어진다.

---

# 64. Prompt의 큰 구성 요소

강의에서는 Prompt를 크게

```text
Instruction
+
Examples
```

의 관점으로 본다.

### Instruction

무엇을 해야 하는지 알려준다.

### Example

어떤 식으로 수행해야 하는지 보여준다.

---

# 65. Prompt Engineering

Prompt Engineering은

> **Model Parameter를 변경하지 않고 추론 시 입력 Prompt를 설계·조정하여 더 원하는 품질의 Output을 얻는 방법**

이다.

```text
Model Training X

Prompt 수정 O
```

라는 것이 중요하다.

---

# 66. Prompt를 더 구체적으로 작성하면 Output이 달라진다

예를 들어 단순히

```text
"해리 포터 1권을 요약해 줘."
```

라고 요청하는 것과

```text
"해리 포터 1권의 핵심 사건을
시간 순서대로 다섯 줄의 Bullet Point로 요약해 줘."
```

라고 요청하는 것은 다르다.

Model은 뒤의 Prompt에서

- 내용
    
- 개수
    
- 형식
    
- 정렬 방법
    

등 더 많은 Constraint를 얻는다.

---

# 67. Prompt Engineering은 Inference Technique

Instruction Tuning:

```text
Training
→ Parameter 변화
```

Prompt Engineering:

```text
Inference
→ Parameter 변화 없음
```

이라는 차이를 명확하게 해야 한다.

---

# 68. System Prompt

사용자가 직접 입력하는 Prompt 외에도 상용 LLM에서는 **System Prompt**가 함께 입력될 수 있다.

System Prompt는

> **User Query와 별개로 Model에 기본적으로 제공되는 상위 수준의 Instruction**

으로 강의에서 설명한다.

---

# 69. System Prompt 구조

개념적으로

```text
[System Prompt]

너는 어떤 역할이다.
어떤 원칙을 따라라.
어떤 방식으로 대답하라.

[User Prompt]

실제 User의 질문
```

이 함께 Model Context에 들어간다.

---

# 70. System Prompt의 역할

System Prompt에는 예를 들어

- Model Role
    
- Response Style
    
- Safety Guideline
    
- 금지 사항
    
- 서비스 정책
    
- Persona
    

등을 넣을 수 있다.

---

# 71. User에게 보이지 않아도 Model은 볼 수 있다

상용 Service에서는 User가 화면에서 보는 Input 외에도 내부적으로 System Prompt가 함께 Model에 전달될 수 있다.

따라서 User Input만으로 Model의 행동 전체를 설명하기 어려울 수 있다.

---

# 72. Open Model과 Closed Model 차이

### 직접 운영하는 Open Model

System Prompt를 사용자가 자유롭게 설정할 수 있다.

### Closed Service

Provider가 정한 System Prompt가 존재할 수 있으며 일반 User가 이를 직접 수정할 수 없는 경우가 있다.

---

# 73. System Prompt는 Training을 대체하지 않는다

System Prompt 역시 결국 **Prompt**다.

즉 Model Parameter를 바꾸는 것이 아니다.

따라서

```text
System Prompt에 적었다.
=
Model이 항상 반드시 그대로 행동한다.
```

는 보장은 없다.

강의에서도 System Prompt가 항상 100% Output에 반영되는 것은 아니라고 설명한다.

---

# 74. System Prompt와 Service Design

강의에서는 System Prompt가 단순 기술 요소뿐 아니라

> **Model Provider가 AI와 User 사이의 Interaction을 어떤 방식으로 설계하고 싶은가**

를 반영할 수 있다고 설명한다.

즉 Product Policy와 Model Behavior를 연결하는 수단이 될 수 있다.

---

# 75. Persona도 System Prompt로 만들 수 있다

예를 들어

```text
너는 친절한 Tutor다.

너는 특정 Fiction Character다.

너는 Professional Coding Assistant다.
```

와 같은 Role을 System Prompt에 넣어 Model의 행동과 말투를 조정할 수 있다.

---

# 76. Personalization과 Context

강의에서는 User에 대한 Memory나 Profile 정보를 Context에 포함하여 보다 개인화된 Response를 만드는 사례도 설명한다.

구조적으로 보면

```text
System/User Context
+
Stored User Information
+
Current Query
      ↓
LLM
```

형태의 추가 Context 제공이라고 이해할 수 있다.

---

# 77. Prompt Engineering ② Chain-of-Thought

또 다른 중요한 Prompting Technique이 **Chain-of-Thought(CoT)** 다.

특히

- Math
    
- Logic
    
- Coding
    
- Reasoning
    

Task에서 중요하게 다룬다.

---

# 78. 일반 Few-shot Prompt

기존 Few-shot은

```text
Question 1
→ Answer 1

Question 2
→ Answer 2

New Question
→ ?
```

처럼 Question과 Final Answer만 보여준다.

---

# 79. Chain-of-Thought Prompt

CoT에서는

```text
Question 1
→ Intermediate Reasoning
→ Answer 1

Question 2
→ Intermediate Reasoning
→ Answer 2

New Question
→ Intermediate Reasoning
→ Answer
```

과 같이 **중간 풀이 과정의 Pattern**까지 Example에 포함한다.

---

# 80. CoT의 목적

단순히 답만 바로 생성하게 하는 대신

```text
Problem
↓
Intermediate Steps
↓
Final Answer
```

라는 Generation Pattern을 유도한다.

강의에서는 특히 수학과 코딩 같은 Reasoning Benchmark에서 CoT가 큰 성능 향상을 가져올 수 있다고 설명한다.

---

# 81. CoT 효과도 Model Scale과 연결

강의에서는 작은 Model에서는 CoT Prompting 효과가 약할 수 있지만 Model Scale이 증가하면서 효과가 크게 나타나는 결과를 소개한다.

이를 다시

```text
Reasoning
+
Scale
```

과 연결해 **Emergent Capability**의 사례로 설명한다.

---

# 82. Zero-shot Chain-of-Thought

CoT Example을 직접 여러 개 제공하지 않아도

```text
Let's think step by step.
```

같은 간단한 Instruction을 질문 뒤에 추가했을 때 중간 Reasoning 형태의 Generation을 유도할 수 있다는 연구가 소개된다.

이를 **Zero-shot CoT**라고 한다.

---

# 83. Few-shot CoT와 Zero-shot CoT 비교

### Few-shot CoT

```text
Reasoning Example 제공 O
```

### Zero-shot CoT

```text
Reasoning Example 제공 X
Instruction만 제공
```

예:

```text
Let's think step by step.
```

---

# 84. Example 자체도 Prompt 성능을 크게 바꾼다

Prompt가

```text
Instruction
+
Examples
```

로 구성된다면 당연히

> **어떤 Example을 선택하는가?**

도 중요한 문제가 된다.

---

# 85. 같은 Task Dataset의 Example도 성능 차이를 만들 수 있다

강의에서는 같은 Sentiment Dataset에서 가져온 Example들이라도 어떤 Example Set을 Few-shot Prompt에 넣었느냐에 따라 성능 편차가 크게 나타날 수 있다는 실험을 소개한다.

즉

```text
Task가 맞는 Example
```

이라고 해서 모두 똑같이 좋은 것은 아니다.

---

# 86. 좋은 Few-shot Example의 직관

강의에서 가장 기본적인 해결책은

> **현재 풀고 싶은 Query와 유사한 Example을 선택한다.**

는 것이다.

---

# 87. Similarity-based Example Selection

현재 Query가

`q`

라고 하자.

후보 Example 중

```text
q와 의미적으로 가까운 Example
```

을 찾아 Prompt에 넣는다.

개념적으로

```text
Current Query
      ↓
Similarity Search
      ↓
가장 유사한 Examples
      ↓
Few-shot Prompt
      ↓
LLM
```

이다.

---

# 88. 왜 Similar Example이 좋은가?

Model은 Prompt 안의 Example을 현재 Task를 푸는 Reference로 사용한다.

따라서 현재 Query와

- Semantic Pattern
    
- Problem Type
    
- Input Structure
    

가 유사한 Example이 더 직접적인 힌트를 제공할 가능성이 높다.

---

# 89. 강의에서 소개한 실험 결과

강의에서는 Query와 가까운 Example을 선택했을 때 상대적으로 먼 Example보다 큰 성능 차이가 나타난 사례를 설명한다.

후반부에서는 가까운 Example이 약 46%, 먼 Example이 약 31% 수준을 보인 사례를 언급하며 약 15%p 차이를 설명한다.

핵심은 정확한 수치를 외우는 것이 아니라

> **Few-shot Example Selection 자체가 In-context Learning 성능에 큰 영향을 줄 수 있다.**

는 것이다.

---

# 90. Example Quality도 중요하다

단순히 유사하기만 하면 충분하지 않다.

강의에서는

```text
현재 문제와 유사
+
Example 자체 Quality가 높음
```

이 중요하다고 설명한다.

---

# 91. Random Example Selection보다 안정적일 수 있다

Random Few-shot Example은 어떤 Sample이 선택됐는지에 따라 Performance가 흔들릴 수 있다.

Similarity-based Selection을 사용하면

```text
Performance ↑
+
Variance ↓
```

와 같이 보다 안정적인 성능을 얻을 수 있다는 흐름으로 설명한다.

---

# 92. Prompt Engineering을 다시 크게 정리

Prompt를 개선하는 방법은 단순히 문장을 예쁘게 쓰는 것이 아니다.

이번 강의에서는 적어도 다음 요소들이 등장한다.

```text
Prompt Engineering
│
├─ Instruction Design
│
├─ Output Format Specification
│
├─ System Prompt
│
├─ Persona
│
├─ Chain-of-Thought
│
├─ Zero-shot CoT
│
└─ Few-shot Example Selection
```

---

# 93. 최근의 Structured Prompt — Skill

강의 마지막에서는 기존 Prompt Engineering의 현대적인 확장 사례로 **Skill / SKILL.md 형태의 구조화된 Prompt**를 소개한다.

핵심은 완전히 새로운 원리가 아니다.

> **특정 Task를 잘 수행하도록 설계한 Prompt를 재사용·공유 가능한 구조로 정리한 것**

이라는 설명이다.

---

# 94. Skill에 들어갈 수 있는 정보

강의에서는 Skill 구조를 예를 들어

```text
Skill Name

Description

Instruction

Usage

Examples
```

등으로 설명한다.

즉 기존 Prompt에서 사용하던

```text
무엇을 해야 하는가
+
어떤 식으로 해야 하는가
+
Example
```

를 구조화한다.

---

# 95. 왜 구조화하는가?

Prompt가 User 개인의 일회성 문장으로만 존재하면 재사용하기 어렵다.

Skill 형태로 정리하면

```text
Task-specific Prompt
      ↓
Standardized Format
      ↓
Save
Share
Reuse
```

가 가능해진다.

---

# 96. Skill의 본질

강의에서는 Skill을 어렵게 생각하지 말고

> **잘 Engineering된 Task-specific Prompt를 구조화하고 공유 가능한 형태로 만든 것**

으로 이해하면 된다고 설명한다.

---

# 97. 여러 Skill을 Context에 넣을 수 있다

Agent 같은 System에서는 여러 Skill을 사용할 수 있다.

예:

```text
PDF Processing Skill

Coding Skill

Search Skill

Document Writing Skill
```

등을 Context에 제공해 두고 User Query에 따라 적절한 Instruction을 활용하도록 만들 수 있다.

---

# 98. Skill 선택의 직관

```text
User:
"이 PDF를 읽어서 정리해 줘."

      ↓

LLM:
현재 Query는 PDF 처리와 관련 있음

      ↓

PDF Skill의 Instruction 참조

      ↓

PDF 처리 Workflow 수행
```

와 같은 구조다.

---

# 99. Skill도 결국 Context다

가장 중요한 강의의 결론은

```text
System Prompt

User Prompt

Skill Instruction
```

모두 LLM 입장에서는 결국 **Context로 들어오는 Textual Instruction**이라는 점이다.

Skill이 Model Weight 자체를 바꾸는 것은 아니다.

---

# 100. Model Training과 Inference를 전체적으로 구분

## Training

```text
Data
↓
Loss
↓
Backpropagation
↓
Parameter Update
```

Model 자체를 바꾼다.

---

## Inference

```text
Prompt
↓
Forward Pass
↓
Probability Distribution
↓
Decoding
↓
Response
```

Parameter는 그대로 둔다.

---

# 101. Post-training과 Prompt Engineering 차이

### Post-training

```text
Instruction Tuning
RLHF
...
↓
Parameter 변경
```

### Prompt Engineering

```text
Instruction
System Prompt
CoT
Examples
Skill
↓
Parameter 변경 없음
```

이다.

# 102. Decoding과 Prompt Engineering 차이

둘 다 Inference 단계에서 사용하지만 조절하는 대상이 다르다.

### Prompt Engineering

```text
Model에 무엇을 입력할 것인가?
```

### Decoding

```text
Model이 만든 Probability Distribution에서
어떤 Token을 선택할 것인가?
```

# 104. 자주 헷갈리는 점 ① — LLM이 직접 다음 Token을 고르는가?

엄밀히 이번 강의의 구분에서는 아니다.

LLM은 **Probability Distribution을 계산**하고 Decoding Algorithm이 실제 Token을 선택한다.

---

# 105. 자주 헷갈리는 점 ② — LLM은 문장을 통째로 만든다?

아니다.

Autoregressive LLM은 기본적으로 Token을 하나씩 생성한다.

그리고 생성한 Token을 다시 다음 Step의 Input으로 사용한다.

---

# 106. 자주 헷갈리는 점 ③ — 생성 종료는 Model이 그냥 알아서 멈추는가?

실제로는 대표적으로

```text
EOS 생성
또는
Maximum Length 도달
```

과 같은 명시적인 종료 조건이 있다.

---

# 107. 자주 헷갈리는 점 ④ — Greedy는 항상 최고의 문장을 만드는가?

아니다.

매 Step에서의 Local Best를 선택할 뿐이고 전체 Sequence Probability가 가장 높은 Path를 보장하지 않는다.

---

# 108. 자주 헷갈리는 점 ⑤ — Beam Search는 Greedy보다 항상 좋은가?

더 많은 Candidate를 탐색할 수 있지만 계산 비용이 증가한다.

또 현대 Open-ended LLM Generation에서 Sampling 방식이 더 적합한 경우도 있다.

---

# 109. 자주 헷갈리는 점 ⑥ — Sampling은 아무 Token이나 동일한 확률로 뽑는가?

아니다.

기본 Random Sampling에서는 Model이 예측한 Probability Distribution에 따라 뽑는다.

Probability가 높은 Token일수록 선택 가능성이 높다.

---

# 110. 자주 헷갈리는 점 ⑦ — Temperature는 Model Parameter인가?

아니다.

Inference 시 Probability Distribution을 조절하는 **Decoding Hyperparameter**다.

Model Weight를 학습시키는 Parameter와 다르다.

---

# 111. 자주 헷갈리는 점 ⑧ — Temperature가 높으면 정확도가 좋아지는가?

그런 의미가 아니다.

일반적으로

```text
Temperature 낮음
→ 보수적 / 안정적

Temperature 높음
→ 다양성 / Randomness 증가
```

방향으로 이해한다.

---

# 112. 자주 헷갈리는 점 ⑨ — Top-k의 k는 K-fold의 k인가?

아니다.

여기서 `k`는

> **Sampling 후보로 남길 상위 Token 개수**

다.

---

# 113. 자주 헷갈리는 점 ⑩ — Top-p와 Top-k는 같은가?

아니다.

### Top-k

```text
Token 개수 고정
```

### Top-p

```text
누적 Probability 기준
→ Token 개수는 동적으로 변화
```

한다.

---

# 114. 자주 헷갈리는 점 ⑪ — Top-p = 0.9이면 상위 90%의 Token을 남기는가?

아니다.

**Token 개수의 90%**가 아니라

> **누적 Probability Mass가 약 90%에 도달할 때까지의 상위 Token 집합**

을 의미한다.

---

# 115. 자주 헷갈리는 점 ⑫ — 같은 Prompt인데 답이 바뀌면 Model이 학습된 것인가?

그렇지 않을 수 있다.

Sampling 기반 Decoding의 Randomness만으로도 동일한 Model이 서로 다른 Response를 생성할 수 있다.

---

# 116. 자주 헷갈리는 점 ⑬ — Prompt Engineering은 Fine-tuning인가?

아니다.

Prompt Engineering은 Inference 단계에서 Input을 조정한다.

Model Parameter를 Update하지 않는다.

---

# 117. 자주 헷갈리는 점 ⑭ — System Prompt와 User Prompt는 완전히 별개의 Model 입력인가?

역할과 우선순위는 다를 수 있지만 LLM 입장에서는 모두 Context를 구성하는 정보다.

강의의 핵심은 User에게 보이지 않는 추가 Instruction도 Model Input에 포함될 수 있다는 것이다.

---

# 118. 자주 헷갈리는 점 ⑮ — System Prompt를 쓰면 행동을 100% 강제할 수 있는가?

아니다.

System Prompt 역시 Textual Instruction이므로 반드시 완벽하게 준수된다고 보장할 수 없다.

---

# 119. 자주 헷갈리는 점 ⑯ — CoT는 Model을 다시 학습하는가?

Prompting 관점에서는 아니다.

Inference Prompt 안에 Intermediate Reasoning Pattern을 제공하거나 그러한 Generation을 유도한다.

---

# 120. 자주 헷갈리는 점 ⑰ — Zero-shot CoT는 Few-shot Example이 필요한가?

아니다.

강의에서는

```text
Let's think step by step.
```

같은 Instruction만 추가하는 방식의 Zero-shot CoT를 설명한다.

---

# 121. 자주 헷갈리는 점 ⑱ — Few-shot Example은 아무거나 같은 Task에서 뽑으면 되는가?

성능이 크게 달라질 수 있다.

강의에서는 현재 Query와 **유사하면서 Quality가 높은 Example**을 선택하는 것이 중요하다고 설명한다.

---

# 122. 자주 헷갈리는 점 ⑲ — Skill은 새로운 Neural Network Architecture인가?

아니다.

이번 강의의 설명에서는

> **특정 Task에 대해 구조화·재사용 가능한 Engineering Prompt**

에 가깝다.

# 127. 이번 강의에서 반드시 기억할 핵심

### 1. Autoregressive LLM은 Token을 하나씩 순차적으로 생성한다.

### 2. 직전에 생성한 Token은 다음 Step의 Input Context에 다시 들어간다.

### 3. LLM 자체는 다음 Token 하나가 아니라 Vocabulary에 대한 Probability Distribution을 출력한다.

### 4. Probability Distribution에서 실제 다음 Token을 선택하는 것이 Decoding Algorithm이다.

### 5. 따라서 실제 Token Generation은 `LLM + Decoding Algorithm`으로 완성된다.

### 6. Generation은 대표적으로 EOS가 생성되거나 Maximum Token Length에 도달하면 종료된다.

### 7. 실제 Library의 `generate()` 함수는 반복적인 Autoregressive Generation과 Decoding 과정을 내부적으로 수행한다.

### 8. Greedy Decoding은 현재 Step에서 가장 Probability가 높은 Token을 선택한다.

### 9. Greedy는 빠르고 간단하지만 Local Choice 때문에 전체적으로 가장 좋은 Sequence를 놓칠 수 있다.

### 10. Beam Search는 상위 K개의 Sequence Candidate를 계속 유지한다.

### 11. Beam Search는 Greedy보다 Search 범위가 넓지만 Beam Size에 따라 계산량이 증가한다.

### 12. Sampling은 Model Probability Distribution에서 확률적으로 Token을 선택한다.

### 13. Sampling은 다양한 Response를 만들 수 있지만 매우 낮은 Probability Token이 선택되어 Quality가 떨어질 수 있다.

### 14. Temperature는 Sampling Distribution의 Sharpness를 조절한다.

### 15. Temperature가 낮으면 높은 Probability Token에 더 집중한다.

### 16. Temperature가 높으면 Distribution이 평평해져 Generation Diversity가 증가한다.

### 17. Top-k는 상위 K개의 Token만 후보로 남긴다.

### 18. Top-k는 Low-probability Token을 제거하지만 고정된 K가 Distribution Shape에 적응하지 못한다.

### 19. Top-p는 Probability가 높은 Token부터 누적해 누적 Probability가 p 이상이 되는 후보군을 사용한다.

### 20. Top-p에서는 Distribution에 따라 Candidate Token 개수가 자동으로 달라진다.

### 21. 강의에서는 현대 LLM Generation의 대표적인 Sampling 방식으로 Top-p를 강조한다.

### 22. Sampling 기반 Decoding 때문에 동일 Prompt에서도 서로 다른 Response가 생성될 수 있다.

### 23. Prompt Engineering은 Parameter를 바꾸지 않고 Input Prompt를 설계하여 Output Quality를 개선하는 방법이다.

### 24. Prompt의 주요 구성 요소로 Instruction과 Example을 생각할 수 있다.

### 25. System Prompt는 User Query와 별개로 Model에 기본 제공되는 상위 수준의 Instruction이다.

### 26. System Prompt를 통해 Role, Policy, Persona, Response Style 등을 조정할 수 있다.

### 27. System Prompt도 결국 Prompt이므로 행동을 완벽하게 강제한다고 보장할 수는 없다.

### 28. CoT Prompting은 Final Answer뿐 아니라 Intermediate Reasoning Pattern을 생성하도록 유도한다.

### 29. 강의에서는 큰 Model일수록 CoT 효과가 강하게 나타나는 결과를 Emergent Capability와 연결한다.

### 30. Zero-shot CoT는 별도의 Reasoning Example 없이 간단한 Instruction으로 중간 추론을 유도한다.

### 31. Few-shot In-context Learning에서는 어떤 Example을 선택하느냐도 성능에 큰 영향을 준다.

### 32. 현재 Query와 의미적으로 유사하고 Quality가 높은 Example을 사용하는 것이 유리할 수 있다.

### 33. Skill은 강의에서 특정 Task용 Prompt를 이름·설명·Instruction·Example 등으로 구조화한 재사용 가능한 형태로 설명한다.

### 34. System Prompt, User Prompt, Example, Skill은 모두 결국 LLM Context를 구성하는 정보다.

# 129. 이번 강의의 핵심 한 문장

> **거대 언어 모델의 추론은 현재까지의 Token Sequence를 입력받아 다음 Token의 Probability Distribution을 계산하고, Greedy·Beam Search·Sampling·Top-k·Top-p 같은 Decoding Algorithm으로 실제 Token을 하나 선택한 뒤 이를 다시 Context에 추가하는 Autoregressive 과정을 EOS 또는 최대 길이에 도달할 때까지 반복하는 것이며, 실제 응답 품질은 Decoding뿐 아니라 System Prompt·Instruction·Chain-of-Thought·Few-shot Example Selection과 같은 Prompt Engineering에 의해서도 크게 달라진다.**

가장 짧게 기억하면 다음과 같다.

```text
LLM
= 다음 Token의 확률을 만든다.

Decoding
= 그중 실제 Token을 고른다.

Autoregressive Generation
= 고른 Token을 다시 넣고 반복한다.

Top-p
= 확률이 높은 후보부터
  누적 Probability p만큼 남겨 Sampling한다.

Prompt Engineering
= Model은 그대로 두고
  Input Context를 잘 설계한다.
```

그리고 Decoding 발전 순서는 다음 하나로 묶어두면 된다.

```text
Greedy
→ 빠르지만 Local

Beam
→ 후보를 여러 개 보지만 비쌈

Sampling
→ 다양하지만 불안정

Temperature
→ Randomness 조절

Top-k
→ 상위 K개만

Top-p
→ 누적 Probability 기준으로
  후보 수를 동적으로 결정
```
