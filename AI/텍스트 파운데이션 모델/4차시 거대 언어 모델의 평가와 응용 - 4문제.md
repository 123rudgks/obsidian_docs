# 1. 평가란 무엇인가?

LLM만의 이야기에 들어가기 전에 강의에서는 일반적인 **Evaluation**부터 정의한다.

평가란

> **우리가 만든 System, Code, Application, Model이 원래 의도한 목적에 맞게 잘 작동하는지를 확인하는 과정**

이다.

강의에서는 평가에 크게 세 가지 요소가 있다고 설명한다.

```text
Evaluation
├─ Goal
├─ Evaluation Method
└─ Evaluation Metric
```

---

# 2. Goal

먼저

> **이 System으로 무엇을 달성하고 싶은가?**

를 정의한다.

목표가 무엇인지 모르는데

```text
좋다
나쁘다
```

를 평가할 수는 없다.

---

# 3. Evaluation Method

두 번째는

> **어떤 방법으로 그 목표 달성 정도를 확인할 것인가?**

다.

예를 들어 배달 Application의 목표가

```text
음식을 User에게 잘 전달한다.
```

라고 하자.

평가 방법으로

```text
배달 시간을 측정
```

할 수 있다.

---

# 4. Evaluation Metric

마지막으로 실제 결과를 숫자 또는 일정한 기준으로 표현할 Metric이 필요하다.

배달시간이라면

```text
평균 배달시간
```

을 Metric으로 사용할 수 있다.

즉

```text
Goal
→ 무엇을 잘해야 하는가?

Method
→ 어떻게 측정할 것인가?

Metric
→ 그 결과를 어떤 값으로 표현할 것인가?
```

로 구분한다.

---

# 5. 일반적인 AI 평가

Machine Learning Model의 전형적인 평가는 **Test Data**를 사용한다.

조건은 다음과 같다.

```text
Training에는 사용하지 않은 Data

하지만
Ground Truth는 알고 있는 Data
```

다.

Model에게 Test Input을 넣고

```text
Prediction
vs
Ground Truth
```

를 비교한다.

---

# 6. 감성 분류 예

Goal:

```text
입력 Text의 감정을 정확히 분류
```

Evaluation Method:

```text
Model Prediction
vs
Human-labelled Ground Truth
```

Evaluation Metric:

```text
Accuracy
```

예를 들어 100개 중 70개를 맞혔다면

```text
Accuracy = 70%
```

라고 평가할 수 있다.

---

# 7. 그런데 Foundation Model 평가가 어려운 이유

기존 AI Model은 일반적으로 특정 Task를 위해 만들어졌다.

예:

```text
Sentiment Model
→ Sentiment Dataset으로 평가

Image Classification Model
→ Classification Dataset으로 평가
```

하지만 Foundation Model은 다르다.

Foundation Model은

- Math
    
- Coding
    
- Translation
    
- Summarization
    
- Reasoning
    
- QA
    
- Classification
    
- Writing
    

등 매우 많은 Task를 수행한다.

따라서

> **특정 Benchmark 하나만 잘한다고 전체 LLM이 좋다고 말하기 어렵다.**

---

# 8. 그래서 LLM은 여러 Task를 동시에 평가한다

LLM Evaluation에서는 일반적으로 여러 Benchmark를 함께 사용한다.

```text
Benchmark A
Benchmark B
Benchmark C
Benchmark D
...
```

그리고 각 Benchmark에서의 Performance를 종합적으로 본다.

강의에서는 GPT-4 같은 Model의 평가표에서도 여러 서로 다른 Task를 동시에 비교했다고 설명한다.

최근 Model의 Technical Report에서는 수십 개에서 매우 많은 Benchmark 결과를 함께 제공하는 경우도 있다고 설명한다.

---

# 9. LLM 평가가 더 어려운 이유 — Evaluation Setting

LLM의 Output은 단순히 Model Weight만으로 결정되지 않는다.

앞 차시에서 배웠듯이

```text
Model
+
Prompt
+
Decoding Algorithm
```

의 영향을 받는다.

따라서 동일 Benchmark에서도

```text
Zero-shot

Few-shot

Chain-of-Thought

Temperature

Decoding Setting
```

등이 다르면 결과가 달라진다.

---

# 10. Fair Comparison이 어렵다

예를 들어 동일한 수학 Benchmark에서

```text
Model A
→ 5-shot

Model B
→ 다른 Setting

Model C
→ 5-shot + Chain-of-Thought
```

로 평가했다고 하자.

Score만 보고

```text
Model C > Model A
```

라고 단순 비교하기 어렵다.

왜냐하면

```text
Model 차이
```

뿐 아니라

```text
Prompting / Evaluation Method 차이
```

가 섞여 있기 때문이다.

강의에서는 GSM8K 예를 통해 이 문제를 설명한다.

---

# 11. LLM 평가에서는 세 요소를 같이 봐야 한다

따라서 평가 결과를 볼 때

```text
1. 어떤 Task인가?

2. 어떤 Evaluation Method인가?

3. 어떤 Evaluation Metric인가?
```

를 동시에 확인해야 한다.

Benchmark Score 숫자 하나만 보면 안 된다.

---

# 12. Task에 따라 Metric도 다르다

예를 들어

```text
Task A
→ Accuracy

Task B
→ F1 Score

Task C
→ 다른 Metric
```

을 사용할 수 있다.

즉 모든 LLM Task를 하나의 Metric으로 평가할 수 있는 것도 아니다.

---

# 13. 정답이 명확한 Task

먼저 상대적으로 평가가 쉬운 경우다.

예:

- Multiple-choice Question
    
- Math Problem
    
- Classification
    

등이다.

---

# 14. MMLU

강의에서는 오랫동안 대표적으로 사용된 LLM Benchmark 중 하나로 **MMLU**를 소개한다.

MMLU는 다양한 전문 영역에 대한 Multiple-choice 문제로 구성된다.

강의에서는 약

```text
57개 전문 분야
```

의 문제를 포함한다고 설명한다.

---

# 15. Multiple-choice는 평가가 쉽다

정답이

```text
D
```

인데 Model이

```text
D
```

를 선택했다면

```text
1
```

틀렸다면

```text
0
```

으로 평가할 수 있다.

많은 문제에 대해 평균을 내면 Accuracy를 계산할 수 있다.

---

# 16. 하지만 자연어 생성에는 정답이 하나가 아니다

문제는 다음과 같은 Task다.

```text
Translation

Summarization

Story Generation

Creative Writing
```

예를 들어 같은 문장을 번역해도

```text
Translation A
Translation B
```

가 모두 올바를 수 있다.

---

# 17. Summarization도 정답 하나가 아니다

어떤 책을 다섯 문장으로 요약한다고 하자.

GPT가 만든 Summary와 다른 Model이 만든 Summary가 다르더라도

```text
어느 하나가 반드시 틀린 것
```

이라고 말하기 어렵다.

사람마다

- 무엇을 중요하게 보는지
    
- 어떤 Style을 선호하는지
    
- 얼마나 자세한 Summary를 원하는지
    

도 다르다.

---

# 18. Open-ended Generation 평가가 어려운 이유

즉 Open-ended Generation에서는

```text
Predicted Label
vs
Correct Label
```

처럼 단순한 비교가 어렵다.

그래서 여러 Evaluation 방법이 발전해 왔다.

---

# 19. 방법 ① Human Reference를 만든다

가장 단순한 방법은 사람이 **Reference Answer**를 만드는 것이다.

예:

```text
Input
↓
Human Expert
↓
Reference Translation
```

그리고

```text
Model Output
vs
Reference
```

가 얼마나 비슷한지를 측정한다.

---

# 20. Reference-based Evaluation

구조는 다음과 같다.

```text
Question / Input
      ↓
Model Output

Human Reference
      ↓

Output ↔ Reference
Similarity 측정
```

즉 정답이 원래 명확하지 않더라도 임의의 모범 답안을 하나 만들어 비교 기준으로 사용한다.

---

# 21. Word-level Overlap

가장 단순한 방법 중 하나는

> **Model Output과 Reference가 얼마나 많은 단어 또는 구문을 공유하는가?**

를 측정하는 것이다.

---

# 22. ROUGE

강의에서는 대표적인 Word-level Overlap Metric으로 **ROUGE Score**를 소개한다.

개념적으로

```text
Reference:
The cat is on the mat.

Model:
The cat sat on the mat.
```

처럼 서로 겹치는 Word/Sequence가 많다면 높은 유사도를 줄 수 있다.

---

# 23. Word Overlap의 한계

두 문장이 의미적으로는 같아도 서로 다른 표현을 사용할 수 있다.

예:

```text
자동차

차량
```

또는

```text
크다

거대하다
```

처럼 Semantic Meaning은 유사하지만 Surface Word는 다를 수 있다.

단순 Word Overlap은 이러한 의미 관계를 제대로 반영하지 못한다.

---

# 24. Context 문제도 있다

`Apple`이라는 단어는

```text
사과
```

일 수도 있고

```text
회사
```

일 수도 있다.

Word 자체만 비교하면 이러한 Contextual Meaning을 충분히 반영하기 어렵다.

---

# 25. 해결 — Sentence를 Vector로 표현

Text를 단순 문자열로 비교하지 않고

```text
Sentence
↓
Embedding Model
↓
Vector
```

로 변환한다.

그리고 Vector Space에서 두 Sentence가 얼마나 가까운지를 측정한다.

---

# 26. Cosine Similarity

강의에서는 대표적으로 **Cosine Similarity**를 사용한다고 설명한다.

두 Vector의 방향이 얼마나 유사한지를 보는 방식이다.

강의의 설명에서는

```text
1
→ 매우 유사

0
→ 관련성이 적음

-1
→ 반대 방향
```

으로 직관을 설명한다.

---

# 27. Semantic Similarity

따라서

```text
Word Overlap
```

보다

```text
Embedding Similarity
```

를 사용하면 서로 다른 표현이라도 의미적으로 유사한 문장을 더 잘 비교할 수 있다.

---

# 28. 이 Embedding Model도 별도로 필요하다

두 Text를 의미 공간에서 잘 비교하려면

```text
문장 의미를 잘 표현하는
Embedding Model
```

이 필요하다.

즉 Evaluation 자체를 위해 또 다른 Model을 사용할 수 있다.

---

# 29. Reference가 없는 경우

하지만 항상 사람이 Reference Answer를 만들 수 있는 것도 아니다.

예:

```text
새로운 Story 생성

Creative Writing

Open-ended Dialogue
```

등은 Reference 자체를 정의하기 어렵다.

이때 다른 방식이 필요하다.

---

# 30. 방법 ② Text 자체의 Quality 측정

Reference 없이 Output 자체가 얼마나 자연스러운지를 평가할 수 있다.

대표적으로 강의에서는 **Perplexity(PPL)** 를 설명한다.

---

# 31. Perplexity

Perplexity는 Language Model 관점에서

> **이 문장이 얼마나 확률적으로 자연스러운가?**

를 보는 Metric이다.

즉 문장을 Token별로 읽으면서

```text
이 다음 Token이
얼마나 자연스러운 Probability를 가지는가?
```

를 확인한다.

---

# 32. Language Modeling과 연결

LLM 자체를 Pre-training할 때

```text
Next-token Prediction
```

을 했다.

Perplexity 역시 Next-token Probability를 기반으로 계산된다.

따라서

```text
Language Model Training Objective
↔
Perplexity
```

는 직접 연결된다.

---

# 33. Perplexity가 낮다는 의미

일반적으로

```text
Perplexity 낮음
→ Model이 해당 Text를
   더 자연스럽고 예측 가능하게 봄
```

으로 이해한다.

---

# 34. 하지만 자연스러움 = 좋은 Response는 아니다

문법적으로 매우 자연스럽다고 해서

- 창의적
    
- 사실에 맞음
    
- 유용함
    
- 재미있음
    
- 논리적
    

이라는 보장은 없다.

---

# 35. Creativity를 어떻게 숫자로 만들까?

예를 들어 Creativity를 평가하고 싶다고 하자.

간단히

```text
사용한 Word 종류 수 ↑
→ Creativity ↑
```

라고 정의할 수도 있다.

하지만 다양한 Word를 사용했다고 해서 반드시 창의적인 것은 아니다.

---

# 36. Hand-crafted Metric의 어려움

Quality라는 개념은

```text
Fluency
Creativity
Coherence
Helpfulness
Correctness
Style
Safety
```

등 매우 많은 요소를 포함할 수 있다.

각 요소를 정확한 Mathematical Metric으로 정의하는 것은 매우 어렵다.

---

# 37. 과거의 해결책 — Human Expert Evaluation

그래서 과거에는 결국 사람에게 평가를 맡겼다.

```text
Model Output
↓
Human Expert
↓
1~5 Score
```

또는 여러 Output을 Ranking한다.

---

# 38. Human Evaluation의 장점

사람은

- 문맥
    
- 자연스러움
    
- 논리
    
- 창의성
    
- 의미
    

같은 복잡한 요소를 종합적으로 판단할 수 있다.

---

# 39. Human Evaluation의 단점

문제는

```text
비용
+
시간
+
Scale
```

이다.

수백만 개 Response를 사람이 일일이 평가할 수는 없다.

---

# 40. 자연스럽게 등장하는 질문

> **“LLM 자체가 이미 전문가 수준의 Text 판단 능력을 가졌다면 LLM에게 평가를 맡기면 안 될까?”**

이 질문에서 **LLM-as-a-Judge**로 넘어간다.

---

# 41. LLM-as-a-Judge

의미 그대로

> **LLM을 평가자(Judge)로 사용한다.**

는 방법이다.

```text
Question
+
Model Response
+
Evaluation Criteria
      ↓
Judge LLM
      ↓
Score
+
Reason
```

형태다.

---

# 42. 아무 기준 없이 “평가해 줘”라고 하면 안 된다

Evaluation에는 Goal과 Criteria가 필요했다.

따라서 Judge LLM에게도

```text
무엇을 평가할 것인지

어떤 기준으로 평가할 것인지

몇 점 범위를 사용할 것인지
```

를 Prompt로 제공한다.

---

# 43. 예: Summary Evaluation

예를 들어 Summary의 Coherence를 평가한다면

```text
다음 Summary를
Coherence 기준으로
1~5점으로 평가하라.

그리고
왜 그렇게 평가했는지 설명하라.
```

같은 Prompt를 줄 수 있다.

---

# 44. LLM Judge의 Output

Judge LLM은

```text
Score: 4

Reason:
...
```

처럼 정량 Score와 자연어 Explanation을 동시에 만들 수 있다.

---

# 45. G-Eval

강의에서는 이러한 LLM 기반 Evaluation의 대표적인 연구로 **G-Eval**을 소개한다.

핵심은 LLM에게 구체적인 Evaluation Criteria를 제공하고 Natural Language Generation Output을 평가하게 하는 것이다.

---

# 46. 정말 사람과 비슷하게 평가하는가?

가장 중요한 검증은

```text
LLM Judge Score
```

가

```text
Human Evaluation Score
```

와 얼마나 비슷한가다.

강의에서는 여러 Evaluation Metric과 Human Score의 Correlation을 비교한 연구를 소개한다.

---

# 47. 큰 LLM은 Human Evaluation과 높은 상관을 보였다

강의에서는 GPT-4급 Model을 Judge로 사용했을 때 기존 자동 Evaluation Metric보다 Human Evaluation과 더 높은 Correlation을 보인 사례를 설명한다.

즉 강한 LLM에서는

```text
Human Judgment
≈
LLM Judgment
```

이 어느 정도 가능해졌다는 흐름이다.

---

# 48. 따라서 LLM을 평가할 때 LLM을 사용한다

이제 구조가 조금 특이해진다.

```text
LLM A
→ Response 생성

LLM B
→ Response 평가
```

즉 AI가 AI를 평가한다.

---

# 49. LLM Judge의 활용은 Evaluation에만 그치지 않는다

강의에서는 이미 **Training Data Filtering**에서도 LLM 기반 평가가 사용된다고 설명한다.

Internet Data가 있다고 하자.

```text
Web Page
↓
Quality Judge
↓
1~5 Score
```

를 계산한다.

Quality가 낮은 Data를 제거하고 높은 Data만 Training에 사용한다.

---

# 50. 왜 Data Filtering이 중요한가?

Foundation Model Training에서는

```text
Data Quantity
```

뿐 아니라

```text
Data Quality
```

도 중요하다.

따라서 LLM을 사용해

```text
이 Text는 교육적으로 좋은가?

정보가 충분한가?

Noise인가?

고품질 문서인가?
```

등을 자동 평가할 수 있다.

---

# 51. LLM이 다음 세대 Model의 Data를 만든다

강의에서는 다음과 같은 순환 구조를 설명한다.

```text
Model A
↓
Data Evaluation / Filtering
↓
더 좋은 Training Data
↓
Model B Training
↓
더 강한 Model B
```

즉 이전 세대 LLM이 다음 세대 LLM의 Training Pipeline에 사용될 수 있다.

---

# 52. 단일 Response Score 외에 Pairwise Comparison도 있다

Response를

```text
1~5점
```

으로 평가하는 것 외에도

```text
Response A
vs
Response B
```

중 어떤 것이 더 좋은지 비교할 수 있다.

앞 강의에서 Preference Learning에서도 같은 구조를 봤다.

---

# 53. Human Preference Evaluation

예:

```text
Question
      ↓
Model A Response

Model B Response
      ↓
Human
      ↓
A가 더 좋다
B가 더 좋다
Tie
둘 다 나쁘다
```

와 같은 Evaluation이 가능하다.

---

# 54. LLM Arena

강의에서는 대표적인 Human Pairwise Benchmark로 **LLM Arena** 계열 방식을 소개한다.

User에게 Model 이름을 숨긴 상태로 두 Response를 보여준다.

즉 **Blind Evaluation**을 한다.

---

# 55. 왜 Model 이름을 숨기는가?

사용자가

```text
GPT니까 더 좋겠지.

Claude니까 더 좋겠지.
```

처럼 Brand Reputation에 영향을 받지 않도록 하기 위해서다.

---

# 56. Arena 구조

```text
User Query
      ↓
Anonymous Model A
Anonymous Model B
      ↓
Response A
Response B
      ↓
User Vote
```

한다.

Vote 이후 어떤 Model이었는지 공개할 수 있다.

---

# 57. Pairwise 결과를 Ranking으로 변환

Model A가 Model B를 여러 번 이긴 결과를 이용해 상대적인 Rating을 계산한다.

강의에서는 Chess나 Go 등에 사용되는 **Elo Rating**과 유사한 방식으로 설명한다.

```text
많이 이긴 Model
→ Rating ↑

많이 진 Model
→ Rating ↓
```

---

# 58. Human Arena의 장점

실제 User가

```text
어떤 Answer를 더 좋아하는가?
```

를 직접 평가한다.

따라서 실제 사용 만족도를 반영하는 매우 중요한 Benchmark가 될 수 있다.

---

# 59. Human Arena의 문제

하지만 Vote가 쌓이는 데 시간이 걸린다.

신규 Model이 나올 때마다

```text
수많은 Human Vote
```

가 충분히 모일 때까지 기다려야 한다.

즉 빠른 Evaluation이 어렵다.

---

# 60. 그래서 Pairwise Evaluation도 LLM에게 맡긴다

Human 대신 Judge LLM에게

```text
Question

Response A

Response B

Evaluation Criteria
```

를 제공한다.

그리고

```text
A가 더 좋다

B가 더 좋다
```

를 결정하도록 한다.

이 방식은 매우 빠르게 많은 Comparison을 만들 수 있다.

---

# 61. 하지만 LLM-as-a-Judge도 완벽하지 않다

Judge 역시 LLM이다.

따라서 자신의 Model Bias와 Generation Bias를 가지고 있다.

강의에서는 대표적으로 세 가지 문제를 설명한다.

```text
1. Position Bias

2. Length Bias

3. Self-preference Bias
```

---

# 62. Position Bias

같은 두 Response를

```text
A = Response 1
B = Response 2
```

로 넣었을 때 A를 선택했다고 하자.

그런데 순서를 바꾸어

```text
A = Response 2
B = Response 1
```

로 입력했는데도 또 A를 선택한다면

```text
Content
```

보다

```text
Position
```

에 영향을 받고 있을 가능성이 있다.

---

# 63. Position Bias의 해결 아이디어

비교 순서를 바꿔 두 번 평가할 수 있다.

```text
Run 1
A vs B

Run 2
B vs A
```

그리고 결과를 종합한다.

비용은 증가하지만 위치의 영향을 줄일 수 있다.

---

# 64. Length Bias

LLM Judge가

```text
긴 Answer
```

를

```text
짧은 Answer
```

보다 더 좋은 Answer라고 평가하는 경향이 있을 수 있다.

---

# 65. 긴 답이 항상 좋은 것은 아니다

같은 내용을 불필요하게 반복하여 Answer Length만 늘렸다고 하자.

실제 Quality는 오히려 떨어질 수 있다.

하지만 Judge가

> “내용이 더 많아 보인다.”

고 판단하여 높은 Score를 줄 수 있다.

---

# 66. Length Bias 보완

강의에서는 Statistical Method 등을 이용해 Length가 Score에 미치는 영향을 보정하는 방법이 존재한다고 설명한다.

즉

```text
Raw Judge Score
```

에서

```text
Length Effect
```

를 제거하려는 것이다.

---

# 67. Self-preference Bias

더 흥미로운 문제는

> **Judge가 자신과 같은 Model Family가 생성한 Response를 더 선호할 수 있다.**

는 것이다.

예를 들어 강의에서는

```text
GPT Judge
→ GPT Response를 상대적으로 선호

Claude Judge
→ Claude Response를 상대적으로 선호
```

하는 사례를 설명한다.

---

# 68. Self-preference는 더 어려운 문제

Position Bias처럼 단순히 순서만 바꾸면 해결되는 문제가 아니다.

Judge Model 자체의

- Style
    
- Preference
    
- Training Distribution
    

과 연결되어 있을 가능성이 있기 때문이다.

---

# 69. Evaluation Bias의 핵심 교훈

> **LLM Judge Score도 절대적인 정답은 아니다.**

따라서 평가할 때

```text
Human Evaluation

Automatic Metric

LLM Judge

Multiple Judges

Bias Correction
```

등을 조합할 수 있다.

---

# 70. LLM 평가 전체 구조

```text
LLM Evaluation
│
├─ 정답이 명확
│    ├─ Accuracy
│    ├─ F1
│    └─ Benchmark
│
└─ Open-ended Generation
     │
     ├─ Reference 있음
     │    ├─ ROUGE / Overlap
     │    └─ Embedding Similarity
     │
     ├─ Reference 없음
     │    ├─ Perplexity
     │    └─ Hand-crafted Metric
     │
     ├─ Human Evaluation
     │
     └─ LLM-as-a-Judge
          ├─ Score
          ├─ Pairwise
          └─ Bias 문제
```

---

# 71. 이제 LLM의 응용

평가를 다룬 뒤 강의에서는 LLM이 실제로 어떻게 확장되고 활용되는지를 살펴본다.

첫 번째는 **Multimodal Foundation Model**이다.

---

# 72. Text-only에서 Multimodal로

초기 LLM은 주로

```text
Text Input
→ Text Output
```

에 집중했다.

최근 Foundation Model은

```text
Text
Image
Audio
Video
```

등 여러 Modality를 처리하는 방향으로 확장된다.

---

# 73. Multimodal이 되어도 Language Model이 중요한 이유

강의에서 중요한 관점이다.

많은 Multimodal Foundation Model은 완전히 새로운 Backbone을 만드는 대신

> **이미 강력하게 학습된 Language Model을 중심으로 다른 Modality를 이해할 수 있도록 확장한다.**

고 설명한다.

---

# 74. Image를 LLM이 어떻게 보는가?

LLM은 원래 Text도 실제 문자열 그대로 보는 것이 아니다.

Text를

```text
Token
↓
Embedding Vector
```

로 바꾸어 본다.

그렇다면 Image도

```text
Image
↓
Visual Encoder
↓
Vector
```

로 만들 수 있다.

---

# 75. Image Vector를 LLM Space에 맞춘다

Image Encoder가 만든 Vector를 그대로 LLM이 이해하지 못할 수도 있다.

따라서

```text
Image
↓
Visual Representation
↓
Projection / Adapter
↓
LLM이 이해할 수 있는 Representation
```

으로 변환한다.

---

# 76. 핵심은 Image를 자연어 문장으로 번역하는 것이 아니다

매우 중요한 구분이다.

```text
Image
→ "사람이 택시 옆에 있다."
```

처럼 먼저 Caption Text로 변환한 뒤 LLM에 넣는 것만을 의미하지 않는다.

강의의 핵심 설명은

> **Image 자체를 Vector Representation으로 만들고, 학습을 통해 그 Vector를 LLM이 처리할 수 있는 Representation Space와 연결한다.**

는 것이다.

---

# 77. 다른 Modality도 같은 원리

Image뿐 아니라

```text
Audio
Video
```

등도

```text
Raw Modality
↓
Representation / Tokenization
↓
LLM-compatible Vector
```

로 만들어 처리할 수 있다.

강의에서는 이를 넓은 의미의 Modality Tokenization 관점으로 설명한다.

---

# 78. Multimodal Model의 Backbone

따라서 강의의 관점에서는

```text
Strong LLM
+
Modality Encoder / Adapter
```

를 결합해 Multimodal Foundation Model을 만들 수 있다.

즉 여전히 LLM이 중요한 Backbone 역할을 한다.

---

# 79. Multimodal Input과 Output

이렇게 확장하면

```text
Image
→ Text 설명

Image + Text
→ Answer

Audio
→ Text / Audio

Video
→ Understanding
```

등 다양한 Task를 수행할 수 있다.

---

# 80. Physical AI로의 확장

강의에서는 이 구조를 Robot까지 연결한다.

Robot은

```text
Vision
```

을 통해 Environment를 보고,

그 상황에서

```text
어떤 행동을 해야 하는가?
```

를 결정해야 한다.

---

# 81. Vision-Language-Action Model

강의에서는 이를 **VLA(Vision-Language-Action) Model**의 형태로 설명한다.

```text
Vision
+
Language Instruction
      ↓
Foundation Model
      ↓
Action
```

이다.

---

# 82. Text Output에서 Action Output으로

일반 LLM:

```text
Context
→ Text Token
```

Robot Foundation Model:

```text
Visual Context
+
Language Context
→ Robot Action
```

로 Output Space까지 확장한다.

---

# 83. 예: Humanoid Robot

Robot이

```text
물체를 본다.
↓
무엇인지 판단한다.
↓
어디로 옮겨야 하는지 판단한다.
↓
잡는다.
↓
다른 Robot에게 전달한다.
↓
냉장고에 넣는다.
```

같은 일련의 행동을 할 수 있다.

강의에서는 이러한 Physical AI에서도 Language Model 기반 Foundation Architecture가 활용되는 흐름을 설명한다.

---

# 84. Foundation Model 발전의 큰 방향

```text
Text
      ↓
Image + Text
      ↓
Audio + Video
      ↓
Action / Robotics
```

로 Input과 Output Modality가 점점 확장된다.

---

# 85. 두 번째 응용 — LLM이 Training Data를 만든다

LLM은 Response만 만드는 것이 아니다.

**다른 AI를 학습시키기 위한 Training Data**도 만들 수 있다.

---

# 86. Synthetic Data

사람이 직접 만든 Data가 아니라 Model이 생성한 Data를 **Synthetic Data**라고 볼 수 있다.

예:

```text
Human Seed Examples
      ↓
LLM
      ↓
새로운 Instructions
+
Responses
      ↓
Training Dataset
```

이다.

---

# 87. 왜 Synthetic Data가 필요한가?

Instruction Tuning Dataset을 사람이 전부 작성하려면 비용이 매우 크다.

따라서 작은 수의 Human-written Example을 기반으로 LLM이 많은 Training Sample을 생성하게 할 수 있다.

---

# 88. Self-Instruct 계열의 직관

강의에서는 사람이 작성한 약 175개의 Seed Example을 시작점으로 LLM을 이용해 약 52,000개의 Instruction Data를 생성한 연구 흐름을 소개한다.

핵심은 숫자보다

```text
작은 Human Seed
↓
LLM Generation
↓
큰 Instruction Dataset
```

이다.

---

# 89. 생성만 하면 끝나는 것은 아니다

Synthetic Data에는

- Duplicate
    
- Low-quality
    
- Unrealistic Sample
    
- Noise
    

가 있을 수 있다.

따라서 Filtering이 필요하다.

---

# 90. Diversity Filtering

생성 Data끼리 너무 비슷하면 중복을 제거한다.

```text
Sample A
≈
Sample B
```

라면 하나를 제거할 수 있다.

---

# 91. 지나치게 이상한 Data도 제거

기존 Data와 너무 멀리 떨어져 있거나 실제 Task Data로 보기 어려운 Sample도 제거할 수 있다.

즉

```text
너무 비슷해도 제거
너무 이상해도 제거
```

하면서 적절한 Diversity와 Quality를 유지한다.

---

# 92. Synthetic Data도 실제 Training에 도움을 줄 수 있다

강의에서는 생성한 Instruction Data로 GPT-3를 Fine-tuning했을 때 Pre-training Model보다 큰 성능 향상이 있었으며 Human Instruction Data 기반 Training과 비교해도 상당한 효과가 나타났다고 설명한다.

또 다른 Instruction Data와 합치면 추가적인 성능 향상도 관찰되었다고 설명한다.

---

# 93. Alpaca

강의에서는 Llama가 공개된 뒤 Stanford의 **Alpaca** Model이 이러한 Synthetic Instruction Data Generation 방식을 활용해 만들어진 사례를 소개한다.

핵심은

```text
Open Base Model
+
LLM-generated Instruction Data
+
Fine-tuning
```

으로 Instruction-following Model을 빠르게 만들 수 있다는 점이다.

---

# 94. Synthetic Data도 LLM으로 다시 평가할 수 있다

Generation:

```text
LLM
→ Synthetic Data 생성
```

그다음

```text
Judge LLM
→ Data Quality 평가
```

를 할 수 있다.

---

# 95. High-quality Data만 선택

강의에서는 생성 Data 전체를 사용하는 것보다 높은 Quality Score를 받은 일부 Data만 사용했을 때 더 좋은 Training 결과가 나타난 연구 사례도 설명한다.

즉

```text
Quantity
```

보다

```text
Quality
```

가 더 중요할 수도 있다.

---

# 96. LLM이 Data Pipeline 전체에 들어간다

이제

```text
LLM
↓
Data Generation
↓
LLM
↓
Data Evaluation / Filtering
↓
Training
↓
새로운 LLM
```

이라는 Pipeline이 가능하다.

---

# 97. 하지만 Synthetic Data에는 위험도 있다

Model-generated Data를 계속 재활용하면

- Noise
    
- Bias
    
- Error
    

가 반복되거나 증폭될 가능성을 생각할 수 있다.

따라서 강의에서도 Quality Filtering의 중요성을 강조한다.

---

# 98. 결국 High-quality Domain Data가 중요하다

강의 후반에서 중요한 실무적 관점을 제시한다.

어떤 회사만이 가지고 있는

- Internal Workflow
    
- Customer Data
    
- Domain Knowledge
    
- 실제 문제 사례
    
- High-quality Annotation
    

같은 Data는 외부 Foundation Model Provider가 쉽게 얻을 수 없다.

---

# 99. 기업의 중요한 자산 — High-quality Proprietary Data

Foundation Model 자체는 점점 범용화되고 공개 Model도 발전한다.

하지만

> **“우리 회사가 실제로 풀어야 하는 문제를 정확하게 표현하는 고품질 Data”**

는 회사 내부에만 존재할 수 있다.

따라서 강의에서는 향후 중요한 경쟁력 중 하나로 **High-quality Data 구축 능력**을 강조한다.

---

# 100. Model보다 Data가 차별화 요소가 될 수도 있다

예를 들어 동일한 Open Model을 여러 회사가 사용할 수 있다.

하지만

```text
Company A
→ 고품질 Domain Data 보유

Company B
→ 해당 Data 없음
```

이라면 결과적으로 서로 다른 수준의 Domain AI를 만들 수 있다.

---

# 101. 따라서 필요한 능력

AI Engineer에게 Model Architecture를 아는 것만 중요한 것이 아니다.

주어진 Task에 대해

```text
어떤 Data가 필요한가?

어떻게 수집할 것인가?

어떻게 생성할 것인가?

어떻게 Filtering할 것인가?

어떻게 AI가 사용할 Format으로 만들 것인가?
```

를 설계할 수 있어야 한다.

---

# 102. 이제 LLM의 한계

강의에서는 여러 강력한 응용을 설명한 뒤 LLM이 여전히 가진 근본적 한계들을 다룬다.

첫 번째는 가장 잘 알려진 **Hallucination**이다.

---

# 103. Hallucination

Hallucination은 여러 방식으로 정의할 수 있지만 강의에서 강조하는 특징은

> **실제 사실이 아닌 내용을 마치 사실인 것처럼 자신감 있고 유창하게 생성하는 현상**

이다.

---

# 104. 기존 Error보다 위험한 이유

일반적인 System Error라면

```text
Error

Unknown

Confidence 낮음
```

처럼 드러날 수 있다.

Hallucination에서는

```text
잘못된 정보
+
높은 자신감
+
자연스러운 문장
```

이 함께 나타날 수 있다.

---

# 105. 따라서 User가 진위를 판단하기 어렵다

잘못된 내용을

```text
"확실하지 않습니다."
```

라고 말하면 User가 주의할 수 있다.

하지만 완전히 자연스럽고 구체적인 Answer를 만들면

```text
정답인지
Hallucination인지
```

판단하기가 더 어렵다.

---

# 106. 존재하지 않는 Source를 이해한 것처럼 말할 수도 있다

강의에서는 실제 내용이 없는 Dummy Link를 제공했는데 Model이 마치 해당 Article을 읽은 것처럼 Summary를 생성하는 사례를 설명한다.

즉

```text
실제 Evidence 없음
↓
그럴듯한 Pattern 추론
↓
사실처럼 Response
```

가 가능하다.

---

# 107. Hallucination 원인 ① Knowledge Cutoff

Model은 특정 시점까지의 Training Data로 학습된다.

그 이후의 새로운 사건을 Model Weight 자체는 알지 못할 수 있다.

그런데 User가 최신 사실을 질문하면 Model은 가지고 있는 과거 Pattern에 기반해 Response를 생성하려 할 수 있다.

---

# 108. 해결 방법 중 하나 — Retrieval

최신 Knowledge를 외부에서 검색하여 Model Context에 넣어줄 수 있다.

```text
User Query
↓
Search / Retrieval
↓
Relevant Current Information
↓
LLM Context
↓
Response
```

이러한 방향을 강의에서는 **Retrieval-Augmented Generation(RAG)** 과 연결한다.

---

# 109. 하지만 Hallucination이 단순히 Knowledge Cutoff만의 문제는 아니다

LLM 자체가

```text
Probability Distribution
```

을 기반으로 다음 Token을 생성하는 Generative Model이다.

즉

> **사실 Database에서 정답을 그대로 꺼내는 System이 아니다.**

---

# 110. Language Model의 본질

강의에서는 LLM을 직관적으로 일종의

> **“말하는 Internet”**

처럼 표현한다.

방대한 Text Pattern을 학습해서 그럴듯한 다음 Token을 확률적으로 생성한다.

---

# 111. 그러므로 확률적으로 자연스러운 것과 사실은 다르다

```text
Probability 높음
≠
사실임
```

이다.

어떤 문장이 언어적으로 매우 자연스럽다고 해서 실제 세계에서 True라는 보장은 없다.

이 점이 Hallucination의 중요한 구조적 배경이다.

---

# 112. LLM을 사용할 때 Task Risk를 고려해야 한다

강의에서는 특히

```text
정답이 하나가 없는 Task
```

에서는 LLM의 다양한 Generation 능력이 매우 유용하다고 설명한다.

예:

- Brainstorming
    
- 여러 Alternative 탐색
    
- Drafting
    

---

# 113. 반대로 정답이 중요한 Task

예:

- 정확한 사실
    
- Production Code
    
- 중요한 의사결정
    
- 책임이 큰 업무
    

등에서는 Output을 검증해야 한다.

```text
LLM Output
≠
자동 승인
```

이다.

---

# 114. Coding Agent와 Responsibility

강의에서는 Coding Agent도 예로 든다.

AI가 Code를 생성했다고 하더라도 User가

```text
Allow

Approve

Apply
```

를 눌렀다면 실제 Product에 적용한 책임은 결국 사용자에게 있다.

---

# 115. 따라서 Human Verification이 필요하다

AI가 생성한 Code를 모두 수작업으로 확인하기 어렵더라도 최소한

```text
Unit Test

Integration Test

Test Suite

Code Review
```

등 검증 체계를 구축해야 한다는 것이 강의의 실무적 조언이다.

---

# 116. 두 번째 한계 — Jailbreak

앞 강의에서도 살펴본 문제다.

Model은

```text
Instruction Tuning
+
Preference Learning
```

을 통해 Safety Alignment를 학습한다.

하지만 특정 Prompt를 이용해 이 Alignment를 우회하려는 공격이 존재한다.

---

# 117. Jailbreak의 핵심

User가

```text
원래라면 거절해야 하는 Request
```

를 직접 묻는 대신 복잡한 Context나 Role Play, Encoding, Instruction을 사용해 Model이 Safety Rule을 따르지 않도록 유도한다.

---

# 118. Do Anything Now 계열 Prompt

강의에서는 과거 대표적인 Jailbreak 방식으로 **DAN(Do Anything Now)** 계열 Prompt를 언급한다.

핵심은 Model에게

```text
Safety Rule을 무시해도 된다.
```

는 새로운 Role이나 Context를 강하게 부여하는 방식이다.

---

# 119. Jailbreak가 가능한 구조적 이유 ① Value Conflict

LLM은 Post-training에서 여러 목표를 배운다.

예:

```text
User Instruction을 잘 따라라.

하지만
Unsafe Request에는 응답하지 마라.
```

문제는 공격 Prompt가 이 둘을 충돌시키는 상황을 만들 수 있다는 것이다.

---

# 120. Instruction Following vs Safety

예를 들어 User가 위험한 Request와 함께

```text
"반드시 특정 문장으로
답변을 시작하라."
```

라고 지시할 수 있다.

그러면 Model 내부에서는

```text
Instruction Following

vs

Safety Preference
```

사이에 충돌이 발생할 수 있다는 것이 강의의 설명이다.

---

# 121. Jailbreak 이유 ② Pre-training과 Alignment Training의 규모 차이

Pre-training에서는 Internet-scale Data를 엄청난 양으로 학습한다.

반면 Alignment Training Data는 상대적으로 훨씬 작다.

```text
Huge Pre-training
>>>>>>>>>
Alignment Data
```

이다.

---

# 122. Encoding을 이용한 우회

예를 들어 Base64 같은 Encoding 형태의 Text는 Pre-training 단계에서 접했을 수 있다.

하지만 Alignment Dataset에서는 그러한 모든 Encoding 형태의 위험 Request를 충분히 학습하지 못했을 수 있다.

따라서

```text
Natural Language에서는 거절

Encoding된 형태에서는
Safety Rule 적용 실패
```

같은 문제가 발생할 수 있다는 강의의 설명이다.

---

# 123. Jailbreak는 Training Pipeline 전체와 연결된다

즉 단순 Prompt Bug가 아니라

```text
Pre-training Objective

Instruction Following

Preference Learning

Safety Alignment
```

등 서로 다른 Training Goal이 상호작용하면서 생기는 구조적 문제로 볼 수 있다.

---

# 124. 하지만 Model은 계속 발전한다

강의에서는 과거의 단순 Jailbreak Prompt들은 최신 Model에서 점차 잘 작동하지 않게 되는 흐름도 언급한다.

즉 공격과 방어가 지속적으로 발전한다.

---

# 125. 세 번째 한계/문제 — AI-generated Text Detection

LLM이

- Assignment
    
- Exam
    
- Interview
    
- Writing
    

등에 광범위하게 사용되면서

> **이 Text가 사람의 것인지 AI가 만든 것인지 판단할 수 있는가?**

라는 문제가 생긴다.

---

# 126. 강의에서 소개하는 접근 — Watermarking

강의에서는 대표적인 연구적 접근으로 **Watermarking**을 소개한다.

핵심 아이디어는

> **Generation Quality를 크게 손상하지 않을 정도로 Token Probability를 미세하게 조절하여 통계적으로 탐지 가능한 Pattern을 Output에 남긴다.**

는 것이다.

---

# 127. Watermarking의 기본 직관

Vocabulary Token을 특정한 방식으로 나누었다고 하자.

Generation 시 Model Provider가 특정 Token Group에 약간 더 높은 Probability를 줄 수 있다.

```text
원래 Distribution
↓
미세한 Probability Adjustment
↓
Text Generation
```

한다.

---

# 128. 사람이 읽기에는 자연스럽다

Probability Adjustment가 너무 크면 Output Quality가 망가질 수 있다.

따라서 사람에게는 거의 차이를 느끼지 못할 정도로 작은 Bias를 넣는다.

---

# 129. 하지만 통계적으로는 Pattern이 남는다

긴 Text에서 특정 Token Group이 예상보다 반복적으로 많이 나타난다면

```text
이 Distribution은
Watermarked Model의 Generation Pattern과
매우 유사하다.
```

고 통계적으로 판단할 수 있다는 것이 Watermarking의 아이디어다.

---

# 130. 강의에서 강조하는 점

강의에서는 이것을

```text
또 다른 AI가
"AI 같아 보인다."
라고 추측
```

하는 것과 구분한다.

Watermarking은 생성 과정에서 미리 설계한 Statistical Signal을 이용해 검출하는 방식이라는 점을 강조한다.

---

# 131. 따라서 AI Text Detection이 원리상 불가능한 것은 아니다

강의의 결론은

> **AI Text를 항상 쉽게 완벽하게 검출할 수 있다는 뜻은 아니지만, 생성 단계에서 Watermark를 설계한다면 통계적 탐지 방법을 구축할 수 있다.**

는 방향이다.

---

# 132. 강의자의 최종 활용 조언

강의 마지막에서는 AI 사용 자체를 피하기보다

```text

↓
직접 읽음
↓
검토
↓
추가 질문
↓
수정
↓

```

하는 과정이 중요하다고 설명한다.

즉 AI가 첫 Draft를 만들었더라도 최종 Output은 사용자가 충분히 개입하고 검토해야 한다는 관점이다.

# 133. LLM Evaluation에서 가장 큰 어려움

기존 Model:

```text
Task 하나
↓
Test Dataset
↓
Metric 하나
```

로 비교적 단순했다.

Foundation Model:

```text
수많은 Task
+
Prompt Variation
+
Decoding Variation
+
Open-ended Generation
+
Human Preference
```

를 모두 고려해야 한다.

따라서 Evaluation 자체가 하나의 큰 연구 분야가 된다.

---

# 134. 평가 방법 전체 비교

|평가 방식|Reference 필요|장점|한계|
|---|--:|---|---|
|Accuracy/F1|O|명확하고 객관적|정답이 있는 Task만|
|ROUGE/Overlap|O|계산 간단|Semantic Meaning 반영 부족|
|Embedding Similarity|O|의미 유사성 반영|별도 Embedding Model 필요|
|Perplexity|X|Fluency 측정 가능|Correctness/Creativity 평가 어려움|
|Human Evaluation|X|복잡한 Quality 판단|비용·시간 큼|
|LLM-as-a-Judge|X|빠르고 Scale 가능|Judge Bias 존재|
|Arena/Human Pairwise|X|실제 User Preference 반영|Vote 축적에 시간 필요|

# 135. LLM Judge Bias 정리

|Bias|의미|
|---|---|
|Position Bias|Response 내용보다 위치를 선호|
|Length Bias|긴 Response를 과도하게 선호|
|Self-preference Bias|자신의 Model Family Output을 선호|

# 152. Reward Model과 LLM-as-a-Judge 차이

둘 다 Response를 평가하지만 역할을 구분한다.

### Reward Model

RLHF Training 내부에서

```text
Prompt + Response
→ Reward
```

를 제공한다.

### LLM-as-a-Judge

일반적인 Model Evaluation에서

```text
Question + Response + Criteria
→ Evaluation Score / Preference
```

를 만든다.

# 156. 자주 헷갈리는 점 ① — Benchmark 하나가 높으면 최고의 LLM인가?

아니다.

Foundation Model은 수많은 Task를 수행하기 때문에 여러 Benchmark를 종합해서 평가해야 한다.

---

# 157. 자주 헷갈리는 점 ② — 같은 Benchmark Score면 공정하게 비교한 것인가?

반드시 아니다.

- Shot 수
    
- CoT
    
- Prompt
    
- Decoding
    
- Metric
    

등 Evaluation Setting도 같아야 한다.

---

# 158. 자주 헷갈리는 점 ③ — Accuracy는 모든 LLM 평가에 사용할 수 있는가?

아니다.

Ground Truth가 명확한 Task에서 주로 사용할 수 있다.

Open-ended Generation에서는 정답 하나가 없을 수 있다.

---

# 159. 자주 헷갈리는 점 ④ — ROUGE는 의미를 완벽하게 비교하는가?

아니다.

주로 Surface-level Word/Sequence Overlap을 기반으로 하기 때문에 Semantic Paraphrase를 충분히 반영하지 못할 수 있다.

---

# 160. 자주 헷갈리는 점 ⑤ — Embedding Similarity는 문자열이 같은지 보는 것인가?

아니다.

Text를 Vector Representation으로 변환해 의미 공간에서 Similarity를 비교한다.

---

# 161. 자주 헷갈리는 점 ⑥ — Perplexity가 낮으면 반드시 좋은 Answer인가?

아니다.

자연스러운 Language인지 평가하는 데 도움이 되지만

- Correctness
    
- Creativity
    
- Safety
    
- Helpfulness
    

등을 모두 보장하지 않는다.

---

# 162. 자주 헷갈리는 점 ⑦ — LLM-as-a-Judge는 사람이 필요 없다는 뜻인가?

아니다.

Human Evaluation과 높은 Correlation을 보일 수 있지만 Position, Length, Self-preference 등 Bias가 있다.

---

# 163. 자주 헷갈리는 점 ⑧ — Arena는 LLM Judge가 평가하는가?

강의에서 소개한 대표 Arena 구조에서는 실제 User가 Anonymous Response A/B를 비교하여 Preference Vote를 제공한다.

---

# 164. 자주 헷갈리는 점 ⑨ — Position Bias란 첫 번째 Answer가 항상 좋은가?

특정 위치에 있는 Answer를 내용과 무관하게 더 선호하는 경향을 의미한다.

어느 위치를 선호하는지는 Judge에 따라 달라질 수 있다.

---

# 165. 자주 헷갈리는 점 ⑩ — 긴 Answer가 항상 Quality가 높은가?

아니다.

따라서 LLM Judge의 Length Bias를 주의해야 한다.

---

# 166. 자주 헷갈리는 점 ⑪ — Multimodal LLM은 Image를 먼저 Caption으로 바꾸는 것인가?

강의에서 설명하는 대표적 방식의 핵심은 아니다.

Image를 Vector Representation으로 만들고 그것을 Language Model이 사용할 수 있는 Representation에 연결한다.

---

# 167. 자주 헷갈리는 점 ⑫ — LLM은 Text밖에 출력할 수 없는가?

Language Model Backbone을 확장하면 Audio나 Robot Action 같은 다른 Output Space와 연결할 수 있다는 것이 강의의 응용 방향이다.

---

# 168. 자주 헷갈리는 점 ⑬ — Synthetic Data는 무조건 품질이 낮은가?

아니다.

강의에서는 Filtering을 잘 수행하면 실제 Instruction Tuning에 유효하게 사용할 수 있는 사례를 소개한다.

다만 Quality Control은 중요하다.

---

# 169. 자주 헷갈리는 점 ⑭ — Data가 많을수록 항상 좋나?

이번 차시에서는 오히려

> **양보다 Quality가 중요할 수 있다.**

는 Synthetic Data Filtering 결과를 강조한다.

---

# 170. 자주 헷갈리는 점 ⑮ — Hallucination은 Model이 모르는 것만 질문할 때 발생하는가?

아니다.

Knowledge Cutoff가 한 원인이 될 수 있지만 Probability-based Generation 자체와도 연결되는 더 넓은 문제다.

---

# 171. 자주 헷갈리는 점 ⑯ — RAG는 Model Weight에 최신 정보를 학습시키는 것인가?

아니다.

대표적으로 Inference 시 외부 Knowledge를 가져와 Context에 넣어 사용하는 방식이다.

---

# 172. 자주 헷갈리는 점 ⑰ — Jailbreak는 Model 자체를 Hacking하는 것인가?

강의에서 다루는 Jailbreak는 주로 Prompt를 통해 Alignment/Safety Behavior를 우회하는 문제다.

---

# 173. 자주 헷갈리는 점 ⑱ — AI Text는 절대 탐지할 수 없는가?

강의에서는 Generation 단계에서 Statistical Watermark를 삽입하면 탐지 가능한 구조를 설계할 수 있다고 설명한다.

다만 이것을 모든 AI-generated Text를 항상 완벽하게 판별할 수 있다는 의미로 확대해서 이해하면 안 된다.

---

# 174. 이번 강의에서 반드시 기억할 핵심

### 1. 평가에는 Goal, Evaluation Method, Evaluation Metric이 필요하다.

### 2. 일반적인 AI 평가는 Training에서 보지 않은 Test Data와 Ground Truth를 이용한다.

### 3. Foundation Model은 특정 Task 하나가 아니라 여러 Task를 수행하므로 여러 Benchmark를 종합적으로 평가해야 한다.

### 4. LLM Evaluation은 Prompt, Few-shot, CoT, Decoding Setting에 따라서도 결과가 달라질 수 있어 Fair Comparison이 어렵다.

### 5. Task마다 Accuracy, F1 등 서로 다른 Metric을 사용할 수 있다.

### 6. MMLU는 강의에서 대표적인 정답 기반 LLM Benchmark로 소개된다.

### 7. Translation이나 Summarization 같은 Open-ended Task는 정답이 하나가 아니어서 평가가 어렵다.

### 8. Human Reference를 만든 뒤 Model Output과 비교하는 방법이 있다.

### 9. ROUGE는 Reference와 Generated Text의 Word/Sequence Overlap을 평가하는 대표적인 방법으로 소개된다.

### 10. Word Overlap은 Semantic Context를 충분히 반영하기 어렵다.

### 11. Text를 Embedding Vector로 변환한 뒤 Cosine Similarity를 계산하는 Semantic Evaluation 방법이 있다.

### 12. Reference가 없을 때 Text의 자연스러움을 Perplexity로 평가할 수 있다.

### 13. Perplexity는 Fluency/Naturalness에는 도움이 되지만 Creativity나 Correctness 전체를 평가하지 못한다.

### 14. 복잡한 Generation Quality는 과거 Human Expert Evaluation을 많이 사용했다.

### 15. Human Evaluation은 Quality가 높지만 비용과 시간이 많이 든다.

### 16. LLM-as-a-Judge는 LLM을 Response 평가자로 사용하는 방법이다.

### 17. Judge LLM에게는 Question, Response뿐 아니라 명확한 Evaluation Criteria를 제공하는 것이 중요하다.

### 18. 강의에서는 큰 LLM의 Judge Score가 Human Evaluation과 높은 Correlation을 보인 연구 결과를 소개한다.

### 19. LLM Judge는 Training Data Filtering에도 사용할 수 있다.

### 20. 이전 Model이 다음 Model의 Training Data를 평가하고 만드는 Pipeline이 가능하다.

### 21. Arena 방식은 Anonymous Model A/B의 Response를 실제 User가 비교한다.

### 22. Pairwise Win/Loss를 이용하여 Elo 계열 Rating으로 Model Ranking을 만들 수 있다.

### 23. Human Arena는 신뢰도가 높지만 충분한 Vote를 모으는 데 시간이 걸린다.

### 24. Pairwise Comparison도 LLM Judge로 자동화할 수 있다.

### 25. LLM Judge에는 Position Bias가 있을 수 있다.

### 26. LLM Judge에는 긴 Response를 과도하게 선호하는 Length Bias가 있을 수 있다.

### 27. LLM Judge에는 같은 Model Family가 생성한 Answer를 선호하는 Self-preference Bias가 있을 수 있다.

### 28. Position Bias는 Response 순서를 바꾸어 반복 평가하는 방식으로 완화할 수 있다.

### 29. Multimodal Foundation Model은 강력한 LLM을 Backbone으로 다른 Modality Representation을 연결하는 방식으로 만들 수 있다.

### 30. Image를 반드시 자연어 Caption으로 먼저 변환하는 것이 아니라 Vector Representation을 LLM-compatible Representation에 연결할 수 있다.

### 31. Image, Audio, Video 등 여러 Modality를 이와 비슷한 방식으로 확장할 수 있다.

### 32. Vision-Language-Action Model은 Vision과 Language를 이용해 Robot Action까지 Output하는 방향의 확장이다.

### 33. LLM은 Synthetic Training Data를 생성할 수 있다.

### 34. 소량의 Human Seed Instruction으로 대량의 Instruction Dataset을 생성할 수 있다.

### 35. Synthetic Data에는 중복 및 품질 문제가 있으므로 Filtering이 중요하다.

### 36. LLM을 Synthetic Data의 Quality Judge로 다시 사용할 수도 있다.

### 37. 강의에서는 전체 Synthetic Data보다 높은 Quality Data만 사용하는 것이 더 좋은 성능을 낸 사례도 소개한다.

### 38. 앞으로 회사가 가진 High-quality Proprietary Data가 중요한 경쟁력이 될 수 있다는 것이 강의자의 중요한 실무적 관점이다.

### 39. Hallucination은 사실이 아닌 정보를 자연스럽고 자신감 있게 만들어내는 문제다.

### 40. Knowledge Cutoff 이후 정보를 질문하는 것은 Hallucination을 유발할 수 있는 한 원인이다.

### 41. Retrieval/RAG를 이용해 외부 최신 Knowledge를 Context로 제공하면 일부 문제를 완화할 수 있다.

### 42. 하지만 근본적으로 LLM은 Probability 기반 Generator이므로 자연스러운 문장과 사실을 동일시할 수 없다.

### 43. 정확성이 중요한 Task에서는 LLM Output을 반드시 검증해야 한다.

### 44. Coding Agent를 사용하더라도 최종 Code의 검증과 책임은 User에게 있다.

### 45. Test Code와 Evaluation Pipeline을 구축하는 것이 중요하다.

### 46. Jailbreak는 Prompt 등을 이용해 LLM의 Safety Alignment를 우회하려는 문제다.

### 47. Instruction Following과 Safety Preference가 충돌할 수 있다는 점이 Jailbreak의 한 구조적 설명이다.

### 48. 매우 큰 Pre-training에 비해 상대적으로 작은 Alignment Training Coverage 때문에 예상하지 못한 Input 표현에서 Safety가 깨질 가능성도 강의에서 설명한다.

### 49. Base64 같은 Encoding 형태의 Input이 Alignment Coverage를 우회하는 사례가 있을 수 있다.

### 50. LLM의 Safety는 지속적으로 개선되지만 Jailbreak 역시 계속 연구되는 문제다.

### 51. AI-generated Text Detection 문제도 존재한다.

### 52. 강의에서는 Generation Probability를 미세하게 조정해 Statistical Pattern을 남기는 Watermarking을 대표적인 탐지 방법으로 소개한다.

### 53. Watermark는 사람이 읽는 Quality를 크게 훼손하지 않으면서 통계적으로 Detection 가능한 Signal을 넣으려는 접근이다.

### 54. 최종적으로 AI Output은 그대로 받아들이기보다 User가 읽고 검증하고 수정하는 과정이 필요하다는 것이 강의의 결론이다.

# 176. 이번 강의의 핵심 한 문장

> **거대 언어 모델의 평가는 단일 정답과 Metric으로 평가할 수 있었던 기존 Task-specific AI와 달리 여러 Task·Prompt·Decoding 조건과 Open-ended Response Quality를 동시에 고려해야 하기 때문에 Benchmark, Reference Similarity, Perplexity, Human Evaluation, LLM-as-a-Judge 등을 함께 활용하며, LLM은 다른 Modality와 Robot Action으로 확장되거나 Synthetic Data 생성·평가에도 사용될 수 있지만 Probability 기반 생성으로 인한 Hallucination과 Alignment를 우회하는 Jailbreak 등의 한계가 있으므로 실제 활용에서는 적절한 평가·검색·검증 체계를 함께 구축해야 한다.**

가장 짧게 압축하면 다음과 같다.

```text
LLM 평가
= 정답 하나로는 부족하다.

LLM-as-a-Judge
= 사람의 복잡한 평가를
  LLM이 일부 자동화한다.

Multimodal
= 다른 Data도 Vector로 바꿔
  Language Model에 연결한다.

Synthetic Data
= LLM이 다음 LLM의
  학습 Data도 만든다.

Hallucination
= 자연스러운 확률적 생성이
  사실을 보장하지 않는다.

Jailbreak
= Instruction과 Alignment의
  빈틈을 Prompt가 파고들 수 있다.

최종적으로
= LLM을 쓰되
  Evaluation과 Verification은
  반드시 함께 설계해야 한다.
```
