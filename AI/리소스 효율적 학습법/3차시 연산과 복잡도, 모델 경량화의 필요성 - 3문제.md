# 1. 수 체계가 중요한 이유

앞에서 배운

```text
Integer

Fixed Point

Floating Point
```

는 단순히 숫자를 표현하는 방식만 다른 것이 아니다.

각 Representation을 실제 Hardware에서 처리하기 위한

```text
Arithmetic Circuit
```

의 복잡도가 다르다.

즉

> **숫자를 어떤 방식으로 표현하는가는 결국 연산 비용을 결정한다.**

---

# 2. Unsigned Integer Addition

Unsigned Integer의 Addition은 우리가 알고 있는 일반 Binary Addition을 수행한다.

```text
A
+
B
↓
Binary Addition
```

한다.

하지만 항상 확인해야 하는 것이 있다.

```text
Overflow
```

다.

---

# 3. Unsigned Overflow

n-bit Unsigned Number는

```text
0 ~ 2ⁿ - 1
```

까지만 표현할 수 있다.

Addition 결과가 이 Range를 넘으면 Overflow가 발생한다.

---

# 4. Carry-out

Unsigned Addition에서는 가장 높은 Bit 밖으로

```text
Carry-out
```

이 발생하면 Overflow라고 판단할 수 있다.

```text
n-bit Addition
↓
Carry-out 발생
↓
Representable Range 초과
↓
Overflow
```

이다.

강의에서는 Unsigned Number에서는 Carry-out이 Overflow 판단 기준이라는 점을 다시 강조한다.

---

# 5. Unsigned Number에는 Underflow가 없는가?

강의에서는 Unsigned Integer의 가장 작은 표현값이 이미

```text
0
```

이므로 Floating Point에서 말하는 의미의 Underflow를 별도로 생각하지 않는다고 설명한다.

즉

```text
Unsigned Integer
→ Lower Bound = 0
```

이다.

---

# 6. Signed Integer에서는 Carry-out ≠ Overflow

Two's Complement Signed Integer에서는 이야기가 달라진다.

```text
Carry-out 발생
```

했다고 해서 반드시 Overflow는 아니다.

---

# 7. 예: +7 + (-5)

4-bit Two's Complement라고 하자.

```text
+7 + (-5)
```

를 계산하면 Binary Addition에서 Carry-out이 발생할 수 있다.

하지만 실제 결과는

```text
+2
```

로 정상적인 Range 안에 존재한다.

따라서

```text
Signed Number
에서
Carry-out
≠
Overflow
```

이다.

---

# 8. Signed Overflow는 부호를 본다

Two's Complement에서 대표적인 Overflow 상황:

```text
Positive + Positive
→ Negative
```

또는

```text
Negative + Negative
→ Positive
```

가 나타난다.

---

# 9. 예: +7 + +2

4-bit Two's Complement Range:

```text
-8 ~ +7
```

이다.

그런데

```text
7 + 2
=
9
```

는 표현할 수 없다.

실제 4-bit Pattern만 남겨 Two's Complement로 해석하면 음수 값이 된다.

즉

```text
양수 + 양수
↓
음수
```

가 되었으므로 Overflow다.

---

# 10. 예: -7 + -2

원래 결과는

```text
-9
```

여야 한다.

하지만 4-bit에서는 `-9`를 표현할 수 없다.

결과 Pattern을 해석하면 Positive Number가 나타날 수 있다.

즉

```text
음수 + 음수
↓
양수
```

가 되므로 Overflow다.

---

# 11. Unsigned vs Signed Overflow

|Number System|대표 Overflow 판단|
|---|---|
|Unsigned|Carry-out|
|Two's Complement Signed|Operand와 Result의 Sign 관계|

따라서

> **같은 Binary Adder를 사용하더라도 Number Representation에 따라 Overflow를 해석하는 규칙이 달라진다.**

---

# 12. 왜 Overflow Detection이 중요한가?

단순 Error Detection 때문만은 아니다.

예를 들어 어떤 Application에

```text
4 bit
```

만 사용해도 되는지 결정하고 싶다면

```text
실제 연산 과정에서
Overflow가 발생하는가?
```

를 확인해야 한다.

즉

```text
Overflow Analysis
↓
필요한 Bit-width 결정
↓
Resource Optimization
```

으로 이어진다.

---

# 13. Subtraction은 Addition으로 구현 가능

Two's Complement에서는

```text
A - B
```

를

```text
A + (-B)
```

로 바꿀 수 있다.

예:

```text
7 - 5
=
7 + (-5)
```

이다.

---

# 14. Hardware 관점의 의미

별도의 완전히 다른

```text
Subtractor
```

를 만들지 않고

```text
Adder
```

를 재사용할 수 있다.

즉

```text
Addition Hardware
+
Two's Complement
↓
Addition + Subtraction
```

이 가능하다.

---

# 15. Hardware Reuse

이것은 Number Representation을 설계할 때 중요한 원칙이다.

> **가능하면 이미 존재하는 단순한 Hardware를 여러 Arithmetic Operation에 재사용한다.**

Two's Complement가 널리 사용되는 이유 중 하나도 여기에 있다.

---

# 16. Fixed-Point에서 새로운 문제 — Binary Point 위치

Fixed Point에서는 같은 Bit-width라도 Binary Point 위치가 다를 수 있다.

예:

```text
5-bit Fixed Point A
Integer 2 bit
Fraction 3 bit
```

와

```text
5-bit Fixed Point B
Integer 3 bit
Fraction 2 bit
```

가 있을 수 있다.

---

# 17. 같은 Bit Pattern이어도 Scale이 다르다

두 Fixed-Point Format은

```text
Scaling Factor
```

가 서로 다르다.

따라서 두 값을 바로 더하면 안 된다.

---

# 18. 실제 Software System에서도 생길 수 있다

예를 들어

```text
Function F1
```

은

```text
Q2.3
```

Format을 사용하고,

다른 개발자가 만든

```text
Function F2
```

는

```text
Q3.2
```

Format을 사용한다고 하자.

F1의 Output을 F2에 그대로 넣으면 값 해석이 달라진다.

---

# 19. Radix Point Alignment

연산하기 전에

```text
Binary Point
```

위치를 맞춰야 한다.

즉

```text
Scale Alignment
```

가 필요하다.

---

# 20. Fixed-Point Addition의 실제 복잡성

같은 Format끼리라면 Addition은 매우 단순하다.

하지만 Format이 다르면

```text
Extension
+
Shift
+
Alignment
+
Addition
```

과 같은 추가 과정이 필요할 수 있다.

---

# 21. Fixed Point에서 Programmer의 책임

앞 차시에서 강조했듯이 Binary Point는 Hardware에 직접 저장되어 있지 않다.

따라서

```text
이 Bit Pattern의
Radix Point가 어디인가?
```

를 Programmer/System이 알고 있어야 한다.

---

# 22. 결과 Format도 결정해야 한다

두 값을 Alignment하여 연산한 뒤에도

```text
Output을
Q2.3으로 할까?

Q3.2로 할까?
```

를 결정해야 한다.

즉

```text
Range
vs
Precision
```

Trade-off가 다시 등장한다.

---

# 23. Integer Multiplication

Binary Multiplication도 기본 원리는 우리가 Decimal Multiplication에서 배운 것과 같다.

예:

```text
1011
×
0101
```

이면 각 Bit에 따라

```text
1011 × 1

1011 × 0

1011 × 1
```

을 Shift해서 더한다.

---

# 24. Multiplication의 중요한 특징 — Bit-width 증가

n-bit Number 두 개를 Multiply하면 최대

```text
2n bit
```

Result가 필요할 수 있다.

즉

```text
n bit × n bit
→ 최대 2n bit
```

이다.

---

# 25. 예: 4-bit × 4-bit

안전하게 전체 Product를 표현하려면

```text
8 bit
```

Result가 필요할 수 있다.

그런데 Output도 4 bit만 유지하려고 하면

```text
Overflow
```

가 발생할 수 있다.

---

# 26. Multiplication은 Addition보다 복잡하다

Multiplication은 내부적으로

```text
Partial Product 생성

Shift

Addition
```

등 여러 작업이 필요하다.

그래서 단순 Addition보다 Hardware가 커지는 경향이 있다.

---

# 27. High-Speed Multiplier

강의에서는 실제 Computer Architecture에서 Multiplication을 빠르게 만들기 위한 다양한

```text
High-speed Multiplier
```

기법이 존재한다고 언급한다.

세부 구조는 이번 강의의 핵심 범위에서 제외한다.

---

# 28. Integer Division

Division 역시 기본 원리는 우리가 배운 Long Division과 유사하다.

하지만 Hardware로 구현하면 훨씬 어려워진다.

---

# 29. Division의 입력·출력 구조

강의에서는 안전한 Bit Range를 기준으로

```text
Dividend
≈ 2n bit

Divisor
≈ n bit

Quotient
≈ n bit

Remainder
≈ n bit
```

관점으로 설명한다.

---

# 30. 왜 Dividend가 더 클 수 있는가?

Division의 관계:

```text
Dividend
=
Divisor × Quotient
+
Remainder
```

이다.

`Divisor × Quotient`가 최대 `2n bit` 규모가 될 수 있으므로 Dividend 역시 더 넓은 Range를 고려해야 한다.

---

# 31. Division이 특별히 복잡한 이유 ①

다른 기본 Arithmetic은 주로 Result 하나를 만든다.

Division은

```text
Quotient
+
Remainder
```

두 Output을 만들어야 한다.

---

# 32. Division이 특별히 복잡한 이유 ②

Division 과정은

```text
Compare

Subtract

Shift

Repeat
```

같은 Iterative Operation을 반복한다.

따라서 Latency가 크다.

---

# 33. 강의의 실무적 메시지

가능하다면 매우 제한적인 Hardware Environment에서는

```text
Division
```

을 줄이는 것이 유리할 수 있다.

예를 들어 Algorithm Transformation을 이용하여 Division을 Multiplication 등으로 바꾸는 방식을 고민할 수 있다는 것이 강의의 관점이다.

---

# 34. 고정소수점 Arithmetic Complexity 비교

강의에서는 특정 28nm CMOS 구현 사례를 통해

```text
8-bit Addition
```

을 기준으로 다른 Arithmetic의 Hardware Area와 Delay를 비교한다.

정확한 숫자를 암기하는 것보다 상대적인 구조가 중요하다.

---

# 35. Fixed Point에서의 상대적 경향

```text
Addition ≈ Subtraction
```

은 상대적으로 단순하다.

```text
Multiplication
```

은 Bit-width가 증가하면서 Complexity가 크게 증가한다.

```text
Division
```

은 특히 Execution Time 측면에서 매우 비싸다.

강의에서도 실제 Hardware 관점에서 곱셈과 나눗셈의 Area가 크게 증가하며, 특히 Division의 Latency가 매우 크다고 강조한다.

---

# 36. 이제 Floating Point

Fixed Point도 복잡했지만 Floating Point Arithmetic은 더 많은 작업을 필요로 한다.

특히 Addition과 Subtraction에서 차이가 크게 나타난다.

---

# 37. Floating-Point Addition

두 수를

```text
M₁ × β^E₁

M₂ × β^E₂
```

라고 하자.

Mantissa를 바로 더할 수는 없다.

먼저

```text
E₁
=
E₂
```

가 되도록 Exponent를 맞춰야 한다.

---

# 38. Exponent Alignment

일반적으로 더 큰 Exponent를 기준으로 잡는다.

예:

```text
1.23 × 10⁵
+
4.56 × 10³
```

이면

```text
4.56 × 10³
=
0.0456 × 10⁵
```

처럼 작은 Exponent의 Mantissa를 Shift한다.

---

# 39. Floating Point Addition의 첫 번째 Overhead

```text
Exponent Compare
↓
Mantissa Shift
↓
Exponent Alignment
```

가 필요하다.

Fixed Point의 같은 Scale Addition에는 없던 작업이다.

---

# 40. Alignment 후 Mantissa Addition

Exponent가 같아지면

```text
Mantissa₁
+
Mantissa₂
```

를 수행한다.

그러나 이것으로 끝나지 않는다.

---

# 41. Post-normalization

Addition Result의 Mantissa가 Normalized Range 밖으로 나갈 수 있다.

예를 들어 Mantissa를

```text
1.xxxxx
```

형태로 유지하기로 했는데 Addition 결과가

```text
10.xxxxx
```

가 되었다고 하자.

---

# 42. 다시 Normalize해야 한다

```text
10.xxxxx × 2^E
```

를

```text
1.0xxxxx × 2^(E+1)
```

형태로 바꿔야 한다.

이를 강의에서는

```text
Post-normalization
```

이라고 설명한다.

---

# 43. Post-normalization 후 또 문제가 생긴다

Exponent를 증가시켰으므로

```text
Exponent Overflow
```

가 발생했는지 다시 검사해야 한다.

---

# 44. Floating-Point Addition 전체 Flow

```text
Exponent Compare
↓
Exponent Alignment
↓
Mantissa Shift
↓
Mantissa Addition
↓
Normalization Check
↓
Post-normalization
↓
Exponent Update
↓
Overflow Check
```

이다.

즉 여러 단계가 연속적으로 발생한다.

---

# 45. Floating-Point Subtraction

Subtraction도 비슷하다.

다만 Mantissa를 뺀 결과가 너무 작아져 Normalized Range 아래로 내려갈 수 있다.

---

# 46. Subtraction 후 Normalization

예:

```text
0.001xxx
```

같은 결과가 나왔다면

```text
1.xxx
```

가 되도록 Mantissa를 Shift하고 Exponent를 감소시켜야 한다.

---

# 47. Underflow Check

Exponent를 감소시켰기 때문에

```text
Underflow
```

가 발생하는지도 확인해야 한다.

---

# 48. Floating Addition/Subtraction이 비싼 이유

단순 Addition Hardware만 필요한 것이 아니라

```text
Exponent Comparator

Variable Shifter

Mantissa Adder

Normalizer

Overflow / Underflow Detection
```

등이 필요하다.

따라서 같은 Bit-width의 Fixed Point Addition보다 복잡하다.

---

# 49. 흥미로운 점 — Floating Point Multiplication

강의에서는 Floating Point에서는 오히려 Multiplication이 Addition/Subtraction보다 구조적으로 간단한 부분이 있다고 설명한다.

---

# 50. Floating Multiplication — Sign

Sign은 두 Operand의 Sign만 보면 된다.

```text
Same Sign
→ Positive

Different Sign
→ Negative
```

이다.

---

# 51. Floating Multiplication — Exponent

Exponent는

```text
E_result
=
E₁ + E₂
```

형태로 처리한다.

Bias가 존재한다면 Bias Correction이 추가된다.

---

# 52. Floating Multiplication — Mantissa

Mantissa는

```text
M_result
=
M₁ × M₂
```

한다.

---

# 53. Addition과의 큰 차이

Addition은

```text
Exponent Alignment
```

을 먼저 해야 해서 Mantissa Operation과 순차적으로 연결된다.

Multiplication에서는

```text
Exponent Addition
```

과

```text
Mantissa Multiplication
```

을 상당 부분 Parallel하게 수행할 여지가 있다.

---

# 54. 그래서 Floating Point에서는

강의의 Hardware 사례에서는

```text
Multiplication
```

이

```text
Addition / Subtraction
```

보다 Latency가 더 짧을 수도 있다는 흥미로운 결과를 설명한다.

이는 Fixed Point에서 일반적으로 생각하던 직관과 다를 수 있다.

---

# 55. Floating Multiplication도 후처리는 필요하다

물론

```text
Normalization

Bias Handling

Overflow / Underflow Check
```

등은 여전히 필요하다.

따라서 절대적으로 간단한 연산이라는 의미는 아니다.

---

# 56. Floating Point Division

Division에서는

```text
Sign
→ Sign 비교

Exponent
→ E₁ - E₂

Mantissa
→ M₁ / M₂
```

형태로 처리할 수 있다.

---

# 57. Floating Division의 특수 상황

Divisor가 `0`이면

```text
±Infinity
```

와 같은 Special Value가 발생할 수 있다.

# 58. 0 / 0

```text

```

처럼 정의되지 않는 연산은

```text

```

# 59. Floating Point Division은 여전히 비싸다

Fixed Point와 마찬가지로 Mantissa Division 자체가 복잡하다.

강의에서는

```text
Division
```

의 실행 시간이 다른 Arithmetic보다 특히 크다고 강조한다.

---

# 60. Fixed Point vs Floating Point

Floating Point의 가장 큰 장점:

```text
Very Wide Dynamic Range
```

이다.

하지만 비용을 지불한다.

```text
Alignment

Normalization

Rounding

Exponent Handling

Special Values

Overflow / Underflow
```

등 때문이다.

---

# 61. Hardware Complexity 차이

강의에서 소개하는 특정 Hardware 구현 예에서는 Floating Point Arithmetic이 같은 Bit-width의 Fixed Point에 비해 훨씬 큰 Hardware Resource와 Execution Time을 요구한다.

정확한 배수는 구현마다 다를 수 있으므로 강의에서 중요한 것은 **상대적 방향성**이다.

```text
Floating Point
→ Flexible / Wide Range

하지만

Hardware Cost ↑
Latency ↑
Energy ↑
```

이다.

---

# 62. Energy와 Hardware Complexity

더 많은 Circuit을 동작시키면 일반적으로

```text
Switching Activity ↑
↓
Energy Consumption ↑
```

한다.

따라서 Arithmetic Complexity가 높아지면 Power/Energy Cost도 증가한다.

---

# 63. 그래서 GPU는 여러 Precision을 지원한다

현대 AI GPU는 단순히

```text

```

만 지원하지 않는다.

AI Workload를 위해

```text

INT8

INT4

등
```

낮은 Precision 연산도 지원한다.

강의에서는 특히 NVIDIA GPU/Tensor Core가 FP 계열뿐 아니라 INT8·INT4 같은 저정밀 Integer 연산까지 지원하는 이유를 이러한 Energy·Compute Efficiency와 연결한다.

---

# 64. 왜 낮은 Precision을 지원할까?

가능하다면

```text
FP32
```

보다

```text
INT8
```

혹은 더 낮은 Precision을 사용함으로써

```text
Memory ↓

Compute ↓

Energy ↓
```

를 얻을 수 있기 때문이다.

# 65. 수 체계 강의의 최종 메시지

앞 세 차시의 핵심은 결국 이것이다.

> **내 Algorithm이 정말 높은 Range와 Precision을 필요로 하는가?**

필요하지 않다면 더 간단한 Number Representation을 사용함으로써 Resource를 아낄 수 있다.

---

# 112. Arithmetic Complexity와 AI가 연결되는 이유

Neural Network의 핵심은 결국 대규모

```text
Addition

Multiplication
```

의 반복이다.

특히

```text
Matrix Multiplication
```

이 핵심 연산이다.

따라서 Parameter와 Activation을 어떤 Number Format으로 표현하는지가 전체 AI Compute Cost에 직접 영향을 준다.

---

# 113. Multiply–Accumulate

Neural Network에서는 대표적으로

```text
a × b + c
```

같은

```text
MAC
= Multiply–Accumulate
```

Operation이 매우 많이 발생한다.

따라서 Multiplication과 Addition을 저비용 Precision으로 바꿀 수 있으면 전체 Model Efficiency가 크게 달라질 수 있다.

---

# 114. 하나의 Operation 차이가 큰 이유

연산 한 번의 차이는 작아 보일 수 있다.

하지만 Neural Network에서는

```text
Operation Cost 차이
×
Billions / Trillions of Operations
```

이 된다.

따라서 작은 Arithmetic Optimization도 전체 System에서는 큰 차이를 만든다.

---

# 115. Memory Access도 중요

Model Weight가 작아지면 단순 Storage만 줄어드는 것이 아니다.

GPU가 Memory에서 가져와야 하는 Data 양도 줄어든다.

```text
Bit-width ↓
↓
Memory Traffic ↓
↓
Bandwidth Pressure ↓
```

가 가능하다.

---

# 116. AI에서는 Compute만큼 Memory가 중요할 수 있다

특정 Workload에서는 Arithmetic Unit보다

```text
Memory에서 Weight를 가져오는 시간
```

이 Bottleneck일 수 있다.

따라서 Compression은

```text
Compute Optimization
+
Memory Optimization
```

둘 다 가능하다.

# 121. 자주 헷갈리는 점 ① — Carry-out이면 항상 Overflow인가?

아니다.

```text
Unsigned
→ Carry-out이면 Overflow

Signed Two's Complement
→ Sign 관계를 봐야 함
```

이다.

---

# 122. 자주 헷갈리는 점 ② — Signed Addition에서 Carry-out은 무시해도 되는가?

Overflow 판단 기준으로는 Carry-out만 보면 안 된다는 의미다.

실제 Arithmetic Circuit 내부에서는 Carry 자체는 여전히 존재한다.

---

# 123. 자주 헷갈리는 점 ③ — 뺄셈 Hardware는 덧셈과 완전히 별개인가?

Two's Complement에서는

```text
A - B
=
A + (-B)
```

로 구현할 수 있으므로 Adder를 재사용할 수 있다.

---

# 124. 자주 헷갈리는 점 ④ — Fixed Point끼리는 항상 바로 더할 수 있는가?

아니다.

Binary Point 위치, 즉 Scale이 같아야 한다.

다르면 먼저 Alignment가 필요하다.

---

# 125. 자주 헷갈리는 점 ⑤ — n-bit 두 수를 곱하면 결과도 n bit인가?

안전하게 전체 값을 표현하려면 최대

```text
2n bit
```

가 필요할 수 있다.

---

# 126. 자주 헷갈리는 점 ⑥ — 왜 Division이 그렇게 비싼가?

반복적인

```text
Comparison

Subtraction

Shift
```

가 필요하고 Quotient와 Remainder를 계산해야 하기 때문이다.

---

# 127. 자주 헷갈리는 점 ⑦ — Floating Point Addition은 Integer Addition처럼 바로 더하면 되는가?

아니다.

먼저 Exponent를 Align해야 한다.

---

# 128. 자주 헷갈리는 점 ⑧ — Floating Point Addition은 Mantissa를 더하면 끝인가?

아니다.

결과가 Normalized Range를 벗어나면

```text
Post-normalization
```

과 Exponent Update가 필요하다.

---

# 129. 자주 헷갈리는 점 ⑨ — Floating Point에서는 Multiplication이 항상 Addition보다 느린가?

강의에서 소개한 Hardware 관점에서는 반드시 그렇지 않다.

Floating Addition은 Exponent Alignment 때문에 많은 순차 단계가 필요해 Multiplication보다 Latency가 길어질 수도 있다.

---

# 130. 자주 헷갈리는 점 ⑩ — Floating Point는 무조건 나쁜가?

아니다.

매우 넓은 Dynamic Range와 사용 편의성을 제공한다.

다만 그 대가로 Hardware Complexity와 Energy Cost가 증가한다.

---

# 131. 자주 헷갈리는 점 ⑪ — 좋은 AI Model은 클수록 무조건 좋은가?

Model Scale이 Capability 향상에 도움을 줄 수 있지만 실제 Deployment에서는

```text
Memory

Cost

Latency

Energy
```

제약이 존재한다.

따라서 실제 Service에는 효율성이 필요하다.

---

# 132. 자주 헷갈리는 점 ⑫ — 모델 경량화 = Model File Size 줄이기인가?

아니다.

Model Size는 여러 Target 중 하나다.

```text
Size

Speed

Energy
```

등을 각각 목표로 할 수 있다.

---

# 133. 자주 헷갈리는 점 ⑬ — Model Size가 줄면 반드시 빨라지는가?

아니다.

Target Hardware가 Compression Technique을 효율적으로 지원하지 않으면 Speed-up이 없거나 오히려 느려질 수 있다.

---

# 134. 자주 헷갈리는 점 ⑭ — 경량화는 Accuracy를 유지하면서 Resource만 줄이는 것인가?

이상적인 목표지만 실제로는 Trade-off가 존재한다.

Compression이 강해질수록 Accuracy가 떨어질 가능성이 있다.

---

# 135. 자주 헷갈리는 점 ⑮ — Accuracy Loss가 조금이라도 있으면 나쁜 경량화인가?

아니다.

예를 들어

```text
Accuracy -0.5%
```

를 감수하고

```text
Memory -75%

Latency -50%
```

를 얻는 것이 Application에 따라 매우 좋은 선택일 수 있다.

---

# 136. 자주 헷갈리는 점 ⑯ — GPU에서 좋은 경량화는 모든 Hardware에서도 좋은가?

아니다.

GPU, NPU, Dedicated Accelerator마다 Hardware Structure와 지원 Operation이 다르다.

---

# 137. 자주 헷갈리는 점 ⑰ — Parameter Count만 줄이면 Resource Efficiency가 좋아지는가?

반드시 아니다.

실제 Operator, Memory Pattern, Hardware Support까지 봐야 한다.

---

# 138. 자주 헷갈리는 점 ⑱ — 경량화가 필요한 것은 On-device AI뿐인가?

아니다.

Large-scale Cloud Inference도 엄청난 Compute와 Energy Cost를 요구하므로 Model Compression이 매우 중요하다.

---

# 139. 자주 헷갈리는 점 ⑲ — Training이 끝나면 Resource 문제도 끝인가?

아니다.

실제로 Product를 운영할 때는 지속적으로 Inference Cost가 발생한다.

대규모 Service에서는 오히려 누적 Inference Cost가 매우 중요할 수 있다.

---

# 140. 자주 헷갈리는 점 ⑳ — 수 체계를 왜 이렇게 깊게 배웠나?

이번 강의의 결론으로 연결된다.

```text
Number Representation
↓
Arithmetic Complexity
↓
Hardware Cost
↓
AI Model Compute / Energy
↓
Quantization / Compression
```

을 이해하기 위해서다.

# 141. 이번 강의에서 반드시 기억할 핵심

### 1.

정수·고정소수점·부동소수점을 구분하는 중요한 이유 중 하나는 각 수 체계의 연산 Cost가 다르기 때문이다.

### 2.

Unsigned Integer Addition에서는 Carry-out을 통해 Overflow를 판단할 수 있다.

### 3.

Two's Complement Signed Integer에서는 Carry-out 자체가 Overflow를 의미하지 않는다.

### 4.

Signed Overflow는 Positive 두 개를 더했는데 Negative가 나오거나 Negative 두 개를 더했는데 Positive가 나오는 것처럼 Operand와 Result의 Sign 관계로 판단할 수 있다.

### 5.

Overflow를 판단할 수 있어야 현재 선택한 Bit-width가 실제 Application에 충분한지를 검증할 수 있다.

### 6.

Two's Complement에서는 Subtraction을 `A + (-B)` 형태의 Addition으로 바꿀 수 있어 Adder Hardware를 재사용할 수 있다.

### 7.

Fixed-Point Number끼리 Arithmetic할 때 Binary Point 위치가 서로 다르면 먼저 Scale을 Align해야 한다.

### 8.

Fixed Point의 Radix Point 위치는 Hardware가 자동으로 아는 것이 아니라 System/Programmer가 관리하는 정보다.

### 9.

n-bit Number 두 개의 Multiplication은 전체 결과를 표현하기 위해 최대 2n bit가 필요할 수 있다.

### 10.

Result Bit-width를 다시 n bit로 제한하면 Overflow나 Precision Loss 문제가 생길 수 있다.

### 11.

Division은 Quotient와 Remainder를 만들며 반복적인 Compare/Subtract Operation을 수행하므로 Hardware Complexity와 Latency가 높다.

### 12.

강의에서는 제한적인 Hardware Environment에서 가능하면 Division을 줄이는 Algorithm Transformation도 고려할 수 있다고 설명한다.

### 13.

Fixed Point에서는 Addition과 Subtraction의 Hardware Complexity가 비슷한 편이며 Multiplication은 더 복잡해지고 Division은 특히 느리다.

### 14.

Floating-Point Addition/Subtraction에서는 Mantissa를 연산하기 전에 Exponent를 Align해야 한다.

### 15.

보통 더 작은 Exponent의 Mantissa를 Shift하여 큰 Exponent에 맞춘다.

### 16.

Floating-Point Addition/Subtraction Result가 Normalized Range를 벗어나면 Post-normalization을 수행해야 한다.

### 17.

Post-normalization에서 Exponent가 변경되므로 Overflow 또는 Underflow도 다시 확인해야 한다.

### 18.

따라서 Floating-Point Addition/Subtraction은 Fixed-Point Addition/Subtraction보다 많은 Processing Stage가 필요하다.

### 19.

Floating-Point Multiplication에서는 Sign 처리, Exponent Addition, Mantissa Multiplication을 수행한다.

### 20.

Exponent Arithmetic과 Mantissa Multiplication을 Parallel하게 수행할 여지가 있어 강의의 Hardware 사례에서는 Floating Multiplication이 Addition/Subtraction보다 빠를 수도 있다.

### 21.

Floating Division에서는 Exponent를 빼고 Mantissa를 나누는 구조를 사용할 수 있다.

### 22.

Floating-Point Division 역시 높은 Hardware Cost와 Latency를 요구한다.

### 23.

Floating Point는 넓은 Dynamic Range라는 장점이 있지만 Fixed Point에 비해 Hardware Complexity와 Energy Cost가 클 수 있다.

### 24.

이러한 이유로 AI Hardware는 FP32/FP16뿐 아니라 INT8/INT4와 같은 저정밀 Arithmetic도 적극적으로 지원한다.

### 25.

낮은 Precision Arithmetic을 사용할 수 있다면 Memory·Compute·Energy Cost를 줄일 가능성이 있다.

### 26.

AI Model Scale이 증가하면 Training뿐 아니라 Inference의 Memory와 Compute Cost도 크게 증가한다.

### 27.

Model Capability를 높이기 위해 Model Scale을 키우는 방식은 Resource Requirement를 빠르게 증가시킨다.

### 28.

Hardware 성능 향상만으로 Model Scale 증가를 계속 감당하기 어려워지면서 Model Compression이 중요해졌다.

### 29.

강의에서는 현재 대규모 AI에서 Model Compression/경량화가 선택이 아니라 필수에 가까워지고 있다고 설명한다.

### 30.

Foundation Model Training을 일부 큰 기업이 수행하더라도 실제 Service를 위한 Inference Cost 문제는 여전히 남는다.

### 31.

대규모 User Service에서는 Query당 작은 Resource 차이도 누적되면 매우 큰 Cost 차이가 된다.

### 32.

Model Compression의 목적은 허용 가능한 Model Quality를 유지하면서 Resource와 Cost를 줄이는 것이다.

### 33.

모델 경량화의 Target은 하나가 아니다.

### 34.

대표적인 Target은 Model Size, Inference Speed/Latency, Energy Consumption이다.

### 35.

Memory가 부족한 경우 Model Size Reduction 자체가 목표가 될 수 있다.

### 36.

Model이 Memory에는 들어가지만 너무 느리다면 Latency Optimization이 목표가 된다.

### 37.

Battery나 Thermal Constraint가 중요하면 Energy Reduction을 목표로 할 수 있다.

### 38.

경량화에서는 어떤 Resource Metric을 개선하려는지 먼저 명확하게 정의해야 한다.

### 39.

Compression이 강할수록 일반적으로 Model Accuracy/Quality가 떨어질 가능성이 높아진다.

### 40.

따라서 모델 경량화의 핵심은 Accuracy와 Resource Efficiency 사이의 Trade-off를 적절하게 선택하는 것이다.

### 41.

Resource를 크게 줄였더라도 Accuracy가 사용할 수 없을 정도로 떨어지면 좋은 Compression이라고 할 수 없다.

### 42.

반대로 아주 작은 Accuracy Loss로 큰 Memory·Latency·Energy Improvement를 얻는다면 좋은 Engineering Trade-off가 될 수 있다.

### 43.

Model Size가 줄었다고 실제 Execution Speed가 반드시 빨라지는 것은 아니다.

### 44.

Target Hardware가 해당 Compression Representation이나 Operator를 효율적으로 지원하는지 확인해야 한다.

### 45.

따라서 Model Compression에서는 Algorithm과 Hardware의 궁합이 중요하다.

### 46.

GPU에 잘 맞는 경량화 기법과 NPU/전용 Accelerator에서 잘 맞는 기법은 다를 수 있다.

### 47.

NPU나 AI Accelerator는 Neural Network와 저정밀 Operation을 더 효율적으로 처리하도록 Specialized Hardware를 제공할 수 있다.

### 48.

On-device AI에서는 Memory, Power, Thermal, Compute Constraint가 모두 강하기 때문에 모델 경량화가 특히 중요하다.

### 49.

Cloud AI에서도 Model Scale과 Request Volume이 매우 크기 때문에 Compression은 중요하다.

### 50.

모델 경량화를 평가할 때는 Parameter Count나 File Size뿐 아니라 실제 Accuracy, Latency, Memory, Energy를 함께 봐야 한다.

### 51.

Neural Network는 대규모 Addition과 Multiplication을 수행하므로 Arithmetic Precision과 Hardware Complexity가 전체 AI Resource Cost에 직접 연결된다.

### 52.

작은 Operation 하나의 효율 차이도 수십억·수조 번 반복되면 전체 System에서 큰 차이가 된다.

### 53.

Bit-width를 줄이면 Weight Storage뿐 아니라 Memory Traffic과 Bandwidth Pressure도 줄일 수 있다.

### 54.

따라서 Model Compression은 Compute뿐 아니라 Memory System Optimization과도 연결된다.

### 55.

이러한 전체 배경을 이해한 뒤 다음의 Quantization, Pruning, Distillation 등 구체적인 경량화 기법을 학습하게 된다.

# 146. 이번 강의 핵심 한 문장

> **연산과 복잡도 관점에서 보면 Integer와 Fixed-Point Arithmetic은 상대적으로 단순한 Hardware로 구현할 수 있지만 Floating-Point Arithmetic은 Exponent Alignment·Mantissa Shift·Post-normalization·Overflow/Underflow 처리 등 추가 단계가 필요해 더 큰 Latency·Hardware Area·Energy Cost를 요구할 수 있으며, 이러한 Arithmetic이 수십억·수조 번 반복되는 AI Model에서는 Number Precision의 작은 차이도 전체 Resource Cost에 크게 영향을 준다. 동시에 Scaling Law를 따라 AI Model 규모와 Training·Inference Compute가 빠르게 증가하면서 Hardware 발전만으로 이를 감당하기 어려워졌기 때문에 Model Compression이 중요해졌으며, 실제 경량화는 단순히 Model File을 줄이는 것이 아니라 허용 가능한 Accuracy Loss 안에서 Model Size·Latency·Energy 등의 목표를 개선하는 Trade-off 문제이고, 실제 효과는 GPU·NPU 등 Target Hardware가 해당 Compression Technique을 얼마나 효율적으로 지원하는지까지 함께 고려해야 한다.**
